# Format notes & reference-code pointers

Read only the section you are working on.

The reference projects cited below (`pyglossary/…`, `mdict-go-web/…`, `draego/…`) are **no longer on disk** — they were removed once the formats were implemented. Their file and function names are kept as provenance: they say where a parsing rule came from and what to search for upstream if a format ever misbehaves, not paths to open.

## MDX / MDD (Octopus MDict)
- **Reference: [`docs/mdict/`](mdict/README.md)**: byte layout (`FORMAT.md`), engine semantics (`SEMANTICS.md`) and wudict's conformance (`CONFORMANCE.md`), read from MDict's own engine. Where this section and `docs/mdict/` disagree, `docs/mdict/` is right.
- Binary, block-compressed (zlib/LZO), optionally encrypted (Salsa20/8 variant), v1.2–v3.0. Has built-in **headword index** (key blocks) — no full-text index. MDD = same container holding resources keyed by `\path\name`.
- Go reader EXISTS and works: `mdict-go-web/internal/gomdict/` — entry points `mdict.go` (`New`, `BuildIndex`, `Lookup`, `Keys`), v3 support in `v3reader.go/v3block.go/v3crypto.go`.
- Plan: inline `gomdict` into the new module. Importer = iterate `Keys()` + locate/decode each record. Resource resolver = existing MDD lookup path. `@@@LINK=` entries become `alias` rows. Embedded `Description`/`StyleSheet` header fields → `meta`.
- Python cross-check: `pyglossary/pyglossary/plugins/octopus_mdict_new/reader.py` (thin; real logic in `pyglossary/plugin_lib/readmdict.py`).

- **Key-list encoding is a property of the version, not of the file type.** In v1.2/v2 an MDD whose header names no encoding has UTF-16LE keys with a two-byte NUL terminator, which `readDictHeader` encodes as the MDD default `meta.keyEncoding = EncodingUtf16` (an `.mdx` defaults to GBK, as in MDict). **v3 is UTF-8 unless the KeyData trailer says otherwise, MDD included**, so its keys are single-byte with a one-byte NUL. Anything that needs the terminator width or the decoder must read `meta.keyEncoding` and never `fileType == MdictTypeMdd`: the two agree for v1/v2 and disagree for v3. `splitKeyBlock` got this from the file type until P73, which walked v3 MDD key blocks at a two-byte stride, stepped over every terminator, and then read one byte past the block (`index out of range [143] with length 143`) or sliced backwards from a stale end index (`slice bounds out of range [32734:32724]`). The failure surfaces as *"<name>.mdx: corrupt or unsupported file"* because the sibling `.mdd` is opened under the `.mdx`'s name — check the `.mdd` first.

- **`@@@LINK=` is not always the whole record.** The marker is documented as the entire record body (`@@@LINK=headword`) and most makers write exactly that, so a prefix test passes on almost every dictionary. Some dictionaries wrap `@@@LINK` in the same HTML shell it gives every article — `<head><link rel="stylesheet" href="OED.css"/></head><div class="entry">@@@LINK=pandore</div entry>` — and a prefix test recognises **none**: they become articles whose visible text is the literal string `@@@LINK=pandore`, both on screen (`Dict.render`) and in the prepared `text.db` (`Reader.Next`, where they should have been `alias` rows). `mdx.linkTarget` therefore discounts markup: a record is a redirect when the marker is the only **visible text** in it, so an article that merely mentions the marker in its prose keeps its body. Both the runtime and the ingest path call it, because a redirect resolved in preview and rendered raw once prepared is the same bug seen twice.

- **Loose sibling assets**: MDict serves files sitting next to the `.mdx`, and **before** the `.mdd` (docs/mdict/SEMANTICS.md §4). That is how a user overrides a packed stylesheet, and how repacks ship their stylesheet and scripts (LDOCE6 keeps `LDOCE6.css` and `entry.js` loose, with no `.mdd` at all). `Dict.Resource` therefore tries the `.mdx`'s own directory first, at the cost of one stat (~1 µs against a ~100 µs HTTP round trip), and **pack media** inherits the order because it reads through `Dict.Resource`. A packed dictionary serves what was packed: an override dropped in after packing takes effect on the next repack. Guards: the ORIGINAL name is used (the index key is lower-cased; `LDOCE6.css` ≠ `ldoce6.css` on a case-sensitive filesystem), the path must stay inside the dictionary's folder, and only asset extensions a dictionary legitimately loads are served — article HTML is third-party, so a stray `href="secrets.env"` must not turn `/res` into a file browser. Loose files are not in `Resources()` (that lists the `.mdd`), so **pack media** adds the ones articles actually *reference*, via `store.ReferencedAssets` — reading the prepared text.db rather than re-parsing the source, and referenced-only because dictionary folders commonly hold several dictionaries and sweeping would pack a neighbour's assets. A packed dictionary therefore keeps its stylesheet and scripts after the source is gone.

## StarDict
- File family: `.ifo` (ini-ish metadata; `sametypesequence`), `.idx`/`.idx.gz` (sorted: word\0 + 32/64-bit offset+size BE), `.dict`/`.dict.dz` (concatenated articles; dictzip = gzip with random-access extra field), `.syn` (synonym → idx-entry index), optional `res/` dir or `res.zip`.
- Article types by `sametypesequence` char: `m` text, `h` HTML, `x` XDXF, `g` Pango, etc. Importer must convert `m`→escaped `<p>`, `x`→HTML (see `pyglossary/pyglossary/xdxf/`), pass `h` through.
- `r` is a resource list, one `type:name` per line (`img:`, `snd:`, `vdo:`, `att:`), names relative to `res/`/`res.zip`. Drawn with `artmark.Media` — the markup DSL's `[s]` uses — by what a browser can do with the file, so `vdo:film.avi` is a file link; `att:` is always one (StarDict ReaderVersion 2). pyglossary reads `r` as plain text; GoldenDict draws it, as here.
- A compressed `.idx` is loaded whole; its inflate bound is the larger of 256 MiB and 16× the compressed size (an index deflates 3–5×, a gzip bomb ~1000×), so a Wikipedia-scale index is read and a bomb refused.
- Reference: `pyglossary/pyglossary/plugins/stardict/reader.py` (idx/syn/dict.dz parsing, sametypesequence handling).
- Go effort if done directly at runtime: ~600–900 LOC + dictzip random access. Under hybrid plan only the sequential import path is needed (simpler: gunzip whole .dict.dz streamwise). Resource resolver: plain files in `res/` or zip entries.

## Aard2 Slob
- Single `.slob` file: header + tags + content-type list + sorted **ref** list (key → bin/item) + LZMA2(default)/zlib-compressed **bins** of items. Has built-in headword index; correct binary search requires ICU UCA collation (pyglossary depends on pyicu — a Go runtime port of that lookup is the riskiest piece of any "direct" plan).
- Reference: `pyglossary/pyglossary/slob.py` or `pyglossary/pyglossary/slob/` (container format), `pyglossary/pyglossary/plugins/aard2_slob/reader.py` (tags, `<a href>` rewriting).
- Hybrid plan: importer walks refs sequentially (no collation needed), decompresses bins once (`ulikunitz/xz` for LZMA2). Resource resolver: keep slob open, direct item fetch by stored bin/item ids (store them in `alias`/aux table or resource name map at import).
- **The ref list is sorted by key; its records are not.** slob.py and pyglossary sort the *position table* and leave the records in the order they were added — verified on the 6.2 GB OED 2020 and the 1.1 GB LEXICO slobs, whose list order and record order disagree. So a walk in list order reads the file at random, and `locate` + `walk` read the position table, sort it by position, and walk the records front to back. Nothing is read at open beyond the header and the list's first and last records; the Reader keeps 24 bytes per ref (place in the list, blob, record position) and reads a blob's keys when it emits the blob, ordering them by place in the list so the display headword is the one the list puts first. Only a preview lookup decodes the whole list (`allRefs`).

## Lingvo DSL
- Plain text, UTF-8/UTF-16(+BOM)/UTF-32; optional `.dsl.dz` (dictzip); optional `.ann`, `.bmp`, and `_abrv.dsl`; resources in `<name>.dsl.files.zip` (plain zip). NO index of any kind ⇒ always fully ingested.
- Syntax: headword line(s) at col 0 (multiple consecutive = same card; `{...}` unsorted parts; `(...)` optional-variant expansion; `~` = headword ref; `<<link>>`), body lines indented; tags `[b][i][c][p][m1..9][s]media[/s][ref][url]...`.
- Reference: `pyglossary/pyglossary/plugins/dsl/` — `lex.py` (tag lexer), `transform.py` (→HTML), `title.py` (headword variant expansion), `reader.py` (encoding detect, .dz handling).
- Go: write lexer/transformer fresh, port rules from the above. dictzip read = sequential gunzip (stdlib `compress/gzip` handles dictzip files sequentially). Resource resolver: `archive/zip` over `.files.zip`.
- **Full reference: `docs/DSL.md`** — grammar, tag table, media zone, encodings, resource-name matching, pipeline map and the running list of known gaps, written for a model to consume. Read it instead of re-deriving DSL behaviour.
- IMPLEMENTED (P4) in `internal/format/dsl/`. Deviations from pyglossary: malformed/empty tags degrade to literal text instead of dropping the entry (real data contains raw `([ ])`); headword variants are stored raw, not XML-escaped. `<name>_abrv.dsl` is absorbed at ingest, not listed: its expansions are baked into the parent's `[p]` labels as `<abbr title=…>` and discovery hides the companion (Lingvo's own behaviour). A `*_abrv.dsl` with no sibling parent stays an ordinary dictionary. A `<name>.ann` annotation is read live (never ingested, never a staleness input) and served as the dictionary's About text, every `#LANGUAGE` section of it, in file order. `#INCLUDE` files are read after the main file, resolved against the including file's folder and never outside it: an absolute, UNC or climbing path is tried by base name beside the includer and nowhere else (a UNC stat on Windows opens an SMB session). Prepared into a library folder named after the source file (D20); a changed source is detected from the recorded size/mtime/hash and re-indexed in place. `WUDICT_DB_DIR` overrides the library location.

## Babylon BGL (added P10)
- Single `.bgl` file: 6-byte header (`\x12\x34\x00\x0{1,2}` + gzip payload offset), then a **gzip stream with an absent/zero CRC trailer** (treat `ErrChecksum`/short trailer as clean EOF). Payload = variable-length blocks, one header byte: **low** nibble = type, **high** nibble = length (`n < 4` means the length is the next `n+1` bytes, big-endian; otherwise the length is `n - 4` inline); type 4 = end marker, type 2 = embedded resource, types 1/7/10/13 = standard entries, type 11 = 5-byte-length entry layout.
- Encoding is a resolution chain, not a field: UTF-8 flag → charset code → source/target language code → cp1252 fallback; `<charset c=X>` tags switch encoding *within* a string (incl. Babylon hex references). Definitions carry `\x14`-delimited fields (part of speech, title, transcriptions). Codecs via `golang.org/x/text` (cp125x, cp874, ShiftJIS, GBK, Big5, EUC-KR), lenient decode.
- Reference: `pyglossary/pyglossary/plugins/babylon_bgl/` (most complete parser); GoldenDict for the **streaming** model — never `io.ReadAll` a BGL.
- IMPLEMENTED in `internal/format/bgl/` (`reader.go` streaming core, `decode.go` key/definition processing, `text.go` cleanup helpers, `tables.go` charset/language/POS tables, `bgl.go` backend). No native index ⇒ DSL-style auto-ingest on first open; type-2 resources served from a lazily-scanned map (direct) or packed into `media.db` (native path).
- **Some BGLs key entries by internal identifier, not by word** (Larousse *Gran Diccionario de la Lengua Española*: every key is `E310420`, the word is in the definition's `\x18` title field and repeated among the alternates, and articles cross-link by id — `bword://E310420`). The metadata pass samples the first 1000 entries and, if ~all of them show that shape, the reader files each entry under its title and demotes the id to an alternate (D71). Whole-file verdict, never per-entry: single entries in Merriam-Webster Collegiate (`A` / `Å`) and Larousse Compact (`about time` / `time`) match the same test and must not be rewritten.

## openZIM (added P92)

- Single `.zim`: 80-byte LE header (magic `0x044D495A`; major/minor u16 at 4/6; `entryCount`/`clusterCount` u32 at 24/28; u64 `pathPtrPos`/`titlePtrPos`/`clusterPtrPos`/`mimeListPos` at 32/40/48/56; u32 `mainPage`/`layoutPage` at 64/68; u64 `checksumPos` at 72), then a NUL-terminated MIME list ended by an **empty string** inside the bound of the nearest structure the header points to (path/title/cluster pointer lists, first dirent, first cluster — libzim `getMimeListEndUpperLimit`; entry text is never validated, and a non-type entry such as mwoffliner 2021's `undefined` declares no type), dirents, clusters, and two u64 pointer lists. A dirent is u16 mimetype, u8 parameterLen, u8 namespace, u32 revision, then u32 `redirectIndex` (mimetype `0xFFFF`), nothing (`0xFFFE`/`0xFFFD`, the deprecated linktarget/deleted markers) or u32 cluster + u32 blob, then NUL path, NUL title, then `parameterLen` bytes — an 8-, 12- or 16-byte fixed prefix and a variable tail, so it can only be read by growing a window, never by a fixed struct. A marker read with a blob's 16 bytes has a garbled path, and a binary search probing it goes the wrong way for any word (libzim `DirentReader::initDirent`). The first headers were **72 bytes**: `mimeListPos` 72 means no checksum, and bytes 72-80 are MIME text (`Fileheader::hasChecksum`). A cluster is an info byte (`codec = b & 0x0F`, `extended = b & 0x10` ⇒ 8-byte offsets) followed by a compressed stream whose FIRST bytes are the blob offset table: read one offset, and `blobCount = offset[0]/W - 1`. The format stores no cluster size. A cluster's extent runs to the next cluster or to the first structure after it: the path and cluster pointer lists, the first dirent (`ptr[0]`, the lowest dirent in every file checked), the checksum, believed only at `size-16`, where libzim requires it. Since 6.0 the dirents follow the clusters, so bounding the last cluster by the checksum handed a compressed one every dirent and both pointer lists, which xz and zstd read as a damaged second stream. **`titlePtrPos` is never a bound**, because in 6.1/6.2 files it points *into* a stored cluster, at the v0 title listing blob. Decoding also stops at the stream's end, as libzim's does (it reads a cluster from its offset to the file's end and decodes only what the offset table names): a zstd extent is cut to its frames by walking the frame and block headers, and an xz, bzip2 or zlib stream that fails to its end is read again by its offset table (`readTable`). A pointer list out of file order (no writer leaves one; libzim reads it) is ordered for the extents.
- Codecs: 0/1 none, 2 zlib, 3 bzip2, **4 xz**, 5 zstd. Only 1 and 5 occur in a 9-file corpus (16,544 clusters), and `extended` is never set, but all five are implemented — three are three lines each. `zstd` is why `github.com/klauspost/compress` is a dependency; cgo libzim is disqualified outright by D4.
- **Decoder sizes come from the stream, not the data.** xz clusters of the old layout declare xz -9's 64 MiB LZMA2 dictionary, and `ulikunitz/xz` allocates the larger of that and its own cap per cluster of 1-2 MB; `xzWithDict` rewrites the block header's dictionary byte to 4 MiB (CRC32 recomputed) and decodes again as declared on a distance or check failure. zstd frames from libzim carry no content size, so `DecodeAll` without a destination allocates 4.6x its output; clusters decode into reused buffers. The blob offset table is checked whole (every offset past the table, inside the body, non-decreasing): checking `offset[0]` alone serves the first blob from inside itself when the header overstates it. All three are pinned by `make test-zim-suite`, openZIM's zim-testing-suite.
- **Namespaces are versioned.** `minorVersion >= 1` (ZIM 6.1), under either major as libzim decides it (`useNewNamespaceScheme`), means the new scheme — `C` content, `M` metadata, `W` well-known, `X` index; below it, `A` articles, `I` images, `-` layout, `M` metadata. The whole compatibility story is one function (`contentNS()`), and every content lookup, resource lookup and link rewrite routes through it. ZIM 6.3 also **removed the title pointer list** (`titlePtrPos` = `0xFFFF…FF` in all nine corpus files).
- **The path pointer list is sorted in raw byte order over `(namespace, path)`** — verified across all 181,966 entries of a real wiktionary, zero inversions. That is what makes this the first format in the tree whose direct backend needs **no resident index at all**: exact and prefix lookup are a binary search over the file (~2 `pread`s per level). The top 11 levels are the same entries for every word, so their keys are kept as searches reach them (`keyCache`, 2047 slots per sorted list, path and title order alike). That halves a miss's reads with no open cost, where libzim reads a 1024-key grid at open. Separately, `docs/SPEC.md` §6c's ban on binary-search work in a direct backend does not apply, because that rule targets a *guessed* collation and byte order is exactly what the file was written with. Consequence: `Dict` implements `PreviewBytes` and `SelfIndexed` (`internal/server/registry.go`), so the server neither bills it for a map it does not hold nor prepares it behind the user's back — ZIM packs whole clusters with zstd (~14×) while a prepared `text.db` DEFLATEs one article at a time (~3.5×, D24), so preparing a 123 MB wiktionary would *expand* it to ~431 MB. Preparation stays available on request; only the automatic path declines.
- **Split archives** (`.zimaa`, `.zimab`, … to `.zimzz`: `split -b`, to fit FAT32's 4 GiB per file) are one ZIM cut at arbitrary byte offsets, so a dirent, a cluster or a blob may span parts. `split.go` reads the parts as one file (`joined`, a binary search over the part offsets); nothing above it knows. `.zimaa` is the main file and the later parts are its companions (`dict.ZIMParts`, the run ending at the first gap); intake asks for them as a run outside its probe budget, every part required.
- **Titles are not always paths.** zimwriterfs keys entries by file name (`Main_Page.html`, titled "Main Page") and devdocs by doc path, so a path lookup misses their titles. The file's own title order - u32 entry indices sorted by `(namespace, title)` in raw byte order - is the fallback (`title.go`, D96 Am. 1): the header's title pointer list (before 6.3), else `X/listing/titleOrdered/v0`, else `v1`, which holds front articles only and no redirects. In every file checked the listing sits in a stored cluster, so a probe is three preads.
- Paths carry no percent-encoding, spell a space `_`, and store an **empty title when it equals the path** — so the headword is `title or path`, and a `_` is never substituted back. MediaWiki capitalises the first letter of a title, so a user's word is tried in a short closed list of spellings (`pathVariants`), each one binary search; that is not case folding, and folded, wildcard and full-text search still arrive with preparation.
- Articles are complete HTML documents. `articleBody` keeps the `<body>` inner HTML plus the head's stylesheet `<link>`s (22% smaller on a real wiktionary), falling back to the whole document when there is no `<body>` — devdocs and zimit captures depend on that fallback. Tag names are matched as ASCII in the document itself: offsets taken from a lower-cased copy are wrong after any letter whose lower case is shorter (`İ`, the Kelvin sign).
- **References are relative to the article's own path**, and a browser resolves them against the URL Kiwix serves it at: `../I/pic.png` from `A/Foo` (every pre-6.1 file), `../../application.css` from `archive/tar/index` (devdocs), `Python/Subpage` from `Python` (wikibooks). Left relative, they were resolved against wudict's URL instead, where `/res/{id}/../I/pic.png` climbs out of the dictionary's folder. `rewriteRefs` resolves every one (RFC 3986 §5.2 with WHATWG's `%2e` dots; `resolveRef`) against the entry's long path (`A/Foo` before 6.1, the path after). A resource becomes its path from the archive's root, which the server maps to `/res/`. An `<a>`/`<area>` link to an article becomes `entry://`: before 6.1 that means the `A` namespace, or a path with none, as libzim looks it up. A link to a stored file (an asset extension other than `.html`/`.htm`, zimwriterfs' and zimit's article names) becomes a resource. Old-scheme `Resources()` names carry their namespace (`I/pic.png`), the names the articles now ask for; `Resource` still takes a bare one. `Exact` retries a path that misses without a one-letter namespace prefix, as libzim's `getEntryByPath` does.
- **libzim parity, measured.** Redirect chains are followed for 50 hops (libzim's watchdog); metadata redirects are followed (`findxMetadata`); a cluster pointer past the file's end costs that cluster's entries, and only a *last* one refuses the file, as a cut-off download (`quickCheckForCorruptFile`); the `M` namespace is read once at open instead of a binary search per key. A differential harness, libzim 9.8 through its public API against this reader, compared every entry of 14 real files (1.79M entries: wiktionary es/ca/ro, wikibooks, bitcoin 2021 old-scheme, devdocs, ZIM 5.0 xz) and of the suite's valid files in all three layouts. It compared kind, path, title, redirect target, MIME, size, content hash, title order and every metadata value, and all were byte-identical. Where they differ, the difference is leniency here: libzim refuses `invalid_checksumpos`, a title list out of bounds, and the broken-blob files, because its constructor touches the damaged cluster through the v1 listing, while this reads every undamaged entry.
- **Nothing proportional to the file is resident.** The path pointer list (8 B per entry, 160 MB on a 20M-entry Wikipedia) is read a 4 KiB page at a time; a stored cluster (codec 0/1 — images, video) is never loaded: its offset table and blobs are read in place, and a resource is served as a seekable window onto the file, so Range requests reach video without buffering it.
- **No `resource.Provider` is registered**, for the same reason bgl has none but the opposite arithmetic: O8's locator exists because reopening an `.mdx` costs 280 MB of index build, and reopening a `.zim` builds nothing at all. Rung 3 is already the cheap path.
- Reference: **`unidict-deps/czim`** (C11, plus its `docs/zim_format.md`) is the only from-scratch implementation of the four that were available, and the structural source here; pyglossary's `zimfile`, `zim-cgo`, and — contrary to expectation — **goldendict-ng's `zim.cc`** are all `libzim` shims and carry no binary knowledge. Two czim defects are **not** ported: a fixed 256-byte MIME-string buffer that silently desynchronises the list walk (a zimit capture has multi-kilobyte paths), and `lzma_alone_decoder` for codec 4, where real files write an **xz** stream (`FD 37 7A 58 5A 00`).

## wudict markdown (D154)

- Normative spec: `docs/WUDICT-MARKDOWN.md`. The examples (`docs/wudict-markdown/examples/{clean,html}.wudict.md`)
  are the spec's §10 byte for byte, and are what the writer produces from §10's sources.
- Standard CommonMark + GFM tables, read by a **stock** parser with no plugins: goldmark v2 (`extension.TableParser`,
  `html.WithUnsafe()`). Entries are the top-level H2 nodes; adjacent H2s are one entry (headword + aliases).
  Verified on the Espasa-Calpe dump in both modes: stock markdown-it-py (`commonmark` + `table`) finds the same
  38,521 entries with the same names.
- `internal/format/wmd`:
  - `read.go`, `index.go`, `units.go` — the reader (D182), in two phases that each parse every byte once. Phase 1
    (inside `NewReader`) reads the structure with goldmark's block parsers alone — the same top-level blocks as the
    full parser (a syntax tree costs ≈43× its text, a block-only one far less) — in ~1 MB chunks cut at heading
    groups. The cuts are chosen ahead and parsed in parallel; each is confirmed by its own chunk's parse, and a
    rejected one (a `## ` line inside a code or HTML block) is repaired by doubling the window over the cuts chosen
    ahead. Each chunk contributes its own link definitions (first label wins, file order); a parse is given only the
    definitions its bracket spans can reference (`labels.go`). Heading text is read once every definition is known:
    a heading without inline syntax is its content, the others are parsed again from their lines alone; then the
    title, header and description from a full parse of the text before the first group. Redirects (`see:`) are
    folded into every matching article (exact, then case-folded); a dangling one becomes a lookup-link article.
    Phase 2 (`Next`) renders units of whole heading groups (~256 KiB), on worker goroutines while the preparation is
    urgent (`dict.Urgent`), inline otherwise, always in file order, with a drift guard against phase 1. Warnings come
    in the order the file read whole gives them.
  - `source.go` — the text a Reader reads a range at a time (`ReaderAt`), so it never holds a whole file: a clean
    plain file in place; a compressed file, or one needing R2.1 repair, decoded once (streaming, across block
    boundaries) into 4 MiB blocks in memory while the preparation budget grants them (`sysmem`, twice their size,
    at most a quarter of the budget), past that into a temporary file removed on Close, and into memory where no
    temporary file can be made. The same pass collects the candidate entry lines and lines 1-2, with
    `bytes.Index`/`IndexByte`/`utf8.Valid` (≈0.3–0.9 ns a byte; a 17 GB file reads at the disk's speed). The
    temporary file stops before the disk holding it falls under 1 GiB free, the memory copy at half the configured
    Go memory limit (else 1 GiB): `*dict.NoRoomError`, which is `dict.ErrTooLarge`.
  - `load.go` — R2.1 decoding of a block; `.gz`/`.dz` suffixes. The R2.4 bound on a compressed file is 1 GiB or
    32 times the file's size, whichever is more (`unpackBound`; a 166 MB Wiktionary unpacks 7.0 times, a gzip
    bomb 100 and more), capped at what the build addresses (2 GiB on 32-bit). Past it: E-format, which is
    `dict.ErrUnreadable` and `dict.ErrTooLarge`.
  - `wmd.go` — registration: every spelling (`.wudict.md`, `.md`, `.wudict.md.gz`, `.wudict.md.dz`) through
    `dict.RegisterSniffed` + `Claim`, so the gate is the same whatever the name (R2.2): line 1 `# title`, line 2
    the `wudict` field, read from a 4 KiB head (decompressed for `.gz`/`.dz`). A DSL-style auto-prepared `Dict`,
    and `MediaSources` (`<stem>.files.zip`, `<stem>.files/`, loose files). The gate reads the source's head on
    every open; the prepared store is then opened without reading the rest.
  - The gate is `dict`'s, applied everywhere a file becomes a dictionary: `Discover`, `Open`/`OpenReader`
    (which report the claim's reason for an explicitly named file), `IsDictionaryFile`, and intake through
    `dict.ClassifyName` → `KindCandidate` + `dict.Claims`: an archive entry's head is read in `intake.Sniff`, a
    loose file's on disk (`OpenPlain`, `holdsDictionary`, `probeCompanions`), and a download may begin by
    name alone (`canBegin`) and is settled once it has arrived.
  - `convert.go` — `clean` mode: one walk applying the R6.6 allowlist and R6.7 escaping, then a stock parse
    proving the body cannot split its entry. Fuzzed as a fixed point: converting the stock rendering of its
    output gives the same output.
  - `rawmode.go` — `html` mode: `CanonLinks`, the `<div>` wrapper unless already one type-6 element, blank lines
    removed or turned into `&#10;` inside `pre`/`textarea`/`listing`.
  - `writer.go` — names (R6.2), header keys (R6.3), bodies spooled to a temporary file with only names in
    memory, redirect folding with chains (R6.4), assembly (R6.1).

- F22 (done) — wudict never emits `bword:`. `bword:` is Babylon Ltd.'s proprietary cross-reference scheme, from its BGL glossaries and Babylon Builder projects (late 1990s); no public RFC-style specification exists, only the behaviour open-source dictionary readers reverse-engineered and preserved. Emitters switched to `entry://`: CSV dump redirect anchors, DSL `[ref]`/`<<ref>>` (dsl reader 2), ZIM `entryRef` (zim reader 2); prepared dictionaries get the stale/rebuild offer, never a forced rebuild. A dictionary's own `bword:` links are stored as found and respelled on every way out by `htmlref.CanonRef`/`CanonLinks` (`bword:[//]w` → `entry://w`, `@sub` → `entry:@sub`): the server's article rewrite (so BGL id links like `bword://E310420` too), `lookup -format raw`, and the CSV dump of both a source and a prepared `text.db`. Resolvers (`parseRef` in `index.html`/`frame.js`) keep accepting `bword:`. Targets are built by `htmlref.EntryHref` (`%`, `#`, controls and a leading `@` percent-encoded), so `[ref]C#[/ref]` links to `C%23`, not to `C` with an empty fragment (dsl reader 3, zim reader 3).
- **The wudict howto** (`internal/howto/wudict-howto.wudict.md`) is the format's standing proof. `howto_test.go`
  checks that it:
  - passes the gate and reads without a warning;
  - keeps every headword under `wudict `;
  - resolves every `entry://` link to one of its headwords, and links only to app pages (`/browse`, `/setup`,
    `/lemmas`);
  - ships every image it shows and shows every image it ships;
  - comes back byte for byte from `wudict dump -mode clean`.

  Write it in that canonical form: one line per paragraph; bold and italic that start and end with a letter
  (punctuation outside); `<kbd>` for controls.
- **Known limit (R9.3, accepted 2026-09-28):** stock goldmark is quadratic on list markers nested on one line
  (`- - - … x`: 40k deep = 2.3 s) and on tens of thousands of reference definitions in one entry (40k = 0.5 s);
  the reader parses every byte twice (a block parse, then a full one). No guard: a crafted file in a dictionary folder can hold its first
  open (the auto-prepare) for minutes. Every other shape measured (brackets, emphasis, backticks, `<`, quotes,
  ordered lists, headings, `##` inside code or HTML) scales linearly.
