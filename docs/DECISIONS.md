# Decision log (ADR-lite)

Status: PROPOSED (awaiting user), ACCEPTED, REJECTED, SUPERSEDED. One line of context each; details in SPEC.md.

## D1 — Source handling: dual-backend — **ACCEPTED 2026-07-24 (user-directed)**
Default = **direct readers** over native format indexes (exact/prefix lookup, zero import step). **Ingest is opt-in** via config `ingest = off|text|full` (global default + per-dictionary override) and unlocks fuzzy/FTS. DSL auto-ingests text transparently (no native index). Supersedes the earlier hybrid-ingest-only proposal.
- Consequence: format packages implement both a runtime `Lookuper` and a sequential `Reader` (ingest scan) — parsing written once, two entry points.
- Known risk accepted: Slob direct lookup uses in-memory refs + Go collation instead of ICU; huge slobs may need a sidecar key cache later.

## D2 — Resource storage — **ACCEPTED 2026-07-24 (user-directed)**
`ingest=off|text`: resources lazy from source (MDD/res/res.zip/.files.zip/slob bins). `ingest=full`: resources packed into a **separate** `<slug>.media.db` (never mixed into the text DB) so text DBs stay small and exchangeable. Pairing via shared `dict_uuid`; runtime resolution order media.db → source → 404; text.db alone degrades gracefully.

## D3 — Server model: persistent HTTP server — **ACCEPTED 2026-07-24**
mdict-go-web style (config layering, auto-open browser). CGI dropped: kills pooling, in-memory direct-backend indexes, SSE progress. CGI shim possible later.

## D4 — SQLite driver: mattn/go-sqlite3 — **ACCEPTED 2026-07-24, AMENDED 2026-07-25**
cgo driver, build with `-tags sqlite_fts5` (as draego does), for native/dev builds. Amendment (P7): release cross-builds use `-tags purego` → `modernc.org/sqlite` (pure Go, FTS5 included) so the GitHub workflow builds every target on one ubuntu runner with CGO_ENABLED=0 — no C toolchains. Both drivers pass the same test suite (`make test-purego`).

## D5 — UX wording for ingestion: "Enable fuzzy & full-text search" — **ACCEPTED 2026-07-24**
Per-dict/all action; progress "Preparing search index…"; full-ingest variant "…and pack media". Ingest is a feature upgrade, not onboarding — adding a dictionary = dropping files in the dict dir.

## D6 — Project/module name — **SUPERSEDED 2026-08-02 by D28**
`github.com/wuweidict/wudict`, code in `wudict/` subdir of the workspace. The module path is now `github.com/wuweidict/wudict` and there is no enclosing workspace.

## D10 — Makefile as developer UI/manifest — **ACCEPTED 2026-07-24 (user-directed)**
The Makefile is the canonical entry point for every meaningful dev action (build/test/run/lint/cross-compile/bench/…), self-documenting via `make help` (default target). New capabilities MUST land with a Makefile target.

## D7 — Location of generated .db files: cache dir only — **ACCEPTED 2026-07-24**
`~/.wudict/db/` — dict dirs stay pristine, works on read-only sources. Since DBs are exchange artifacts, the UI must expose them ("Reveal in Finder" / show path per dictionary) so users can find and share them despite the hidden location.

## D12 — Open strategy & streaming search — **ACCEPTED 2026-07-25 (user-directed, P8)**
Opening a dictionary (heavy in-memory index) is the real latency, not searching. Three rules: (1) **cheap probe** — `dict.Probe` reads header-only metadata (name/entry-count) so `/api/dicts` and cache-location never build the full index; formats without a prober fall back to full Open (guarded by `HasProber` to stay off concurrent/auto-ingest paths). (2) **lazy source** — an ingested dict opens only its `.text.db`; the direct backend is opened solely on a resource-fallback miss (the embedded Store serves its auto-attached media.db first), so ingesting a dict now *lowers* its open cost instead of doubling it. (3) **background warm** — `Registry.Warm()` pre-opens all dicts bounded off the request path.
- `/api/search` streams **NDJSON** (`begin`/`hit`/`end`); `hit` carries a preference slot index so the client renders progressively and honors a user-defined dictionary order. The `dict` param accepts an ordered, enabled-only id list (panel drag/chevron order + enable toggles, persisted client-side). Dropdown stays alphabetical (name lookup) — distinct task from result ranking.

## D13 — Auto-index on first search — **ACCEPTED 2026-07-25 (user-directed)**, values renamed 2026-07-28
Indexing is no longer an explicit action. `AUTO_INDEX = on|off` (default **on**, opt-out). The values were `fuzzy|off` until D16 retired the word "fuzzy" for a search mode that no longer existed; `fuzzy` is still accepted as a synonym for `on`, so an existing config.toml keeps working. Since D24 what it builds is the ~2 MB find index only — never the heavier contains/full-text indexes, and it never strips or rebuilds what a user has chosen. The first time a dictionary is searched, the server builds its **headwords-level** index in the background (`entry.maybeAutoIndex`, `sync.Once`, guarded by `Caps.Fuzzy` so already-indexed/DSL/wudict dicts no-op) — cost follows usage, no first-run indexing storm (`Warm` still only *opens*). Full-text stays opt-in (large/expensive). Failures (read-only cache, no reader) are swallowed silently. UI fallout: panel drops "Fuzzy only"; "Enable fuzzy & full-text search" → **"full-text search"**, "Full + pack media" → **"FTS + pack media"**; a fuzzy search on a not-yet-built dict shows "preparing fuzzy index…" (ready on the next query) while full-text keeps its explicit "enable full-text search" link. Builds on D12 (cheap open makes the extra index free at query time).

## D8 — DSL in direct-mode — **RESOLVED by D1**
Transparent auto-ingest of text on first open; `.files.zip` resources stay lazy.

## D9 — Split-DB naming: `<slug>.text.db` + `<slug>.media.db` — **ACCEPTED 2026-07-24**
Slug = human-readable dictionary name (filesystem-safe). Self-describing for manual transfer/exchange; loader pairs by `dict_uuid`, not by name.

## D19 — The library is private; using it is a remembered choice — **ACCEPTED 2026-07-27 (user-directed)**
Reverses D17. The db dir is wudict's **library** — its own working area — and is **never a discovery root by default**. Four parts:
1. **Precise registration.** `store` registers the bundle main file `text.db` (exact name) and the loose `.text.db` suffix — never bare `.db`, which made an internal sidecar a public dictionary type: a `media.db` carries the same `user_version` and `meta` table as a text.db (for uuid pairing), so it opened as a phantom `wudict:slob` dictionary. Exact-name matching also avoids a `text.db` *suffix* swallowing an unrelated `context.db`.
2. **Hard guard + exclusion.** `DICT_DIR == DB_DIR` is a startup error (canonical paths, symlinks resolved); independently, `dict.ExcludeDir` makes discovery skip the library subtree wherever it sits — which also covers a db dir nested inside the dictionary folder, a case the equality check alone would miss.
3. **Consent (`USE_CACHED`, default off).** The library is listed only when the user opts in. This makes `reg.Count()==0` a *correct* first-run signal again with no special-casing: opted out + empty dictionary folder ⇒ empty registry ⇒ setup page appears. Dedup when opted in is by **source path** (a prepared dictionary is hidden only when its source is among the discovered files), so a dictionary whose source lives outside the current dictionary folder is still offered instead of silently vanishing.
4. **Enriched setup page — one page, one act** (harmonized 2026-07-27). The page presents two *sources* of one library (folders, and previously imported dictionaries), so it commits **once**: a single primary button at the foot, plus a way back. The former second button ("Use these dictionaries", sitting under the library list) was not merely redundant — it posted without the `path` params, **silently discarding any folders typed above it**. Folded into the one Save, whose label names the deed (folders → "Use this folder"/"Use these folders"; library alone → "Use these dictionaries") and which enables when *either* source is chosen. The escape hatch is **"Back to dictionaries"**, not "Cancel" (nothing is pending to abandon — no change applies until Save) and not "Close" (this is a page at its own URL, not a modal over content); and it is an `<a href="/">` styled as a button, not a `<button>` assigning `location.href`, so ⌘/middle-click, the context menu, the status bar and the "link" role all work. The keep-checkbox moved down beside the list it governs, and one line states the whole outcome: `✓ 55 dictionaries in 2 folders + 82 previously imported`. The "keep my N previously imported dictionaries" checkbox defaults to **CHECKED** when the library is non-empty (amended 2026-07-27): those dictionaries exist because the user prepared them, checking only makes otherwise-invisible ones reachable and is reversible, while leaving it off silently hides working dictionaries whose data sits on disk. It also mirrors the real setting once one exists, and now sends its state **both ways** (`useCached=0` turns the library off) — before, it was write-only-true, so clearing it could not undo an earlier yes. Note the box only governs prepared dictionaries this folder does *not* account for: one whose source is in the chosen folder keeps working with its indexes either way, via `PreparedFor`. Below the folder chooser it lists "Previously imported dictionaries" (name · format · entries · index/media badges) with **Use these dictionaries**, plus an "also keep my N previously imported dictionaries" checkbox on the folder flow — three outcomes: folder only, library only, both. Clicking a Use button *is* the "don't ask again": it persists `USE_CACHED=1` via `config.SaveKey`, and the setup page only ever appears while nothing is in use. Listing the library (`GET /api/library`) never enrolls it.

Rejected alternative (the elegant-but-lossy "Option A"): drop the library scan entirely and require users to copy prepared dictionaries into their dictionary folder. Refused because it forces **data duplication** — the app would refuse to use data it already has. Consent achieves the same separation of concerns without making the user pay twice for the same dictionary.

## D20 — Library layout: one folder per dictionary + `info.txt` receipt — **ACCEPTED 2026-07-27 (user-directed)**
The flat `<slug>-<hash8>.text.db` / `.media.db` naming is replaced by `<db dir>/<source file name>/{text.db, media.db, info.txt}` — e.g. `AHD5-2017/`. A dictionary is now **one folder**: copy, move, zip or hand it over as a unit, and drop it into a dictionary folder to use it elsewhere (discovery recognizes the bundle by its `text.db`). Details:
- **Naming** mirrors the source *file* (extension dropped; `.dsl.dz` drops both), spaces and case preserved, only path-illegal characters replaced. Collisions between same-named sources take a format tag — `AHD5-2017` and `AHD5-2017 (mdx)` — never a hash.
- **Allocation is a claim**: `ClaimDir` uses `os.Mkdir` (atomic) and immediately writes the `source` line, so two concurrent first-time ingests of same-named sources cannot take the same folder. Read paths call `LookupDir`, which never creates anything — browsing dictionaries can't litter the library. Ownership is always verified, so a same-named dictionary in another format can never be served from the wrong folder.
- **Registry layers, one source of truth**: folder names are the inventory (`ls` is the listing); each `text.db` meta is authoritative for content. `info.txt` is a *derived receipt*, regenerated after every ingest and media pack, carrying exactly one fact of its own — `source`, the claimed path. That claim is the **ownership record**, deliberately outranking meta's `source_path`, which is only what a format reader chose to report (real readers report relative or empty paths). No library-wide manifest: that would be a real second source of truth.
- **Staleness moves into the meta.** The content hash used to live in the file name; now `SourceChanged` compares recorded size/mtime, re-hashing the first 1 MiB only when those differ, and a changed source is re-indexed **in place**. Consequences: a touched-but-unchanged file no longer re-indexes, stale `-oldhash` files no longer accumulate, and "superseded ingest" disappears as an orphan category. `clean` now reports incomplete/unreadable folders, interrupted ingest temps, and pre-folder flat leftovers — never a healthy prepared dictionary, whatever became of its source.
- **Adoption, not migration** (user-directed, revised 2026-07-27). The first cut treated pre-folder flat files as disposable (`clean` fodder) — but a real library contained exactly those, so the library listed nothing and the user was asked to re-prepare data the app already had, i.e. the data duplication D19 exists to avoid. `store.AdoptLoose` now runs at server startup and **renames** `<slug>-<hash8>.text.db` (+ its `.media.db`) into `<name>/{text.db, media.db, info.txt}` — no re-indexing, nothing deleted, folder chosen so adopting and re-preparing converge on the same place. A loose file is left untouched only when that dictionary already has a prepared folder; that (a genuine duplicate) is the sole remaining "superseded" orphan class. Still no *schema* migration: the databases themselves are unchanged.

## D21 — DICT_DIR takes several folders — **ACCEPTED 2026-07-27 (user-directed)**
One dictionary root was a needless limit (external drives, shared folders, a second collection). Syntax per layer, chosen so each looks native where it is written: **repeatable flag** (`--dict-dir A --dict-dir B` — nothing to escape, identical on every platform), **`os.PathListSeparator` in the environment** (`:`, `;` on Windows — it is a path list, so it follows the `$PATH` convention; a comma would be novel and `:` on Windows collides with drive letters), **TOML array** `DICT_DIR = ["a", "b"]` with the scalar form still valid, so nothing breaks and no migration is needed. Semantics — the part that actually matters:
- **Order ranks nothing.** Result ranking already belongs to the panel (D12, drag/chevrons, persisted). Root order decides exactly one thing: which folder wins a tie.
- **Two levels of dedup.** Folders: `dict.DedupeDirs` collapses one folder listed twice however it is spelled — a repeat, a trailing separator, a symlink, a case variant on a case-insensitive filesystem — using `os.SameFile` where both paths exist (string comparison sees none of those) and canonical strings for paths that do not (an unmounted drive must still be kept, and still deduped). First spelling and order win. Applied at `NewRegistry`/`SetDirs`, so every source funnels through it, and again when the setup page saves, so duplicates never reach `config.toml`. Nested folders are NOT duplicates: they are different directories whose overlap is reported per root. Dictionaries: dedup by canonical path (`EvalSymlinks`). Overlapping roots are normal once several are allowed (`~/Dicts` plus `~/Dicts/Spanish`, a symlinked shortcut); without it the same dictionary gets two registry ids — two panel rows and doubled hits in every all-dictionaries search. `DiscoverAll` reports per root both what it contributed (`New`) and what it holds (`Total`), so an overlapped folder reads "1 dictionary, already listed above" instead of the lie "no dictionaries found".
- **A missing folder is a warning, never fatal** — an unmounted drive must not take the other folders down. Reported per folder at startup and per row on the setup page.
- **The `DICT_DIR == DB_DIR` guard applies to every folder**; nesting is still covered by `dict.ExcludeDir`. The **library stays single** (D19/D20 depend on one place for prepared dictionaries) — the asymmetry is deliberate: many sources, one library.
- Wherever the CLI takes a folder (`list`, `ingest`, `searchall`) it now takes a list too, in either spelling.
Fixed in passing: `filepath.WalkDir` lstats its root, so a **symlinked dictionary folder silently yielded nothing**; `Discover` now resolves the root it is given (links *inside* the tree are still not followed, which keeps cycles and surprise duplicates out).

## D22 — Folders are visible and editable from the app — **ACCEPTED 2026-07-27 (user-directed)**
Where dictionaries are read from, where prepared ones live, and which `config.toml` is in effect were visible only in the startup block on stderr — a terminal the user may never see, since the app opens a browser for them. The setup page knew all of it but was reachable only while the registry was empty. Fixed with three pieces, no new mental model:
1. **`/setup` is permanent**, pre-filled with the folders in use and offering Cancel once dictionaries are being served. It is the folder *editor*, not just the first-run chooser.
2. **A settings disclosure in the panel** — moved to the top (2026-07-27): one line directly under the master switch, above the first card, showing a cog and the counts (`3 folders · 112 dictionaries`) with **no visible label**, per show-don't-tell; the name survives as `title`/`aria-label` for tooltips and screen readers. At the foot of a 55-card list it was undiscoverable; at the top it costs one line and doubles as the panel's scope. The cog is an **inline SVG**, not ⚙️: emoji renders as a colour blob on macOS and flat on Windows, sits on its own baseline, and cannot inherit `currentColor`. Originally described as a foot-of-panel disclosure (`GET /api/config`): each dictionary folder with its own count/status, the library with prepared/in-use counts, the config file — all click-to-copy, with **Edit folders…** linking to `/setup`.
3. **Value origins.** `config.Load` records which layer set each key (`flag`/`env`/`file`/`default`). When a flag or environment variable outranks the file, both the panel and the editor say so: *"set by the --dict-dir flag — it overrides the config file"*. Without this the UI would happily save a folder list that silently does nothing next launch; a settings screen that lies is worse than none.
**Rescan moved out of the panel header into that section** (user-directed): it re-walks every folder and re-opens every dictionary, far too expensive to sit beside the close button as a curiosity click.
**Reveal in the file manager** uses each platform's own established wording — *Reveal in Finder* (macOS), *Show in File Explorer* (Windows), *Open Containing Folder* (Linux) — with the matching command (`open -R`, `explorer /select,`, `xdg-open` on the containing folder, since selection is not portable there). Two guards, both deliberate: the path must be one the app already displays (a dictionary folder or below, the library or below, or the config file — never an arbitrary path handed to the shell), and the request must come from **loopback**, since revealing opens a window on the machine running the server, not the one browsing it.
Deliberately NOT built: an editor for launch-time settings (port, IP, speex backend). Those cannot be applied live, so offering edit fields would invent a "restart required" mode this app does not have.

## D23 — A second launch hands over instead of failing — **ACCEPTED 2026-07-27 (user-directed)**
Launching wudict while it is already running now opens the **running** instance in the browser and exits 0, behind a deliberately loud ASCII banner saying the new launch did nothing. This is the desktop single-instance activation pattern (a second double-click activates the running app; Windows apps forward the command line and focus the window) translated for an app whose window IS a browser tab.
- **Identity first.** A port can be held by anything, so we `GET /api/config` with a 700ms timeout and require the `Server: wudict/<version>` header (added for this purpose, on every response). Anything else — a foreign server, no answer, a timeout — keeps the original "port in use" error and opens nothing. Sending a user's browser to an unknown local service on the strength of a port number would be worse than an error.
- **Loud, because the launch is a lie otherwise.** The banner states that the options just passed were NOT applied, prints what the running instance is actually serving, and — when the requested folders differ from the running ones — says so explicitly. Silently opening an old instance is exactly how someone spends ten minutes wondering why their new `--dict-dir` did nothing.
- **Bind before working.** The listener is now claimed *before* adopting library folders, scanning dictionaries or auto-preparing indexes. Binding last meant a duplicate launch printed a full startup summary and built a search index before discovering it had nothing to do.
- `--no-browser` is honoured (banner only), and the handoff exits **0**: the user's intent ("open wudict") was satisfied. Scripts that relied on a non-zero exit for "could not start" see 0 in this one case.
**Rejected: an HTTP `/exit` endpoint to kill the running instance** (user's option B). Any web page could fire `GET http://127.0.0.1:6888/exit` with an `<img>` tag — no CORS, no user action — so a random site could kill the app; it would also discard work in flight (a long ingest), might not be the user's instance to kill on a shared machine, and races `TIME_WAIT` on rebind. If takeover is ever wanted, the safe mechanism is a PID lockfile plus `SIGTERM` behind an explicit `--replace` flag: a signal requires the same OS user and cannot be sent by a web page.

## D24 — Cheap by default, enriched by one click — **ACCEPTED 2026-07-28 (user-directed)**
A prepared dictionary could take several times the disk of the file it came from. Measured on a 40k-entry dictionary (45.6 MB source, 5.1 MB gzipped): the "headwords only" database was **72.4 MB**, of which **69.1 MB (95%) was article text** — every search index together came to 2 MB. So the disk problem was never the indexes.
1. **Article bodies are DEFLATE-compressed per row** (measured 3.8x smaller; the test corpus is random word soup and therefore pessimistic — real dictionary HTML compresses further). Per row rather than in shared blocks so a row stays independently readable without a block cache; skipped for bodies under 120 bytes and whenever it fails to win. Discrimination is a one-byte NUL sentinel — article text never starts with NUL — so **mixed rows are legal**: databases written before this keep opening, with no migration and no schema-version bump. `NO_COMPRESS=1` / `--no-compress` restores verbatim storage for those with disk to spare.
2. **The trigram ("contains") index is opt-in per dictionary.** It is only 3% of yesterday's database, but ~100% of a compressed, bodyless index — it costs as much as everything else put together, and serves a mode most people never use. `store.Plan{FullText, Contains}` replaces the single Level; the default plan builds neither trigram nor anything else optional.
3. **Finding a headword has no switch.** exact and prefix (accent-insensitive) work on every backend and cost ~2 MB, so they are not features to enable — which is why their badges were removed: a badge lit on every row for every dictionary is decoration. The panel now shows the three things that cost real disk (**contains · full-text · media**) as switches with their measured sizes, one click to add, one to remove.
4. **Stripping is offered only while the source file exists.** That is what makes it reversible — and it removes the need for confirmation prompts entirely: a dictionary whose source is gone carries the only copy of its own text, so its switches are locked with an explanation rather than made dangerous. Rule: *the source is the safety net; without it, nothing can be stripped.*
**Formats that prepare themselves are not an exception** (fixed 2026-07-28): DSL and BGL have no native index, so their text.db must exist and must hold the article text — but *indexing that text for full-text search* was still automatic for them, the last place where a heavy index was imposed rather than chosen. They now prepare with the same cheap plan as everyone else (first open of the measured dictionary: 29.5 MB → **17.2 MB**), and full-text is a switch for them like any other format.
Net on the measured dictionary: default preparation went from **84.0 MB (1.84x the source) to 29.5 MB (0.65x)** — 17.2 MB for a format that prepares itself, with contains and full-text no longer paid for by people who never use them. Auto-indexing (D13) now builds only the ~2 MB find index and never strips or rebuilds what a user has chosen.

## D25 — Background work must not take the machine — **ACCEPTED 2026-07-28 (user-directed)**
Measured (docs/PERF.md): a single "all dictionaries" search over a 100-dictionary library started **one ingest goroutine per dictionary** — no bound anywhere — producing 18 GB RSS and 1000 %+ CPU. Four fixes:
- **F1 Bounded indexing.** All background preparation flows through one limiter, `INDEX_WORKERS`, **default 1**: preparing a dictionary saturates a core and holds ~300–500 B per headword, and a background convenience must never take the machine from the person using it. `"auto"`/`0` = every core; the value is clamped to `[1, NumCPU]`. Work the user explicitly asked for gets a separate single slot, so a click never queues behind a long background job (worst case INDEX_WORKERS+1). Measured: 424 % → 154 % CPU.
- **F2 Release what is superseded.** After a dictionary is prepared, its direct backend — the thing holding the per-headword map — is closed after a 10 s grace (in-flight reads finish) and the pages handed back with `FreeOSMemory`. `Registry.Warm` no longer opens *unprepared* dictionaries at all: opening one builds that map, and doing it for a whole library was several GB for dictionaries nobody had searched. Measured: 474 MB → 172 MB resident after the storm.
- **F3 One copy, not two.** Preparing no longer calls `e.open()` for a display name while `OpenReader` parses the same file again; the name comes from a header-only probe. The largest object in the process is no longer duplicated for the duration of an ingest.
- **F4 Optional ceiling.** `MEMORY_LIMIT` (e.g. `"4GB"`) sets Go's soft heap limit; unset means none. With F1 in place the peak is close to the live set anyway, so this is a safety net rather than a necessity.
- **S2 Bounded preview memory** (user-directed, same day). An all-dictionaries search still materialised every *unprepared* dictionary's headword map (~6 GB transient). `PREVIEW_MEMORY` (default **1 GB**) now caps what unprepared dictionaries may hold open, weighed at `EntryCount × 350 B`; a janitor evicts least-recently-used backends every 20 s, **never** touching one used in the last 45 s and **never** running on the request path — a search fanning out over a hundred dictionaries would otherwise evict what it is about to reuse, and each reopen costs 0.2–1.1 s. Prepared dictionaries weigh zero and are never evicted (nothing to reclaim); the predicate is "answers from a prepared database", which also catches DSL/BGL embedding a `*store.Store` directly. `entry.open` moved from `sync.Once` to double-checked locking so an evicted backend can be reopened. Chosen over S1 (skipping unprepared dictionaries in search) because it keeps results complete. Extended the same day to `upgraded.src` — the source handle a prepared dictionary opens when a resource misses `media.db`. It holds the same per-headword cost, so it is weighed, timestamped on each resource fetch and released by the same janitor; the sweep ranks both kinds on one LRU (`reclaimable{used, bytes, free}`). Releasing it is invisible: text still comes from SQLite and the next resource request reopens the handle.

## D26 — MDict sub-entries: inlined, not searched — **ACCEPTED 2026-07-29 (user-directed)**
Repacked MDict dictionaries store an article's expandable sections as ordinary headwords with an `@` prefix — LDOCE6 No-Voice ships **95,162 of them against 65,382 real words**, so 59 % of its "entries" are `@collocations_woman`, `@examples_woman`, `@entrymenu_woman`. Two consequences, handled separately:
1. **A link to one is not navigation.** `entry://@examples_woman` used to go through `lookupWord`, replacing the article being read with a fragment of itself (and `lookupWord`'s trailing-digit strip turned `@wordfamilies_0654` into `@wordfamilies_`). Such a link now **inlines** the section next to the link that asked for it, with a close control; a second click removes it. Nothing touches the search box, the URL or history — this is expansion *within* an article, not a move between articles. Script-bearing articles render in the sandboxed iframe, which is same-origin, so `frame.js` fetches the fragment itself (`/api/search?mode=exact`) and inserts it where the article's own stylesheet and `toggle()` are already loaded — the fragment's own ►/▼ accordions work with no extra plumbing. Shadow-DOM articles get the same handler in `index.html`. The fragment's duplicate `<link rel=stylesheet>` is stripped on insert.
2. **They are hidden from browsing.** `@`-prefixed headwords are excluded from prefix, contains, full-text, the accent-fold fallback and the headword listing — but remain reachable by **exact** lookup, which is exactly what the inlining needs. A bare `"@"` (the symbol as a headword) is not hidden. The filter lives in the SQL, so limits apply to visible rows and **existing prepared databases behave correctly with no re-index**; new ingests additionally record `sub_entries` and report `entry_count` as words only (an already-prepared dictionary keeps its old inflated count until re-indexed — cosmetic, self-healing).
Measured before/after on the real dictionary: a prefix search for "collocations" returned `@collocations_000, @collocations_1, @collocations_12…` via the fold fallback; it now returns nothing.

## D14 — Resource URLs: root-only, root-absolute `/res/…` — **ACCEPTED 2026-07-25 (user-directed)**
**Reverses** the earlier relative-URL convention. wudict is served at the site root; `RewriteEntryHTML`, client `resURL`, and the srcdoc bridge all emit **root-absolute** `/res/{dictID}/…`. Reason: articles render in three contexts (main page, Shadow-DOM, **srcdoc iframe**) and a *relative* ref resolves against each context's differing base URL — third-party dictionary scripts inside srcdoc re-resolve against the wrong base, producing the `res/{d}/res/{d}/…` doubling 404 (hit twice: OED `OED4.js`, AHD5 `wavs/*`). Absolute `/res/` is context-insensitive: same origin URL everywhere, trivial `startsWith("/res/")` idempotency, one rewriter. Trade-off: implicit reverse-proxy **subpath** mounting is dropped; if ever required it returns deliberately via injected `<base href>` + a server-known prefix, not implicit relative URLs. Related: resource Content-Type is now taken from an authoritative `webMIME` extension map at serve time (Go's `mime.TypeByExtension` returns `text/plain` for `.css`/`.js` on some platforms → browsers reject stylesheets/scripts under strict MIME checking).

## D29 — FTS5 is mandatory, so the tag-less build must be the safe one — **ACCEPTED 2026-08-02 (user-directed)**

## D30 — Startup readiness is an explicit phase, and `/api/dicts` streams — **ACCEPTED 2026-08-02 (user-reported)**
On a slow machine, or a fast one with ~100 dictionaries, the first launch showed `Loading dictionaries…`, then **`⚠ All dictionaries are disabled — enable some in the ☰ panel`**, then — minutes later — normal search. The warning was false and actively misleading: it sent the user to a panel that would list their dictionaries perfectly intact.

Three defects compounded. (1) `doSearch` used one emptiness test, `!enabledOrderedIds().length`, for two unrelated conditions — "the user disabled everything" and "the list has not arrived". (2) The search form was live from first paint (`autofocus` + a submit handler bound at parse time) while `loadDicts()` was still in flight, so an eager query reached that branch with `dicts === []`. (3) `/api/dicts` was all-or-nothing — fan out, `wg.Wait()`, one array — so the vulnerable window lasted as long as the **sum** of every dictionary's metadata resolution, not the slowest one. The warning then *persisted*, because `loadDicts`'s cleanup was `finally{if(!lastQuery)setStatus("")}` and the premature search had already set `lastQuery`.

**`/api/dicts` now streams NDJSON** (`begin`+`total` → one `dict` per row in completion order → `end`), which is what D12 already did for `/api/search` and for the same stated reason: time-to-first-byte must be one open, never the sum of all of them. `total` comes from the registry with no opens at all, so the client knows how many are coming before any of them resolve.

**The client has a named readiness phase** — `boot` (0 rows: search controls `disabled` **in the markup**, so there is no window between first paint and script execution; indeterminate spinner; rotating Cook Ding 庖丁解牛 waiting messages) → `partial` (≥1 row: fully interactive, per the requirement that search unlocks on the **first** available dictionary) → `ready` → `failed` (stream error, or no `begin` within 20 s: interactive anyway, with a retry — a hung server must never leave the form permanently inert).

**The gate is now phase-derived, not count-derived.** "All disabled" requires a *settled, non-empty* list: mid-stream the rows that happen to have arrived may all be disabled while dozens still coming are not, so before `ready` the same branch reads as loading and re-runs itself when the stream completes. `handleIndex` serves `/setup` when the registry is empty, so on this page an empty list can only ever mean "not ready yet". Supporting fixes: `setStatus` takes an owner token so a long-running writer retracts only its own message; the panel header says "Still loading…" rather than "No dictionaries"; `renderPanel` repaints are debounced (it rebuilds its whole list, and would otherwise run once per arriving row).

**Deliberately indeterminate, with a factual counter.** Per-dictionary cost spans orders of magnitude (cold MDX ~180 ms, cold SLOB ~1 s), so a progress *bar* would be guessing; `N of M ready` cannot be. The counter removes the uncertainty that causes the panic, the messages handle the mood, and none of them claims imminence.

**Standing rule:** never let one predicate carry two meanings. If a test is reachable in a state its message does not describe, the state — not the message — is what is missing.

## D31 — Bulk full-text is an offer in the drawer, not a call to action in the header — **ACCEPTED 2026-08-02 (user-reported)**
The panel header carried a **`⚡ index all`** button. Two independent faults, one psychological and one factual.

**Factual: the name was untrue.** Every dictionary is indexed by headword automatically on preparation (`AUTO_INDEX`, D20/D24) — "index all" therefore described work already done, and its real semantics were *"build the full-text index inside article bodies for every dictionary"*, the one index that costs gigabytes of disk and a long single-file CPU pass. A lightning bolt plus "all" reads as *complete your setup* — so an optional extra was dressed as a repair for a product that is already fully functional. Curiosity alone guarantees clicks, and the cost is asymmetric: the click is instant and free, the consequence is minutes-to-hours of CPU and unbounded disk. **Prominence must track value to the user, not cost to the machine.**

(2) **Site it by value**: it moves into the "Folders & configuration" drawer as quiet muted text beside "Rescan folders" — deliberate, findable, not encountered. ## D32 — `wudict.toml`, created only in `~/.wudict`, portable only when declared — **ACCEPTED 2026-08-02 (user-directed)**
The config file was `config.toml`, searched in `<exe-dir>` → `~/.wudict` → `/etc/wudict` → `./`, and generated **next to the executable if that directory was writable**, falling back to `~/.wudict`.

**The writability probe was answering a question it cannot answer.** It was read as *"this directory is ours"*. It is not: `go install` lands in `~/go/bin` and Homebrew (Apple Silicon) in `/opt/homebrew/bin` — both user-writable, both **shared bin directories**, and both the most likely install paths. The exe-adjacent pattern is sound — but only under a precondition it never checked: *the application owns its directory*. Guessing harder (matching `/opt`, `/usr`, …) was considered and rejected: a denylist is incomplete by construction and would still have missed `~/go/bin`, `~/.local/bin` and Scoop.

**The rule is inverted, and now complete.** Nothing is inferred: wudict writes exactly one path, `~/.wudict/wudict.toml`, beside the library it already owns. **Portable mode is declared by the user** placing a `wudict.toml` next to the binary — it then wins the search and receives the saves, and the creation path is never reached. ## D33 — Enabled set and order live on the server (`state.json`), not in localStorage — **ACCEPTED 2026-08-02 (user-directed)**
Which dictionaries are searched, and in what order, were kept in `localStorage` under `wudict_order` / `wudict_disabled`.

**localStorage is keyed by origin**, and the origin includes the port. Changing `SERVER_PORT`, reaching the same server as `127.0.0.1` instead of `localhost`, opening it from a phone on the LAN, or clearing site data each hands the user a blank slate. Curating a hundred dictionaries and losing it to a port change is not a preference that survived; it is a preference that was never stored. The **server owns the dictionaries** — it is the only party that can answer "which of them do I search" consistently for every client, and the only one that can *act* on the answer.

Acting on it is the second reason, and the one that made this a bug rather than a preference. `Registry.Warm()` pre-opens every prepared dictionary; it had no way to know any of them were disabled, so **turning a dictionary off bought the user nothing** — the SQLite handle was opened anyway. A switch whose only effect is on the client's request parameters is a decoration. `Warm` now skips disabled entries, which is why `Prefs` is a **constructor option** (`WithPrefs`) and not a setter: `NewRegistry` starts the warm-up, and a warm-up told what to skip after the fact has already spent the memory.

**The line is "does this describe the collection, or the browser looking at it?"** Theme, wide mode and the last dictionary picked in the dropdown stay in `localStorage` — they *should* differ between a laptop and a phone. The enabled set and the order move to one collection-level `state.json`, placed **beside the `wudict.toml` in effect** rather than at a hardcoded path, so a portable install (D32) carries state and config together and `--config` re-points both. It is deliberately not inside the library folders: D20 defines those as individually transferable units, and "which dictionaries are enabled" is a fact about the set, not about any member.

**Identity is repaired, not assumed.** Ids are `sha256(path)[:12]`, so renaming a folder changes every id at once. Records store `{id, path, name}` and are re-attached down a ladder of decreasing strength — id → absolute path → *unique* file name — where each rung may only claim an entry no stronger rung took, and the file-name rung requires uniqueness on **both** sides (without that guard every library entry, all of them named `text.db`, would swap identities with each other). The repair is written back, so a later save cannot resurrect the stale id as a duplicate. `name` is stored for a readable file and never used to match: it is a display string, and matching on it would be fake precision.

**Nothing is deleted on the client's word.** The client can only speak for dictionaries it can see, so a save retains records it did not mention, appended in their stored order — an unmounted drive must not cost the user the settings for everything on it. Symmetrically, the client refuses to save at all if its initial read failed: "nothing is disabled, no order" would be our ignorance overwriting their configuration. A first run reports `exists: false`, which is the client's one-time cue to adopt (and then erase) an older build's `localStorage` rather than starting the user over.

Unauthenticated LAN writes are not a new exposure: `/api/setup` already lets any client on the interface rewrite `DICT_DIR` in the config file, and this is strictly less powerful.

**Standing rule:** state belongs wherever the thing it describes lives. Per-device *look* is the browser's; per-collection *meaning* is the server's — and a switch the server cannot see is a switch that does nothing.

## D34 — `Fold` is versioned; a stale index is marked, not disabled — **ACCEPTED 2026-08-02**
`dict.Fold` is called in two places with different lifetimes: at query time on what the user typed, and at ingest time on every headword, where the result is **persisted**. Nothing recorded which version of `Fold` produced a stored index, so **any future edit to `Fold` would silently desynchronise every prepared dictionary** — add `ß`→`ss` and a query folds to `strasse` while an index built last month still holds `straße`. No error, no warning, and invisible to every test, because tests ingest fresh data with the same `Fold` they query with. The failure mode is a search that quietly stops finding words it used to find. This was a live defect independent of any morphology or normalization work (O2/O3 in `docs/OPEN.md`).

**The audit corrected the scope.** `Fold`'s output reaches disk in exactly **one** place: `ingest.go:198`, the trigram index behind *contains*. Three things that looked folded are not — `entry_fts` stores raw `w`/`txt` and folds with SQLite's own `unicode61 remove_diacritics 2` tokenizer; `idx_entry_w` is a raw `COLLATE NOCASE` index; and the direct backends rebuild their fold indexes on every open. So a `Fold` change invalidates one index, on dictionaries that opted into one mode — not the whole library. Knowing that is what made the response proportionate.

**Absent means 1, not 0.** Every database ever written carries no `fold_version` key and was, necessarily, built by the folding in force when the key was introduced. Defaulting a missing key to 0 would have declared every existing library stale on the day this shipped — a feature whose first act is a false alarm teaches users to ignore it.

**A stale index is marked, not disabled, and never auto-rebuilt.** Both of the obvious stronger responses are wrong. *Disabling contains* overreacts: a folding change alters one narrow class of characters, so a stale index is still exactly correct for every dictionary containing none of them — withdrawing the mode from a Spanish dictionary because Japanese dakuten handling changed is absurd, and for a source-less dictionary it would be an unrepairable loss where a partly-correct index was available. *Auto-rebuilding* is worse: a version bump makes every contains-enabled dictionary stale at once, which is precisely the first-run indexing storm `docs/PERF.md` M2 warns about. The proportionate response to "possibly inaccurate for some characters" is to say so and offer the repair.

**The repair reuses the switch that is already there.** A stale chip stays *on*, gains a dotted border and a `⟳`, and its click sends `contains=1` — the feature it already has — which `setFeatures` reads as "rebuild this". No new endpoint, no new confirmation, no third chip state to explain: asking for something you already have is an unambiguous request to make it true again, and it is the same atomic temp+rename rebuild as any other index change.

No logging was added in `store`: it is a library that returns diagnostics rather than printing them (D13). The `logx.V` line lives in `setFeatures`, where it reports the *action*, not the state.

**Standing rule:** any function whose output is written to disk owns a version constant, bumped in the same commit as the behaviour. The alternative is not "we will remember" — it is a silent, undetectable divergence between what was indexed and what is queried.

## D35 — Expand-all is a page-lifetime toggle, remembered nowhere — **ACCEPTED 2026-08-02 (user-directed)**
Results render as one `<details class="dict">` per dictionary, and exactly one — the highest-preference dictionary with hits — opens automatically. Comparing a word across a whole collection therefore meant opening sections by hand. A `⊞`/`⊟` button now opens and closes all of them.

The interesting decision was where the state lives, and the answer is **nowhere**.

**Not on the server.** D33's rule ends *"a switch the server cannot see is a switch that does nothing"* — that clause was written about disabling a dictionary, which was a decoration until `Warm()` could act on it. Expand-all is the mirror case: it has **no server-side consequence at all**. The same NDJSON is streamed, `perDict` is unchanged, nothing is opened, indexed or skipped differently. The switch does its entire job in the browser, so putting it in `state.json` would have bought a `UIPrefs` struct, a schema change, merge semantics and tests for a value the server would never read.

**Not in localStorage either**, which is where `wudict_theme` and `wudict_wide` live. The sharper discriminator behind D33's look/meaning heuristic is **how expensive the state is to recreate**: a curated order and enabled set across a hundred dictionaries is minutes of work, so losing it to a port change (localStorage is origin-scoped) is a real injury. Expand-all is one click. Persisting it only buys the failure mode where a user enables it once on a wide screen and meets an inexplicably different app on a laptop weeks later, with nothing on screen to explain why.

**Page lifetime is the sweet spot, and it is self-clearing.** One `let expandAll=false`. Reload returns to the default; there is no tomorrow in which it surprises anyone. It survives searches *within* the page, which is the point — the people who want this are comparing term after term, and a click-scoped action would charge them a click per query, penalising exactly the workflow it exists for.

**A toggle, not a one-shot action, because the two directions are symmetric.** VS Code's explorer offers *Collapse All* with no inverse, and that works only because the directions are asymmetric there: collapsing is bounded, expanding a file tree is unbounded. Here both directions are bounded and equal — N dictionaries, all open or all shut — and expanding by one click while collapsing costs one click per dictionary would be a one-way door. Symmetric operations want a toggle.

The default is untouched: auto-open the top-preference dictionary, which gets the user reading with no scrolling and is right for almost every search.

Two implementation notes. The auto-open block is skipped entirely while expand-all is on, and `openedIdx` stays `null` — otherwise a lower-index dictionary arriving late would close a section being read. And `content-visibility:auto` on open sections hands back the cost: articles are built eagerly either way (`renderSlot` appends them all; the accordion only hides them), so opening pays layout and paint, which the browser can now skip for anything not scrolled to.

**Standing rule:** before choosing where a setting lives, ask what breaks if it is lost. State that is expensive to recreate earns durable storage; state that is one click away earns none, and storing it anyway only buys a way to confuse the user later.

## D36 — One `.col` geometry for the toolbar and the content — **ACCEPTED 2026-08-02**
Adding the expand-all button (D35) made the toolbar visibly wider than the result cards. The button was not the cause; it was the first thing to touch a boundary that had been in the wrong place all along.

**The measurement.** `.container` was `width:92%; max-width:800px; padding:0 var(--sp-2) var(--sp-5)` under a global `box-sizing:border-box`, so the cards sit `--sp-2` (`.618em` — φ⁻¹, from the project's own golden-ratio spacing ladder) inside their 800px box. `.bar form` was `max-width:800px; margin:0 auto` with **no gutter of its own**. Below the cap, `.bar`'s horizontal padding stood in for one and the two happened to line up; above it, nothing did, and the bar ran ~9.9px wider on each side. The misalignment therefore existed at every viewport over 600px, in a varying amount — invisible only because `justify-content:center` kept a content-sized cluster of controls away from its own edge. Five buttons filled the row, the cluster reached the boundary, and the boundary was wrong.

**The naive fix was wrong in the other direction.** Simply adding `padding:0 var(--sp-2)` to the form corrects widths above the cap and *breaks* the ≤600px case, where the form would then be inset twice — once by `.bar`, once by itself — while the cards are inset once. Two elements described by two rules that have to agree at three breakpoints (`auto` / `92%` / `800px`), in two modes (normal / wide), is six chances to drift and no mechanism preventing it.

**So the geometry is named once and worn by both.** A `.col` class carries width, cap, centring and gutter; `<main class="col container">` and `<form id="frm" class="col">` wear it, `.container` keeps only its bottom padding, and `.bar form` keeps only the flex arrangement of what is inside it. `.bar` drops its horizontal padding — it is full-bleed anyway, and the gutter now belongs to the column. The wide-mode override and the ≤600px `width:auto` are each stated once, for both. The two boxes are no longer *equal*; they are the *same*, which is the only version of this that stays true.

**Ends anchored, not centred.** `.bar form .tools{margin-left:auto}` on the first view toggle splits the row at its real semantic seam — query controls (`input`, mode, dictionary, 🔍) against view controls (`◐ ⇔ ⊞ ☰`) — so free space is absorbed in the middle and both ends stay pinned to the column. Content no longer determines width; width determines layout, and a sixth button costs nothing. It is inert at 800px, where the controls already fill the row, and does its work in wide mode.

The 🔍 button was considered for removal (Enter submits, the input is `autofocus`, `/` focuses it, and mobile keyboards render a Search key for `type=search` in a form) and **kept** by decision: it is the one control that names the app's primary verb.

**Standing rule:** when two elements must line up, do not give them matching values — give them the same rule. Matching values are a coincidence maintained by hand, and every breakpoint doubles the number of hands.

## D37 — Sticky section headers, sized by `[open]` — **ACCEPTED 2026-08-02**
Scrolling a long article lost all trace of which dictionary it came from: the `<summary>` naming it had scrolled off, and the top bar auto-hides on scroll-down, so nothing on screen answered the question.

**The header was already there; it just did not stay.** The alternatives considered all proposed *adding* something — a breadcrumb in the bar, a transient pill that fades in while scrolling, a per-dictionary colour. Each was rejected on its own terms. The breadcrumb is disqualified by our own scroll handler (`cur>80&&cur>prevScroll` hides the bar exactly while you are reading, so the information would be absent precisely when wanted). The fading pill is the worst option available: every appearance is peripheral motion, the one stimulus the visual system is built to interrupt on, spent to tell the reader something they only sometimes want. Per-dictionary hues have the best theory — colour resolves pre-attentively, before foveation — and fail in practice at 105 dictionaries, where hues stop identifying anything, and against a deliberately calm one-accent palette they would cost more composure than they buy recognition. Colour is a good redundant cue and a bad primary one.

So: `position:sticky` on the existing summary. Nothing new to learn, nothing new to render, and a second benefit that turns out to matter more than the first — **the collapse control is now permanently within reach**, so a dictionary can be closed from anywhere inside it rather than by scrolling back to find its top. With expand-all (D35) that becomes the primary way of navigating results.

**`overflow:hidden` → `overflow:clip` is what makes it work at all.** `hidden` establishes a scroll container, and a sticky element sticks to its nearest scrollport — which would have been a box that never scrolls, so the header would simply not have moved. `clip` clips to the same border-radius and creates no scrollport. One word, and the difference between working and mysteriously not.

**Two jobs, two sizes, and `[open]` already distinguishes them.** A *closed* header is a row in a list scanned across a hundred dictionaries: it wants presence. An *open* one is a context label consulted occasionally while reading: it wants to disappear. That maps exactly onto a state CSS already has, so the compact size (~39px → ~25px) needs **no sentinel element, no IntersectionObserver and no scroll handler** — and, better than any of those, the resize is triggered by a click the user just made instead of arriving as a surprise in their peripheral vision. Detecting *stuck* would have been more precise and worse: it would animate on scroll, which is the motion this design is trying not to spend. Horizontal padding moved from `em` to `rem` so the type change moves the header's height and never the name's left edge.

**`--stick` is measured, not guessed.** The bar wraps to two rows on narrow screens, so a hard-coded offset would either hide headers under it or float them below a gap; a `ResizeObserver` publishes the real height (a `resize` listener would miss the reflow caused by the dictionary `<select>` growing as names load). `body.barhidden` drops it to `0` when the bar slides away, on the bar's own `.28s`, so the two read as one piece of chrome moving rather than two things reacting to each other.

**Standing rule:** when the interface has to answer "where am I", look first for the element that already says so and ask why it left. Adding an indicator is the second-best answer to a question a persisting label answers for free.

## D38 — Section scroll corrections: two rules, both conditional — **ACCEPTED 2026-08-02**
Should clicking an accordion section scroll it into view? **Not unconditionally**, and the two directions fail differently enough that they need different rules.

**Scrolling every opened section to the top is wrong here, for a reason specific to this app.** The top-preference dictionary is already open when results arrive, so clicking a *second* summary is nearly always an act of **comparison** — "and what does Chambers say?". Moving the page to put the new section at the top takes the one being read off screen and turns comparison into replacement. Two further objections: expanding a section pushes only what is *below* it, so the summary the user clicked never moves and their visual anchor is already perfect; and under expand-all (D35) the behaviour would fire once per dictionary.

**Open needs help only when it revealed nothing.** Click a summary sitting near the bottom of the viewport and the content unfolds entirely below the fold — the user asked to see something and saw nothing. So: if the section's top is below half the viewport, bring it up to the bar; otherwise do nothing. Silence in the common case.

**Close needs help not to vanish, and that need is one D37 created.** Before sticky headers, collapsing a section meant scrolling back to its top first, so closing could never disorient. Now it can be collapsed from 3000px inside itself, after which the document shrinks, the browser clamps the scroll position, and the user lands somewhere arbitrary — often the end of the page. Returning them to the row they just closed is not taking control away; it is honouring the position they still implicitly occupy. Firefox and Chrome's scroll anchoring hides some of this. Safari does not.

That asymmetry is not the usual smell of a wrong rule, because the two cases have different causes: open occasionally fails to *reveal*, close fails to *stay*.

**Three implementation traps, all avoided.** (1) The `toggle` event fires for programmatic opens too — `renderSlot` sets `det.open = expandAll` on every arriving row, so a `toggle` handler would make the page jump while results stream in. Listening for a **click on the summary** is inherently user-initiated (and sidesteps `toggle` not bubbling). (2) The new height must be laid out before it is measured, so the decision happens in a `requestAnimationFrame` after the browser has applied the toggle. (3) Both corrections scroll **up**, which brings the auto-hidden bar back — so they must aim at the bar's real height and not at `--stick`, which is momentarily `0` while the bar is away. `--barh` and `--stick` were split for exactly this, and `scroll-margin-top:var(--barh)` on the section lets `scrollIntoView` land correctly with no arithmetic and no re-derivation when the bar rewraps.

`prefers-reduced-motion` downgrades both to an instant jump — mandatory for anything that moves the viewport without being asked.

**Standing rule:** never move the viewport to express a state change. Move it only when the alternative is the user losing their place — and then by the smallest amount that fixes it.

## D39 — `bword://#fragment` is an in-article jump, not a lookup — **ACCEPTED 2026-08-03**
Reported against `eng-eng-stanford-ep.mdx`: links like `bword://#HistAI` did nothing. Dogfooded with `wudict lookup` — the Stanford Encyclopedia articles carry their own tables of contents as `<a href="bword://#HistAI">` pointing at an `id="HistAI"` **in the same article**, and the "Artificial Intelligence" entry alone has sixteen of them.

`wordFromHref` strips the fragment and returns `""`, and both click handlers then did `preventDefault()` and stopped — the code even said so: *"bword://#frag carries no word: swallow the click"*. Swallowing was right as far as it went (searching for an empty word would be worse) but it treated a two-part address as if only the first part existed. **The fragment is the whole message.** A lookup-scheme link with no word is not a broken cross-reference; it is the article navigating itself.

Both renderers needed it, and they need it differently. Shadow-DOM articles resolve the target through `a.getRootNode()` — a `ShadowRoot`, which has `getElementById` via `DocumentFragment` — and scroll directly. **Iframe articles cannot scroll themselves at all**: `renderFrame` sizes the iframe to its content, so its own document has nothing to scroll and `scrollIntoView` there is a no-op. `frame.js` therefore reports the target's offset and the page moves. That distinction is invisible until you try it, and this dictionary lands on the iframe path because its articles carry `<script>` (MathJax).

`getElementById` rather than a `querySelector("#"+id)`: dictionary HTML is hand-authored and its ids routinely break the CSS identifier grammar (leading digits, dots, colons), so a selector would need escaping that `getElementById` makes unnecessary. Legacy `<a name>` is scanned only when that misses.

Neither `scrollIntoView` nor `scroll-margin-top` can be used, because the correct resting place is below **two** things the target knows nothing about: the fixed bar and its section's sticky header (D37). One shared `revealAt(viewportTop, section)` measures both and scrolls the page, with `prefers-reduced-motion` honoured as in D38.

**Known gap, deliberately not closed.** The same articles also emit `bword://Artificial Intelligence Notes#note-9` — a word *and* a fragment. Today the word is looked up correctly and the fragment ignored, so the link works but lands at the top of the target article. Honouring it means threading the fragment through `lookupWord` → `doSearch` → an asynchronous, streamed, possibly multi-dictionary render, and then locating the right rendered article. That is a different size of change; the reported failure was the dead link, and this one is merely imprecise.

**Standing rule:** when a URL has parts, handle every part or say which one you dropped. A handler that silently keeps the first half of an address will look correct in code review and dead on screen.

## D40 — A cross-reference is scoped to the dictionary it came from — **ACCEPTED 2026-08-03 (user-directed)**
Every `bword://` / `entry://` / `d:` / `x:` link was searched across **all enabled dictionaries**. That is too wide and it is wrong about what the link means: an author writing `<a href="bword://The Turing Test">` inside their encyclopedia is pointing at **their own** entry. Answering with 40 dictionaries' takes on the phrase buries the one article that was actually referenced, and pays for 104 lookups nobody asked for.

Measured against the real corpus before committing to the rule: in `eng-eng-stanford-ep`, `bword://The Turing Test` and `bword://Cognitive Science` each resolve to exactly one headword **in that same dictionary**. The premise holds.

**Scoped, but never sticky.** The scope is a property of *this navigation*, not of the user's preferences, so it never touches the `#dict` selector — that control is the user's standing choice for words **they** type, and a link click silently rewriting it is precisely the "state changed and I don't remember doing it" failure D35 was decided against. It is a one-shot `scopeOnce`, consumed by the search that reads it, in the same idiom as `navRecord`.

**Never a dead end.** If the source dictionary genuinely has no such entry, the search widens automatically, once, and says so under the results. The guard is `!anyShown`, not `!anyResults`: a dictionary that errored, or that lacks the index the current mode needs, has *not* said "no such word", and widening past it would discard its "enable substring search" offer.

**The scope is visible where it applies.** A note under the results — not in the status line, which fades on a timer — names the dictionary and offers *Search all dictionaries* in one click. Scope describes what is on screen, so it lives and dies with it. Silently widening without a word would be indistinguishable from the link having been global all along, so the fallback says what it did too.

**Shareable and reversible.** The URL gains `from=<id>` alongside `dict=`, so Back/Forward through a chain of cross-references reproduces each scoped view exactly, and a shared link shows the recipient what the sender saw — while `dict=` continues to mean the selector and nothing else.

**Double-click stays global**, in both renderers. Selecting a word is the user asking what something *means*; following a link is the author saying where to *go*. Same destination type, opposite provenance, so they get opposite scopes.

**Word-plus-fragment now works.** `bword://Artificial Intelligence Notes#note-9` looks up the headword in its own dictionary and then reveals `#note-9` inside the article it finds (verified: that headword exists in the same dictionary and does contain `id="note-9"`). Shadow-DOM articles are measured on the next frame; iframe articles receive the fragment through `frameDoc`'s `data-frag` and jump themselves — **after** reporting their height, never before, because the parent sizes the iframe from that message and a target beyond an unsized 90px frame would be clamped by a document that has not grown yet.

**Standing rule:** a link's scope is a fact about where it was written, not about where the user happens to be looking. Carry the provenance with the click, and let it narrow the answer.

## D41 — One reference parser; exact terms and picked prose are different inputs — **ACCEPTED 2026-08-03**
Reported: clicking the footnote marker `<a href="bword://Artificial Intelligence Notes#note-1">` issued `?q=Artificial&dict=…` — the headword truncated at the first space and the fragment gone.

**The proximate bug.** `lookupWord` began with `w.trim().split(/[;.,:{}()\[\]\s]/)[0].replace(/\d+$/,"")`. That line is *correct* for the caller it was written for — a double-clicked text selection, which is prose and arrives with trailing commas and footnote digits attached. It is *silent corruption* for the caller that was later pointed at the same function: an author's link target, which is an exact headword and is frequently several words long. Measured on the real article: **all 59** cross-reference targets in Stanford EP's "Artificial Intelligence" are multi-word, so every one of them was being truncated, and 72 fragments were being discarded.

**The class of problem.** A cleaner that is right for one caller is data loss for another, and nothing in the signature said which kind of input it wanted. The fix is not a smarter regex — no regex can distinguish "prose the user swiped" from "a headword the author wrote" once both are bare strings. **It is two functions:** `searchFor(term, …)` uses its term verbatim; `lookupSelection(text)` tidies prose and then calls it. Every caller now states which it has.

**The same shape, one layer up.** The href was parsed by *two* half-parsers (`wordFromHref`, `fragFromHref`) over the same string with different regexes, and callers re-derived the reference's KIND from the shape of the result — `null` meant "not a reference", `""` meant "fragment only", a leading `@` meant "sub-entry". Three meanings smuggled through one return value is what let a term reach the wrong cleaner in the first place. Replaced with one `parseRef(href)` returning `{kind, word, frag}` — `"lookup" | "anchor" | "sub"`, or `null` — parsed once, dispatched once, never re-derived. `frame.js` carries the mirror image, and the message it posts is now typed by provenance (`"ref"` = author's link, `"pick"` = user's selection) instead of leaving the app to infer it from whether a `dict` field happened to be present.

**The first-principles point that governs all of it: `bword://Artificial Intelligence Notes#note-1` is not a URL.** The `//` promises an authority component, and an authority may not contain spaces — while headwords contain spaces, apostrophes, ampersands and question marks routinely. Anything that normalises an authority (`new URL()`, and most "helpful" URL utilities) mangles them. So the parse is by string position only, splitting at the first literal `#` **before** decoding, so a `%23` inside a headword stays part of the headword rather than being promoted to a delimiter. This is the same fact that already forced `rewrite.go` to convert `bword://@…` into the slash-less `bword:@…` server-side: `@` is the userinfo delimiter and URL normalisation eats everything before it.

**Separation of concerns, as it now stands.** *Server, render time* (`rewrite.go`): rewrite resource references and defuse the `//@` spelling — the only normalisation that must happen before the HTML leaves. *Client, click time* (`parseRef`): one string → one typed reference. *Client, dispatch*: kind → action (inline a sub-entry, jump inside this article, or search). *Client, search layer* (`searchFor` / `lookupSelection`): exact terms verbatim, picked prose tidied first, provenance carried as scope (D40).

Two gaps closed in passing: a plain `<a href="#foo">` now works inside shadow-DOM articles, where document fragment navigation cannot see shadow ids and the browser would previously have dirtied the page URL with a hash matching nothing (iframe articles are left alone — the browser does it natively there); and bare-word slob links are now scoped to their dictionary like every other author reference.

**Standing rule:** a function that cleans its input must say whose input it is. When two callers disagree about whether a string is already exact, that disagreement belongs in the type — two functions, or a tagged value — never in a regex trying to guess.

## D42 — `Keywords` has one stated contract, resolved in one place — **ACCEPTED 2026-08-04**
`wudict keys -n -1` panicked in `makeslice: cap out of range`. The panic is the symptom; the defect is that `Dictionary.Keywords(offset, n)` was documented as *"returns up to n headwords starting at offset"* and said nothing about `n <= 0`, a negative offset, or an offset past the end. Four implementations had drifted into **three different readings**:

- mdx / slob / stardict computed `end := min(offset+n, len(entries))`, so `n = -1` produced `end = -1` and `make([]string, 0, -1)` — the panic. A large `n` would have overflowed the same sum the other way.
- store ran `clamp(n)`, which maps `n <= 0` to `maxLimit` — so "no limit" silently meant **500**, and every browse was capped at 500 whatever was asked for. `maxLimit` bounds HTTP *search* results (FTS-audit #7); `Keywords` is not reachable over HTTP at all, and `cmdKeys` is its only caller.
- the interface comment implied none of the above.

**The contract is now written down** — `n <= 0` means no limit, `offset < 0` counts as 0, an offset past the end returns nil — and, more usefully, it is **resolved in one function** rather than restated at each backend. `dict.KeywordRange(total, offset, n) (lo, hi, ok)` is the only place that arithmetic exists, so a fifth backend cannot invent a fifth reading. It bounds against the *remaining* count (`n < total-offset`) instead of computing `offset+n`, which is precisely the overflow that produced the panic.

**`wudict keys` now lists everything unless asked otherwise** (user-directed). The old default of `-n 50` was a silent truncation of a command whose entire purpose is to be piped into `grep`, `wc` or `sort`: it lied about small dictionaries and quietly cut off every large one, with nothing on screen to say so. Output is buffered — a large dictionary is over a million lines and an unbuffered `fmt.Println` is one write syscall each — and a write error (`| head` closing the pipe) ends the dump rather than crashing.

**Standing rule:** an interface method that takes a limit must say what a non-positive limit means. If it does not, every implementer answers differently, and the disagreement surfaces as a panic in whichever one the user happens to reach first.

## D43 — Article HTML is parsed, not pattern-matched — **ACCEPTED 2026-08-04**
Reported: in OALD10, the pronunciation link resolved to `http://localhost:6888/plaintiff__gb_1.ogg%22`. Four defects, none of them where the symptom appeared.

### The markup

```html
<a onclick="new Audio(this.href).play()" href=plaintiff__gb_1.ogg" class="sound">
```

**The opening quote is missing.** Every browser resolves that through the WHATWG tokenizer's *attribute value (unquoted)* state, which ends the value at whitespace and keeps the stray quote — so the value really is `plaintiff__gb_1.ogg"`, and `this.href` really does resolve against the page origin. The browser was right; we never saw the attribute at all.

### RC1 — markup matched with regular expressions

`attrRef` was `\b(src|href|data|poster)=(?:"([^"]+)"|'([^']+)')`: **it requires a quoted value.** An unquoted one — legal HTML, and what this dictionary writes — does not match, so the reference was left untouched and escaped to the page root. `store/media.go` carried a second, weaker copy of the same pattern, whose comment asserted that "unquoted attributes are rare in dictionary markup". They are not: OALD10 writes one on every pronunciation link, and every one of those assets was silently omitted from `pack media`.

The failure is not a missing case, it is the technique. The same patterns also matched `src="…"` inside a `<script>` string literal, inside an HTML comment, and inside prose, and `<base\b[^>]*>` and `<style>(.*?)</style>` both mis-terminate on a `>` inside a quoted attribute. These are not edge cases to be patched one at a time; they are the difference between matching text and parsing a document.

**Fixed by parsing.** New `internal/htmlref` walks articles with `golang.org/x/net/html`'s tokenizer — the WHATWG state machine browsers implement — so we see exactly what the browser sees. Every token type is accounted for in a documented table, including the two that most needed distinguishing: text inside `<style>` is CSS and gets rewritten, text inside `<script>` is never touched. Untouched elements are emitted as their **original bytes**, so quoting, attribute order, case and whitespace all survive; only an element with a changed value is re-serialised. Both call sites now share it.

### RC2 — the classifier was element-blind

A pattern matching `href="…"` cannot know what element it sits on, so every relative `href` became `/res/{dict}/…` — including `<a href="defendant">`, which is a *headword* in a slob dictionary. Cross-references were being turned into resource fetches that could only 404, and D41's bare-word link handling could never fire because the server had already rewritten the href out of its reach.

`href` is now a resource only where a browser actually **fetches** one — `<link>`, SVG `<image>`, `<use>` — and anywhere else (including `<span class="xr-g" href="defendant_e">`, which is how OALD10 spells a cross-reference) only when it unmistakably names a file. That last line is drawn by `dict.IsAssetName`: `defendant` and `defendant__gb_1.ogg` differ by extension and nothing else. It is an allowlist because the fetching elements are a short closed set, while the elements a dictionary might hang its own `href` on are not.

### RC3 — a correctly parsed value can still be unusable

Parsing gives `plaintiff__gb_1.ogg"`, which resolves to nothing. `htmlref.Clean` strips it, and the justification is about URLs rather than about HTML quoting (which the tokenizer does not report): **RFC 3986 excludes `"`, `'` and a backtick from every component of a URI** — they must be percent-encoded, so a raw one is malformed however it arrived. The tokenizer agrees from the other side, raising *unexpected-character-in-unquoted-attribute-value* for exactly those characters. Only a **trailing** one is stripped; a leading quote is a different malformation, and removing it could change which file is named rather than restore it.

### RC4 — a lazily-built index read without being built

Independent, and it made every one of the above invisible to verify: `slob.Resource` read `d.exactIdx` and `d.foldIdx` **without calling `ensureExact`/`ensureFold`**, assuming some earlier lookup had triggered them. For a *prepared* dictionary that never happens — searches are answered from `text.db` and the slob is reopened solely as the resource fallback (`upgraded.src`), where no lookup runs. So **every resource in every prepared, unpacked slob dictionary was 404**, and `wudict res` never worked at all.

**Standing rule:** parse structured input with a parser for that structure. A regular expression over markup is not a shortcut to the same answer — it is a different, weaker answer that agrees with the parser only on well-formed input, and dictionary HTML is not well-formed. When the browser and your matcher disagree about what a document says, the browser is not wrong.

## D44 — A schemeless `href` is a cross-reference, in both renderers — **ACCEPTED 2026-08-04**
`<a class="Ref" href="defendant" title="defendant definition">` in OALD10 has no `entry://` prefix. It should still resolve, and `defendant` is a real key in that slob — verified against the file.

Two things had to be true, and only one of them was. D43 stopped the server rewriting the href into `/res/{dict}/defendant` (a resource fetch that could only 404), so the reference now survives to the client intact. But **`frame.js` had no bare-word branch**: `index.html` gained one in D41 and its mirror never did, so inside a sandboxed iframe such a link fell through to the browser and navigated the frame to a relative URL under `about:srcdoc`, losing the article. That is exactly the wrong half to be missing — a script-bearing dictionary is precisely what gets rendered in an iframe, and OALD10 carries a `<script>`.

Both dispatch chains now agree, checked by lifting each file's real parser and branch conditions into a harness and running the article's actual references through them: `defendant` and `@topic_law-and-justice?level=c2` (whose `?` is part of the key, not a query — also verified) become scoped lookups, `#relatedentries` an in-article jump, `/res/…ogg` audio, and real schemes are left to the browser.

### Compared with GoldenDict-ng, whose sources were read for this

GoldenDict reaches the same result by a different and rather elegant route: it serves the article page under its own `gdlookup://` scheme, so **a plain relative link inherits it by ordinary URL resolution** and becomes a lookup with no special-casing at all (`articleview.cc:1186`, *"Plain html links inherit gdlookup scheme"*). Its Aard backend additionally rewrites `<a href="X">` to `bword:X` up front (`aard.cc:350`). We arrive at the same place with an explicit branch, because our articles are served as fragments inside a shadow root or an `srcdoc` iframe, neither of which has a base URL we could hang that trick on.

Where we deliberately do **not** follow it — each verified by running its regex against the real markup rather than read off the page:

- **`https://` links become word lookups.** The guard is `[^#](?!ttp://)`, which excludes `http://` but not `https://` (`ttps:/` ≠ `ttp://`), so `<a href="https://example.com/x">` is rewritten to `bword:https://example.com/x`.
- **Every `<a href>` becomes a lookup, including audio.** `<a href="plaintiff__gb_1.ogg">` becomes `bword:plaintiff__gb_1.ogg` — a search for the file name. We keep D43's test: on a non-fetching element an href is a resource only when it names an asset file.
- **The same quoted-attribute assumption we removed in D43.** Its pattern requires `href="`, so OALD10's `href=plaintiff__gb_1.ogg"` is invisible to it too, and falls through to `gdlookup://` — another word lookup. GoldenDict does not play this dictionary's pronunciation audio either, by two independent paths.

One remaining difference is a real choice rather than a defect: a reference like `l2:politics_and_society:law_and_justice?cefr=c2` looks like a URI scheme, so we leave it to the browser while GoldenDict looks it up. Its regex converts *everything*, which is what also produces the `https://` bug. The key does not exist in this dictionary, so nothing is lost today; treating unknown schemes as headwords would need an allowlist of the real ones, and there is no evidence yet that any dictionary depends on it.

**Standing rule:** when a behaviour lives in two renderers, a fix to one is half a fix. `index.html` and `frame.js` implement the same contract for different sandboxes, and every branch added to one must be added to the other or explained in place as deliberately absent.

## D45 — The page and its scripts are cached as one unit — **ACCEPTED 2026-08-04**
Reported: in Merriam-Webster Collegiate 2015, `<a href="entry://complainant">` did nothing. The dictionary is not defective — `complainant` and `suer` are both real headwords in it, and the server serves the article with the `entry://` links intact. The article was correct, the client was not, and the reason was neither of them.

**Two halves of one protocol, cached independently.** `index.html` is served fresh from `/`, while `/assets/frame.js` was served with `Cache-Control: max-age=604800` at a **fixed URL** — up to a week stale. They ship in the same binary and are versioned together, so nothing in the build could tell them apart; only the browser could. D41 renamed the message frame.js posts for a cross-reference from `{t:"lookup"}` to `{t:"ref"}`/`{t:"pick"}`, and a cached frame.js went on posting a name the new index.html no longer listened for. Every `entry://` link went nowhere.

The failure is precisely shaped by which renderer a dictionary lands in: shadow-DOM articles never load frame.js and kept working, so the symptom appeared only in **script-bearing dictionaries** — Merriam-Webster carries one — which reads as "this dictionary is broken" rather than "your cache is stale". That is what makes this class worth fixing structurally instead of by telling the user to hard-reload.

**Content addressing.** The page now requests `/assets/frame.js?v=<8 hex of sha256(frame.js)>`, and the same for mark.min.js, so the URL changes exactly when the bytes do. The week-long cache becomes correct rather than dangerous, and gains `immutable`. Deliberately **not** the build version: a developer rebuild leaves `Version` at `dev`, which would keep a changed script behind an unchanged URL — the very failure being replaced.

`/` is now served `no-cache`. It is the only thing that names those hashes, so a heuristically-cached page would ask for a stale script by its old hash and put the two out of step again. Content addressing is only as good as the freshness of the document that does the addressing.

**Standing rule:** two files that must agree must be *fetched* as one unit, not merely built as one. Shipping them in the same binary proves nothing about what the browser holds; give the dependent file a URL derived from its content, and make the file that names it revalidate.

## D46 — An `.mdd` is inspectable, not discoverable — **ACCEPTED 2026-08-04 (user-directed)**
`wudict keys x.mdd` failed with "unsupported dictionary format". Two proposals were rejected before the right one, and the rejections are the useful part.

**Rejected: `res -l`.** It changes the *output type* of a command. `res` emits the bytes of one resource and has `-o` to write them to a file; `res -l` would emit a list of names to stdout. Those are two operations wearing one name, and `-o out.ogg -l` would be meaningless with nothing in the flag set saying so.

**Rejected: `keys -res <dict.mdx>`.** Better — the flag would select a collection rather than change what the command emits — but it fails on three counts, all pointed out by the user. It **assumes the .mdx exists**, which is not a contract we can offer: a user may hold only the resource file. It **conflates companions**: an .mdx may have `NAME.mdd`, `NAME.1.mdd`, `NAME.2.mdd`, and the union of all of them is not what naming one file asked for. And it is **one more syntax to memorise** for an operation the user already knows how to spell.

**Accepted: `wudict keys x.mdd`, with no flag at all.** An .mdd is the *same key-block file format* as an .mdx, carrying file bytes where the articles would be — a key/value store in its own right. So `keys` enumerates it and `res` fetches from it, with the identical grammar, the identical `-offset`/`-n` semantics (D42), and no second spelling. This also matches **mdict-utils**, which people already know.

**The mechanism this needed: openable is not the same as discoverable.** `dict.Open` and `dict.Discover` shared one registry, so registering `.mdd` as a format would have made every companion appear as a dictionary in the panel — the same greedy registration the store package already warns about, where a bare `.db` key made every `media.db` sidecar open as a phantom dictionary. `RegisterInspectable` splits the two: `openerFor` consults dictionary formats first and inspect-only containers last (so a real format always wins), while `discoverableFor` never sees them at all. Verified against the real folder: 39 `.mdd` files present, 0 discovered, 51 `.mdx` still found.

**One contract worth stating: whatever `keys` prints, `res` accepts, unchanged.** MDD stores keys as `\path\name`; the listing normalises to the forward-slash, no-leading-separator form the rest of wudict uses, and keeps the **original case** (`audio/es/Argentina/…`) because lookup is case-insensitive. Round-tripping every printed name back through `Resource` is a test, not an assumption.

**Standing rule:** when a user reaches for an existing verb on a new kind of file, the answer is usually to make the verb work — not to add a flag, and not to make them name a different file. A new spelling is only justified when the operation is genuinely different, and "enumerate the keys of a key/value container" is the same operation whatever the values happen to be.

## D47 — @font-face is hoisted out of the shadow root — **ACCEPTED 2026-08-05**
AHD5's IPA rendered as fallback serif: `<font face="Minion New">ă</font>` showed `ă` in Times New Roman, and devtools reported the family as unresolved. The font was not missing. `ahd5.css` — served from the `.mdd`, 2.9 MB — declares four `@font-face` rules, `'Minion New'` among them, with the TTF inline as a base64 `data:` URI. It was fetched, parsed, and then ignored.

**The rule that bites: `@font-face` does not participate in shadow-tree scoping.** Ordinary rules in a shadow root apply to that tree, which is precisely why D-era article rendering uses one — the dictionary's CSS cannot reach the chrome. Font *families*, though, are resolved against the **document's** font set, so a face declared inside a shadow tree is parsed into a sheet nothing can select from. There is no scoped form of `@font-face` in CSS: a face is document-global or it does not exist. This is not a browser bug and there is no flag for it.

The symptom is shaped by the renderer, exactly as in D45: script-bearing dictionaries render in an iframe, which is a real document, so their fonts have always worked. Only shadow-DOM articles — the majority — lost them, silently, for as long as the shadow renderer has existed.

**Fix: lift the faces, and only the faces.** After an article is connected, its stylesheets are walked and every `CSSFontFaceRule` is copied into one document-level `<style id="wudict-fonts">`. Every other rule stays scoped where it belongs, so the isolation the shadow root exists for is untouched.

**Read the faces from CSSOM, do not re-parse the CSS.** The engine has already parsed the sheet in order to render the article; `link.sheet.cssRules` is same-origin and readable. Re-parsing 2.9 MB of CSS in JavaScript to learn something the engine already knows would be waste, and a hand-written parser would have to get comments, escapes, `@media`, `@supports`, `@layer` and `@import` right — the walk descends through all of them instead, and `rule.style.getPropertyValue("font-family")` replaces a regex over `cssText`.

**One guard: the chrome's own families are skipped.** A face is document-global by nature, so a dictionary declaring `@font-face{font-family:Helvetica}` would restyle the application around it. Dropping such a rule costs the dictionary nothing — the system face takes over, which is what naming `Helvetica` asked for. This exposure is inherent to `@font-face`, not to this fix; GoldenDict carries the same one, with the difference that its chrome is not in the document.

**Standing rule:** a shadow root scopes *rules*, not *registrations*. Anything a stylesheet installs into a document-wide namespace — fonts today, and by the same rule `@counter-style`, `@property`, `@keyframes` referenced from outside — is invisible from inside a shadow tree, and has to be hoisted deliberately or it will fail silently.

## D50 — `no-cache` needs something to revalidate against — **ACCEPTED 2026-08-05**
Raised while costing out minification of `index.html`. The page is 102,574 bytes and `handleIndex` set `Cache-Control: no-cache` and then wrote the body — no `ETag`, no `Last-Modified`, and `net/http` adds neither for a plain `Write`. So **every load, including a plain reload, re-sent the whole 100 KB.**

`no-cache` does not mean "do not store"; it means "revalidate before use". Half of that contract was missing: the browser was told to ask, and given nothing to ask *with*, so the only question it could pose was "send it again". D45 chose `no-cache` for a real reason — the page is the only thing naming the content-addressed script hashes, and a stale one would request stale scripts — but the cost it accepted was avoidable. `s.indexETag` is computed with `s.indexPage` under the same `sync.Once`; an unchanged page now costs a 304 and no body, and the freshness guarantee is **unchanged**: the browser still contacts the server on every single load.

This is D45's content addressing turned around. There the URL carries the hash so the answer can be cached forever; here the validator carries it so the question is cheap to ask.

**`http.ServeContent`, not `If-None-Match == etag`.** The header is a *list*, it may be `*`, and a GET compares entity-tags **weakly**, so a cache may echo our own validator back as `W/"…"`. An equality test would silently fail to match a tag we issued ourselves and re-send the page — the bug would look exactly like no fix at all. net/http implements RFC 9110 §13.1.2; hand-rolling it is the kind of "sloppy assumption" that produced D43.

**Hashed after substitution.** `{{VERSION}}` and the two asset hashes are part of what the browser holds, so a rebuild changing only the stamp must invalidate.

**Deliberately no `Last-Modified`.** The bytes are embedded in the binary and have no meaningful date; `time.Time{}` suppresses the header. Offering a second validator we cannot stand behind is worse than offering one.

**No validator on the first-run setup page.** That body is a function of registry state nothing versions, so an ETag there would be a promise we cannot keep.

**Rejected: minifying index.html.** Measured first: 39% of the file is comments, so minification would save ~50 KB — of a **10.8 MB** binary (0.46%), served over loopback, parsed in single-digit milliseconds against a startup that opens 102 dictionaries in *seconds*. The toolchain cost is structural rather than merely effortful: `go install …@latest` must keep working tag-less (D29) and **never runs the Makefile**, while `go:embed` embeds committed files — so a build-time minifier means either making node a prerequisite nothing would run, or committing a generated `index.min.html` permanently able to drift from its source. A step `go install` silently bypasses is the wrong shape for a project whose Makefile is the developer UI (D10).

**Rejected: gzip/brotli.** Measured: gzip −64% (36,737 B), brotli −69% (31,508 B) — both beat minification. Declined by the user on the correct grounds: wudict is served over loopback, so compression adds CPU on both ends to shorten a memcpy. Revisit only if serving over LAN becomes a real use.

**Standing rule:** a cache directive is half a protocol. Whenever one is set, name the validator that answers it — otherwise "revalidate" degrades to "re-download", quietly and forever.

## D51 — In a srcdoc article, the browser resolves against the wrong URL — **ACCEPTED 2026-08-05**
Clicking the English/American tabs in Cambridge English Dictionary Online loaded **the whole app inside the article's own iframe**. The dictionary's `scripts_cb.js` was suspected and is innocent: the nested app came up at `?q=wool&mode=prefix&dict=all` — character-for-character the *parent's* URL, which no dictionary script could reproduce. That is the browser resolving a relative reference against a base URL.

**An `about:srcdoc` document splits the two URLs that decide what `#x` means.** Its document URL is `about:srcdoc`; its **base URL is inherited from the parent browsing context**. Link resolution uses the base, same-document detection compares against the document URL, and they disagree — so `#dataset-british` resolves to `<the app's own URL>#dataset-british`, is judged a different document, and triggers a **cross-document navigation**. `frameDoc` emits no `<base>`, and D43 drops any the dictionary shipped, so nothing intervenes.

**How the wrong assumption got in.** D44's exclusion list in `frame.js` was derived by *mirroring index.html's*, and its comment said so: *"an in-page anchor (the browser follows those natively here, which index.html cannot do inside a shadow root)"*. `#` is the single entry where the two renderers genuinely differ, so mirroring was guaranteed to get exactly that one wrong. Four lines above, the same block states the real rule — those links *"navigated the iframe to a relative URL under about:srcdoc and lost the article"*. The base-URL inheritance that motivated D44's bare-word branch and D45's absolute `/res/` URLs breaks fragments for the same reason; the fix was applied to two of three consequences and explicitly carved out for the third.

**Neither renderer can leave a fragment to the browser** — shadow roots because document fragment navigation cannot see shadow ids (D41), srcdoc because the document URL is not the base URL. `frame.js` now owns fragment clicks: `preventDefault` (categorically correct here, not a guess about one dictionary), then the existing `jumpToFragment` deferred by a task so the offset is measured *after* the dictionary's handler has changed the layout, with `post()` first for the reason the load handler already documents. **Propagation is deliberately not stopped** — unlike a `bword://` reference this click belongs to the dictionary, and cancelling the navigation was the only thing Cambridge's jQuery tabs needed from us.

**The cousin: external links.** The same Cambridge entry links to `dictionary.cambridge.org` three times. The sandbox grants no `allow-top-navigation`, so the default navigates *the iframe* — a whole website inside the small box where the article was. In the shadow renderer the same click costs the user their search instead. One cause, two shapes of damage, one answer in both renderers: a new tab. The frame hands the URL to the parent rather than opening it itself, because **a popup from a sandboxed frame inherits that sandbox** unless `allow-popups-to-escape-sandbox` is granted — the site would open without `allow-forms` and its own search box would be dead. Widening the sandbox to fix a link is the wrong trade.

**The scheme test on `{t:"open"}` is not decoration.** `window.open` in the parent runs in the TOP page's context, so a `javascript:` URL posted by a dictionary's own script would execute with our origin, our article cache and our prefs API. An article can already open popups (`allow-popups`), so nothing here widens what a dictionary can do — but this message must never become the way it gains more.

**Rejected: `<base href>` in the frame document.** The obvious first thought and it fixes nothing: no base value can equal `about:srcdoc`, so fragments still resolve cross-document, and it would re-root every relative reference besides.

**Rejected: assigning `location.hash` inside the frame.** It would work — `about:srcdoc#x` *is* a same-document navigation — and would buy `:target` and `hashchange` for free. But each click pushes an entry into the iframe's session history, which joins the top-level history, so **Back would walk backwards through tab clicks** instead of leaving the page.

**Deferred: serving articles from real same-origin URLs instead of srcdoc.** The structural answer — document URL == base URL, so fragments, `:target`, `hashchange` and relative references all work natively and this whole class disappears; it is what GoldenDict gets from `gdlookup://`. It costs a round trip per article, requires articles addressable by (dict, key), and reopens the sandbox question, since a real URL with `allow-same-origin` lets dictionary scripts reach the parent while dropping it breaks the sub-entry `fetch`. The direction to take if a third instance of this class appears.

**Known limitation of the accepted fix:** `:target` CSS and `hashchange` listeners still do not fire in either renderer. A dictionary implementing tabs purely through `:target` would remain inert. Only the deferred option above changes that.

**Standing rule:** an exclusion list is a claim about the *container*, not a list to copy between renderers. Every entry has to be re-derived against the environment it runs in — the entries that agree cost nothing to re-check, and the one that differs is the one that will bite.

The cgo flavour (mattn + in-process speex, NDK pinned per ABI, `-Wl,-z,max-page-size=16384`) remains the documented upgrade path if .spx playback matters on Android.

**Rejected: gomobile `bind`/`build`** (above); **c-shared + JNI** (same-process lifecycle buys a localhost server nothing and forces an NDK plus glue); **SAF copy-in import** (doubles storage for multi-GB dictionaries — revisit if the all-files grant proves too scary for users); **foreground service** (a dictionary is used while it is on screen; the child dies with the task, and that is correct for v1).

**Standing rule:** the Android app adds no Go code and no build tags — it is the *same* binary, packaged. Anything Android needs from the program arrives as flags and environment (`HOME`, `TMPDIR`), so the desktop surface is untouchable by the port.

## D53 — Android engine: cgo parity — mattn FTS5 + in-process speex, via the NDK — **ACCEPTED 2026-08-05 (user-directed)**

## D54 — Android shell: the container is Android 16, not Android 14 — **ACCEPTED 2026-08-06 (review of D52/D53)**
A code review of the `android-cgo` branch found four defects that share one shape: the shell was written against assumptions about its container that the container has since stopped honouring, or never honoured.

**Edge-to-edge is not optional.** `values-v35/styles.xml` set `windowOptOutEdgeToEdgeEnforcement`. Android 15 forces edge-to-edge on apps targeting API 35+, and Android 16 **disabled that opt-out** for apps targeting API 36 — which is us (`targetSdk 36`). The attribute was therefore doing nothing, and the page — which has a `position:fixed` top bar and a fullscreen panel, and knows nothing of system bars — was drawing under the status bar and the gesture bar. The opt-out is deleted and `MainActivity` pads the root by `systemBars() | displayCutout()`, with the IME folded into the bottom inset because an edge-to-edge window no longer gets `adjustResize` applied by the decor (`adjustResize` is declared anyway, for the pre-35 path). **The shell absorbs the platform, not the page:** no `viewport-fit=cover`, no `env(safe-area-inset-*)`, nothing in `index.html` learns what Android is. Window, inset padding and WebView pre-paint all use one `window_bg` colour that follows day/night (`values-night/`), and the system-bar icon appearance follows it too. *Known gap:* the page has its own light/dark/auto picker, so an explicit override disagrees with the strip until a page→shell theme channel exists — deferred, not forgotten.

**`onBackPressed()` is dead code on any modern device.** Apps targeting API 35+ get predictive back by default, and for those the framework no longer calls it — so the back button would have exited the app instead of walking the SPA's history. `OnBackInvokedCallback` is now registered on API 33+, and only while `canGoBack()` (kept in step by `doUpdateVisitedHistory`), so the system keeps its own predictive-back-to-home animation for the last press. The old override stays for API 26–32.

**A WebView has no tabs.** D51 hands an article's external links to the page, which opens them with `window.open()` — inert in a WebView unless multiple windows are enabled and `onCreateWindow` answers. Enabled, and answered by handing the transport a throwaway WebView purely to learn the URL (the callback carries no other way to get it), which then goes out as `ACTION_VIEW`. `shouldOverrideUrlLoading` covers ordinary link clicks the same way. Our own origin stays; `data:`/`blob:`/`about:`/`javascript:` stay, because those are the article machinery's own URLs.

**`--dict-dir` was commented out.** The shared `Dictionaries` folder was created, permission-prompted for, and never scanned — with `HOME` = the app's files dir, the server's default `$HOME/Dictionaries` resolved to the app-private fallback, so `MANAGE_EXTERNAL_STORAGE` and its dialog were doing nothing. Fixed by *not* restoring the flags: the shell seeds `~/.wudict/wudict.toml` with `DICT_DIR` on first launch instead. A flag is the highest config layer, so `EditableInFile("DICT_DIR")` would be false and the ☰ panel would correctly refuse to change the folders — on the one platform with no command line to change them from. Coming from the file, the panel owns them. Cost accepted: the server's fully-commented first-run template is not written on Android, because a config file is already there.

**Also fixed:** an exec'd child is reparented to init when Android kills the app, so a stale server can still hold 6888 — `ServerProcess` now adopts a server that is already listening, but only after `/api/config` answers with `configInfo`'s own field names, since loopback is shared with every app on the device; `awaitPort` watches the child as well as the socket, so a server that dies on startup reports its own last line instead of holding "Starting…" for the full minute and then blaming the network; late `onReady`/`onFailed` callbacks no longer touch a destroyed activity; `packagingOptions` → `packaging`; the version-stamp closure calls `waitFor()` rather than `exitValue()` on an unreaped process, which was silently turning good tags into `dev`; and the CI version step's `[ … ] && …` is now an `if`, because run steps are `bash -e` and it would have aborted on exactly the runs that pass a tag.

**Standing rule:** a `targetSdk` bump is a change of container, not a number. Every behaviour the shell relies on — insets, back dispatch, storage, window.open — has to be re-derived against the API level being targeted, not the one the pattern was written for.

## D55 — Narrow viewports: the field is the row — **ACCEPTED 2026-08-06 (user-directed)**
The bar laid nine controls out as a flat row of peers (`flex-wrap:wrap; justify-content:center`), each entitled to its intrinsic width. That is right at 800px and wrong at 360px for two reasons. **Vertical is the scarce axis:** the wrap cost an entire second row — `padding-top:5.6em` — permanently, on the device with the least height to give. **And the controls are not peers:** `#q` is the app, mode and dictionary are scope the user *consults*, and the rest are view settings the ☰ panel already houses.

**The pill.** Below 600px `#q`, `#mode` and `#dict` are wrapped in one bordered `.pill` that takes the whole row: the field reads as large because it *is* the row, and two borders and two gaps of visual noise disappear with it. Above 600px the wrapper is `display:contents` and the chips are `display:none`, so the desktop bar renders exactly as it always did — **one markup, two rule sets, no second layout to keep in step.**

**The chips.** Each scope control is a `<span class="chip">` with its real `<select>` laid over it transparently (`position:absolute; inset:0; opacity:0; appearance:none`). The select keeps the native full-screen picker, the keyboard, its `aria-label` and its `.value`, so **every call site that reads `$("dict").value` is untouched — only the rendering is replaced.** `.seg` is `align-self:stretch` with `min-width:40px` so the transparent select covers a 44px target rather than the 22px the chip's text occupies: the chip is what you see, the seg is what you hit.

**The rule the chips obey** is the one D48 and D49 already established, stated generally: **the default carries no information, so it costs no pixels; a departure from the default is the only thing worth naming — and is exactly when the user needs reminding of it.** `All dictionaries` is what every session already is, so at `all` the dictionary chip is a book glyph alone and grows a name only when scoped; the mode chip recedes to `--fg-faint` at `starts with` and takes the accent tint otherwise. `"starts with"` shortens to `"starts"` and the other three keep their words — those are the words the mode dropdown, the per-dictionary switch and the result summaries all use, and a chip that renamed *full-text* would sever the link to every other place it appears (the same trap D48 caught in the bulk-FTS wording).

**Dropped below 600px rather than shrunk,** because each is a big-screen affordance: `🔍` (the form has exactly one implicit-submission field, so Enter still submits, and a phone keyboard offers a Search key anyway), `⇔` (below 600 `.col` is already `auto`, so wide mode has nothing left to widen) and `⊞` expand-all (putting a hundred articles on screen at once is not a phone act). `◐` theme moves to the panel head — a second *mount point*, not a second control: both elements carry `.themeBtn` and one handler drives the pair, the way the wordmark already has two homes.

**Gutters reclaimed.** Three nested `.618em` insets — column, list, article — put 30px of a 360px screen into margins before a word of a definition. At `.382em` that is 18px: **+8% article width.** And `body{padding-top}` below 600px is now `calc(var(--barh) + var(--sp-2))`, deleting the `5.6em` magic number: `--barh` is measured synchronously at the end of the body, so it is real before first paint and the padding can never drift from the bar again.

**One behaviour change, deliberate:** `#mode` had no `change` handler at all — it took effect on the next submit. Survivable while a 🔍 button sat beside it; with no submit button on narrow, picking a mode would have appeared to do nothing. Made symmetric with `#dict`: re-run if there is something to re-run. This applies at every width.

**Measured, 360px:** bar 2 rows → 1 (`5.6em` → ~66px, ~24px back), search field ~100–130px → **~206px**, article width +28px.

**Standing rule:** a responsive breakpoint is not a place to shrink things. Ask which controls are the app and which are settings, and let the second group leave.

## D56 — Progress is chrome, statements are content — **ACCEPTED 2026-08-06 (user-directed)**
`#status` reserved **34.3px permanently** — `padding:var(--sp-2) 0` (16.1px) plus `min-height:1.4em` (18.2px) — above the first result, at every viewport, for a line that is `opacity:0` for almost the whole session. An audit of its 14 call sites split them cleanly in two: **progress** (`Searching…`, `N of M ready`), which is ephemeral, non-actionable and read peripherally if at all, and **statements** (`⚠ All dictionaries are disabled`, `searched 12 of 105 — still loading`, `✓ full-text enabled on 12`), which are meant to be read and sometimes acted on. One box reserving permanent space for both is the wrong shape: progress should cost **no layout**, statements should cost layout only when they exist.

**Progress moved into the search field, as a morph.** A `⌕` glyph at the field's LEADING edge crossfades into the spinner while a search is in flight. Nothing appears, nothing moves — a glyph changes identity inside a box that was already occupied, which is the least intrusive transition physically available, and it sits at the locus of action: the user just typed there, and on a phone their thumb is still there. At rest the `⌕` also gives the field an identity, which matters most below 600px where the wordmark is hidden.

**Rejected: the trailing edge, over the native `✕`** — the user's first instinct, and worth recording why it fails. `::-webkit-search-cancel-button` renders only when the field is non-empty, and `doSearch` returns early on an empty query, so the `✕` is present for **100% of searches**: the collision is total, not occasional. Occupying that slot would mean hiding the user's escape hatch exactly when a search is in flight; it would put a non-interactive thing where an acquired motor plan says "tap to clear" (target substitution — worst on a phone, where the target is thumb-sized and there is no hover to disambiguate); and it renders *status* where *control* lives, which is a category error. Also rejected: **a spinner beside the `✕`** (the `✕` then shifts under the finger on every search) and **an animated field border** (zero layout and rather beautiful, but a large moving element in the foveal field that fights the focus ring for the same pixels).

**Two timings make it calm rather than twitchy.** Most searches settle in 200–600ms, and a spinner shown at t=0 for 180ms is a *flash* — perceptually worse than no indicator, because it reads as a glitch rather than as work. `BUSY_DELAY=200` holds it back until a search is slow enough to need explaining; `BUSY_MIN=400` keeps it visible once it has appeared. The same pair of ideas `STATUS_MIN` already applies to the status line, applied to a glyph. Under `prefers-reduced-motion` the ring holds and only the rotation stops.

**Statements keep the column, and cost nothing until they exist.** `#status` becomes a `grid-template-rows:0fr → 1fr` transition: real height animation with no measurement and no magic number. Three levels, one job each — `#status` is the grid, `.msg` is the clipped row, `.txt` carries the padding *inside* the clip, so the closed state is 0px and not 0px-plus-padding.

**A golden-mean defect, fixed in passing:** the ladder is `.382 · .618 · 1 · 1.618 · 2.618` — clean φ powers — and `min-height:1.4em` was the one number in this stylesheet off it. It was also redundant: `line-height` is already φ, so `13px × 1.618 = 21.03px` sizes the open state by itself. Deleted rather than re-tuned.

**Recovered: 34.3px on every viewport, permanently** — in the steady state *and* during every search, since the common case no longer produces text at all.

**Standing rule:** before reserving space for a message, ask whether it is a statement or a symptom. A symptom belongs in the chrome that is already on screen, at the locus of the action that caused it; only a statement earns room in the reading column.

## D57 — The submit button is gone, at every width — **ACCEPTED 2026-08-06 (supersedes the narrow-only hide in D55)**
D55 hid `🔍` below 600px and kept it above, on the conservative ground that a hidden submit button is still the form's *default button* and therefore cannot disturb implicit submission. D56 then put a `⌕` inside the field, and the bar was carrying a magnifier next to a magnifier. Re-examined, the conservatism had also been resting on an unchecked assumption.

**The decisive fact:** the app has searched **as you type** since long before any of this — `#q`'s input handler, 300ms debounce, from two characters — and a paste fires `input` too. So the button was never the path for the ordinary case; it only ever mattered for a query the debounce skips (one character) or a deliberate re-run of an identical query. **Enter covers both**, and always did.

**Enter still submits with no button at all**, by a different clause than before. HTML's implicit-submission algorithm: with no submit button, submit unless the form has *more than one* field that blocks implicit submission. The blocking list is input types Text/Search/URL/Telephone/Email/Password/Date/Month/Week/Time/Local-Date-and-Time/Number — `<select>` is not on it. This form has exactly one blocking field (`#q`), so it submits, and the existing `submit` listener runs unchanged. Verified by count, not by eye: one blocking field, zero submit buttons.

**Accessibility, considered and answered.** The one real argument for a click target is pointer-only input — head-pointer, eye-tracker, switch — where "press Enter" means a round trip through an on-screen keyboard. Live search answers it: any query of two characters or more runs with no keypress whatsoever, including a mouse-pasted one. A single-character query still needs Enter, but a pointer-only user reaching one already has the on-screen keyboard open. No WCAG success criterion requires a submit button, and `role="search"` plus a `⌕` plus a `Search…` placeholder plus results appearing as you type leaves no discoverability gap.

**Standing rule:** before keeping a control "just in case", enumerate what it uniquely enables. If every entry on that list has another path the user already takes, the control is not a safety net — it is a second magnifying glass.

## D58 — A motion ladder: φ in the time domain — **ACCEPTED 2026-08-06 (user-directed)**
The field spinner from D56 inherited the shared `.spin`: 14px, a 2px ring, `--accent`, **0.7s per revolution**. Four separate things made it shout, and each has a fix that is derivable rather than tuned by eye.

**Speed.** 0.7s/rev is ~514°/s, and the arc passes any given point ~1.4 times a second — inside the few-hertz band where a repeating motion reliably captures attention (the same reason a blinking cursor is impossible to ignore). Now `--t-6` = **φ² seconds** per revolution, which is `360°/φ² = 137.5°/s` — **the golden angle per second**, the divergence angle phyllotaxis advances a sunflower's seeds by. 3.7× slower, and it lands in the register of a clock hand: unmistakably moving, demanding nothing.

**Colour.** `--accent` is reserved for headwords (`dt`) and active states; spending the app's loudest colour on a non-event ranks it above the content, which is the hierarchy upside down — the same error D48 caught in the shouted bulk-FTS wording. The arc is now `currentColor`, i.e. the *same* `--fg-faint` the `⌕` is already drawn in, and the ring behind it is transparent. So the morph changes **nothing but geometry**: same box, same size class, same colour.

**Size.** Inset 2px inside the glyph's box — 10px, φ⁻¹ of the 14px `⌕`, with the stroke thinned to 1.5px to match.

**The minimum-display timer is gone, and that is the semantic fix.** `BUSY_MIN=400` existed to stop the spinner strobing, but a hold is exactly what creates the contract the user objected to: *wait for me to finish*. The 382ms opacity transition already **is** a minimum display — a spinner cancelled part-way through its fade-in reverses from wherever it reached, so it cannot strobe; it can only leave a ghost. Moving the guarantee from a timer into the transition lets the indicator go the instant the results are there, because it never arrived hard enough to owe the user a departure.

**The ladder itself.** `--t-1:.236s … --t-6:2.618s` — the same φ progression as `--sp-*`, in time. Geometric for a reason that is not decorative: **perceived duration grows roughly logarithmically, so equal ratios read as equal steps while equal differences do not.** It is why f-stops, musical intervals and decibels are all geometric. With a ladder, a duration is chosen by picking a rung instead of by taste, and `BUSY_DELAY` becomes φ⁻³ s rather than a round 200.

**Not done here:** the existing transitions (`.16s`, `.18s`, `.25s`, `.28s`, `.35s`) are all within a few ms of a rung and could be retrofitted onto `--t-*`. Left alone deliberately — they are tuned values, and "nearly invisible" is not "invisible". A separate pass, if wanted.

**Standing rule:** an indicator's job is to *report*, not to *promise*. Anything that must be waited out — a hold timer, a hard appearance, an accent colour, a few-hertz rhythm — converts a report into a contract.

**Regression, and the rule it produced (2026-08-06).** The first cut of the smaller spinner sized it with `inset:2px; width:auto` and it vanished on screen. Cause: the shared `.spin` carries `margin-right:.4em` for its inline uses and is declared *later* than `.qled>*{margin:0}` with **equal specificity**, so its margin wins on that element. That was harmless while the width was explicit — over-constrained absolute positioning simply drops `right` — but `width:auto` makes the solver *spend* the margin: `14 − 2 − 2 − 6.4 = 3.6px`, a box too small to see. Fixed by stating the geometry explicitly and restating `margin:0` at the higher specificity. **Rule: never size an absolutely positioned box from insets alone when a shared class may put a margin on it** — and when a shared class is being re-skinned, resolve the cascade rather than assuming the more specific selector covers everything, because it only covers the properties it actually names.

## D59 — A dictionary's bundled resource can be overridden from its library folder — **ACCEPTED 2026-08-07 (user-directed)**
Cambridge English Dictionary Online's entry tabs (English / American / Business) showed only the first, and clicking did nothing. The renderer was innocent: **the dictionary ships a corrupt jQuery.** `jquery.js` inside the slob is 86,659 bytes of which **12,186 are NUL** — nine holes, each an exact multiple of 1,354 bytes, in a 64-block structure, head and tail intact (so damage, not truncation). It cannot parse, `$` is never defined, `scripts_cb.js` dies on its first statement, and no tab handler is ever bound. The `on` class on the first `.tabs__content` is in the **stored HTML**, not something the script set — which is why the DOM looked like a working tab widget stuck on tab one.

**Diagnosed, not guessed.** An independent slob parser (own header decode, own zlib call, no wudict code) produced a **byte-identical** blob, so wudict serves exactly what the file stores. A jsdom harness ran the real article and the real `scripts_cb.js` against an intact jQuery: the guideword transform fires, the click handler binds, and the three tabs switch correctly — **a good jQuery is the entire fix, and no renderer change is needed.** A scan of every `.slob` in the corpus found this is the only damaged blob among 40+ JS/CSS resources, so it is one broken file, not a systemic fault. D51 is also exonerated: those tabs never worked here — the old nested-iframe symptom was the browser following `href="#dataset-british"`, which happens whether or not jQuery is bound, so fixing it replaced a visible wrong thing with an invisible dead one.

**The mechanism, and why it is not a special case.** `/res/{id}/{name}` now serves `<library folder>/res/{name}` when that file exists, falling back to the bundled blob otherwise. It knows nothing about jQuery, about Cambridge, or about what a working replacement looks like: **any resource of any dictionary can be shadowed.** The library folder is the right home — wudict's own storage rather than the user's possibly read-only dictionary folder, already displayed with a reveal button in the panel, and the unit D20 made transferable, so a repair travels with the dictionary it repairs. Overrides are served `no-cache` (not the bundled `max-age=86400`): a file the user is actively editing must not have their next attempt hidden by yesterday's copy.

**Rejected: shipping jQuery and substituting it** when a bundle is unusable — effective and zero-effort, but it would make wudict carry a third-party library to paper over one broken file, under a rule reading "if a resource named jquery.js fails, use ours". Also rejected: **rewriting the blob inside the .slob** (bins are compressed and every offset after the patched one shifts, so it means rewriting 963 MB of a file we did not author) and **stripping the NULs** — the holes replaced 12 KB of real code, so a NUL-free copy is still broken, just harder to diagnose.

**Damage is now stated, once.** A NUL byte cannot occur in JavaScript, CSS, HTML, JSON, XML, SVG or plain text, so finding one in a resource of those types is proof the stored blob is damaged. `/res/` watches the bytes it is already copying (one `IndexByte` per buffer, no buffering of the resource) and logs a warning naming the file and the override path — once per dictionary+resource, because the fact is about the file and every article referencing it would otherwise repeat it. Binary types are exempt: a NUL is perfectly ordinary in a font, an image or an audio blob. **The bytes are never altered** — diagnosing damage is not licence to modify what the dictionary stores.

**Path safety, verified by removing it.** `name` comes from a URL, so it is `path.Clean`ed on a rooted copy and then checked with `within`. Both guards were deleted in a mutation run: four traversal vectors leak a file above the directory without them, and the test fails as it should. Neither guard resolves symlinks and neither needs to — the only way a link reaches that directory is the user putting it there, in wudict's own storage, reachable only from loopback.

**Amendment (2026-08-07):** `res/` was described, in the code and in every doc, purely as a way to *replace* a damaged file — but because the override is consulted before the dictionary is opened at all, it equally *supplies* a resource the container never contained, which is the commoner case for dictionaries repacked from a website (an article referencing `js/entry.js` that no `.mdd` ever held). Nothing in the mechanism changed; the framing had hidden half of what it does, and the docs and tests now cover both. Nested names are part of that: articles routinely ask for `js/…` and `css/…`, and a flat-only override would have been useless for exactly the dictionaries most likely to need one — now asserted rather than assumed. **Known asymmetry, documented not fixed:** an overridden `.spx` is served verbatim while a bundled one is transcoded to WAV (D18), because `serveOverride` returns before the transcode path — and since `.spx` maps to `audio/wav` in the MIME table, the bytes would also be mislabelled. Fixing it means deciding how the WAV cache is keyed for a file the user can edit, so it is a separate change; until then the docs say to supply `.mp3`/`.wav`.

**Standing rule:** when a dictionary misbehaves, establish whether the bytes we serve are the bytes it stores *before* touching the renderer. A parser that shares no code with ours settles it in minutes; a renderer change made without that answer is a guess that will be defended for months.

## D60 — Iframe height must be measured from content, never from the viewport — **ACCEPTED 2026-08-07**
Some articles showed a large blank strip below their content — up to ~490px on Cambridge. Not the dictionary's styling: `styles_cb.css` sets no height on `html` or `body`. Two defects in `frame.js`'s `post()`, both from the same root cause — it measured the frame using a quantity that *depends on the frame's current height*.

For the ROOT element, `scrollHeight` is defined as **max(scrolling area, viewport)** (CSSOM View), and the viewport here **is** the iframe the parent already sized from our previous answer. So:

**(1) A ratchet.** `documentElement.scrollHeight` can never report less than the height we were last given, so the frame could only ever grow. Invisible for as long as every article merely got taller; obvious the moment content could shrink in place — which is exactly what D59 restored, since Cambridge's tabs now switch a long "English" panel for a short "American" one. Measured: **492px of blank frame**.

**(2) A runaway.** The parent sets `height = h + 6`. That 6px lands in the viewport, the viewport is fed back through `scrollHeight`, and the next measurement returns it — so **every `post()` call added 6px permanently**. There are three timed calls on load (immediate, 600ms, 2500ms), so *every* article in the iframe renderer was born with 18px of dead space, plus 6 more per tab click, per late reflow, per ResizeObserver fire. This one was never reported because 18px reads as generous padding rather than as a bug.

**The fix is to measure boxes whose height is driven by their CONTENT**: the root's own border box, body's border box plus margins, and body's `scrollHeight`. The root's `scrollHeight` is still consulted, but only when it genuinely *exceeds* the viewport — i.e. when it reports real overflow rather than the clamp — so the growth path is unchanged while shrinking now works. The `+16` is body's 8px margins, which do not collapse into `html` because `overflow-y:hidden` makes it a block formatting context — which is also why the root's own border box already includes them.

**Verified without a browser**, by simulating the frame/parent loop from its definitions: the old measure never reaches a fixed point and adds 6px per call; the new one settles in a single step, survives repeated tab switching, and honours the parent's 48px floor. The simulation also corrected two of my own predictions — I expected the old code to settle at a ratcheted value, and it does not settle at all.

**Standing rule:** a self-measuring element must never measure itself with a quantity the measurement itself determines. If the parent sizes us from `h`, then nothing that depends on our current size may appear in `h` — and for the root element, `scrollHeight` always does.

## D61 — `format=raw|clean|text`: the article, reduced for clients that are not our page — **ACCEPTED 2026-08-08 (user-directed)**
An article `Body` is the dictionary's own HTML, and wudict's page renders it with the dictionary's own CSS and scripts. A client that is **not** that page — a hover extension, a script, another front-end — wants neither and pays heavily for both. `/api/search` gains `format`; `raw` remains the default, so the desktop path is byte-for-byte what it was.

**There is no semantic tier, and there cannot be a generic one.** `dict.Result` is `{Headword, Body}`; wudict never parses senses, parts of speech or examples, because every dictionary's markup is its own — which is precisely why the UI renders articles unmodified. So the honest tiering is not semantic-vs-chrome but **structural-vs-verbatim**: `clean` (allowlisted structure, no scripts/styles/presentation, references absolutised) and `text` (no markup at all). Structured JSON was considered and dropped: it would need per-dictionary extraction rules, which is a research project, not a query parameter.

**Measured before claiming.** I had asserted a 3–5x reduction. On the real corpus (`q=speed`, nine heavy dictionaries, 748 KB of raw article) the first cut of `clean` managed **1.5x** — because stripping attributes leaves the tag skeleton standing. In one LDOCE entry, **3,237 of 3,796 elements are `<span>`**, and a classless `<span></span>` is 13 bytes of nothing: 42 KB of pure skeleton in a single article. Unwrapping elements whose attributes did not survive (`Policy.Bare`, `<span>` only — a bare `<div>` still opens a block) took `clean` to **1.9x** and LDOCE specifically from 63% of raw to 41%. `text` is 2.6x. The doc, the code comments and the kickoff note were all corrected from the number I had asserted to the number that was measured.

**A second walker, not more hooks on `Rewriter`.** The two have opposite contracts: `Rewrite` promises the ORIGINAL BYTES wherever a value did not change, because it edits articles rendered with the dictionary's own CSS where any drift is a visual bug; `Sanitize` promises that nothing survives that was not explicitly allowed, so it must re-serialise everything. A walker asked for both would keep neither. They share the package, and the WHATWG tokenizer — the part worth having exactly once.

**Allowlist, never denylist**, for both tags and attributes: an article is third-party HTML and the set of attributes that can carry behaviour is not enumerable in advance. Unknown elements are **unwrapped** rather than dropped, so a custom element can never silently swallow a definition. `Sanitize` also *discards* what the tokenizer cannot parse, the opposite of `Rewrite`'s rule — a sanitiser that passes through what it failed to parse is not a sanitiser.

**One rescue, and it earns its keep.** `<object>` is dropped as an embedding vector, but DSL spells pronunciation as `<object type="audio/x-wav" data="…">`, so dropping it would have silently removed audio from every DSL dictionary in the library. `Policy.Replace` rewrites it to a plain `<audio src="…" controls>` — the content survives in a form needing no plugin, no script, and no client knowledge of how DSL happens to spell it. Caught by a test, not by inspection: the first run of the endpoint test showed the pronunciation simply gone.

**Standing rule:** publish a ratio only after measuring it. Both numbers I asserted from reasoning (3–5x reduction, and the belief that attribute-stripping is where the bytes are) were wrong in the same direction — optimistic — and the corpus said so in one run.

## D62 — Two Android flavours: `foss` keeps All-files access, `play` imports through SAF — **ACCEPTED 2026-08-13 (user-directed)**
The shell asked for `MANAGE_EXTERNAL_STORAGE` and read `/storage/emulated/0/Dictionaries` as ordinary paths. That is correct for GitHub and F-Droid and is the one line that makes a Play listing unlikely to be approved: All-files access carries its own Console declaration with a closed list of eligible core functionalities (file manager, backup, antivirus, on-device document search), and a dictionary reader is on none of them. One source tree now builds two flavours on a `dist` dimension: `foss` is today's behaviour verbatim, `play` declares **no** storage permission at all.

**Two premise corrections, both from reading the tree.** `WRITE_EXTERNAL_STORAGE` was never the blocker — it is `maxSdkVersion="29"`, inert on every device Play polices, and Play's *restricted* set is SMS and Call Log, not storage. And **`content://` can never reach the Go program**: the server is exec'd as a plain POSIX child with no JVM and no Binder handle, so a URI only the Android runtime can resolve is not something Go code could be taught to open. The real choice was "copy bytes in from Java" or "pass file descriptors over a unix socket" — never "teach Go about SAF".

**Why copying in is cheap rather than wasteful.** Shared storage is touched by discovery, one ingest read, preview mode (D15), and the *lazy* resource fallback that opens the original only when `media.db` misses. With the D24 media switch on, a prepared dictionary never needs its source again, and `internal/store/clean.go` already treats a vanished source as *not* an orphan. The source is an **import-time input, not a runtime dependency** — so D52's "SAF copy-in doubles storage" objection only ever applied to copy-*and-keep*, and the importer offers to delete the originals through the same write grant, making it a move.

**The seam is one class, at one FQN, present only in the flavour source sets.** `com.legbehindneck.wudict.Storage` — `dictDirs` / `ensureAccess` / `handleShellUri` / `onActivityResult` / `onPageFinished` / `onNewIntent`. Not `BuildConfig.FLAVOR` branching: a copy in `src/main` would be a duplicate class, so the Play APK **cannot compile or even name** `MANAGE_EXTERNAL_STORAGE` — which is what automated review scans for. `MainActivity` and `ServerProcess` hold no flavour logic; the all-files dialog moved verbatim into `src/foss/Storage.java`. The in-page import trigger reuses the existing `openExternal` scheme interception (`wudict://import`) and injects its button from `onPageFinished` — **no `@JavascriptInterface`, no new HTTP endpoint, and no edit to `internal/server/web/*`.** The manifest split is additive union only; `tools:node="remove"` is never used.

**Both flavours now live in `getExternalFilesDir()`** — HOME, `wudict.toml` and the db dir — not `/data/data/…`. User-directed and correct: on an unrooted phone the private dir gives the user no way at all to reach their own config or library, and the panel's reveal button and the DB paths of D7 are worthless if the path cannot be opened. It costs nothing in permissions on any API level, sits on the larger volume, and is reachable over USB/MTP and adb. **Accepted cost: it is wiped on uninstall.** Existing installs are not moved — `AppDirs.resolveRoot` keeps the legacy internal root when `filesDir/db` already has content, so nobody's multi-GB library silently migrates; only the tiny TOML is copied across (different mounts, so `renameTo` cannot be used).

**Export is postponed indefinitely** (user-directed). It is the honest counterweight to the uninstall wipe and was step 9 of the plan; it is not being built now, and this is recorded so it is not mistaken for an oversight.

**`applicationId` stays `com.legbehindneck.wudict` in both.** Play App Signing and the GitHub keystore are different certificates, so the two builds cannot cross-update; accepted rather than fragmenting the id.

**Rejected, with reasons.** The **fd bridge** (SAF → `LocalSocket` SCM_RIGHTS → `ReadMsgUnix`) is mechanically real but needs an `io/fs`-shaped indirection threaded through `internal/dict`, five format packages and `internal/gomdict` — `mdict_base.go` alone re-opens `mdict.filePath` at six sites, and sibling resolution is *path arithmetic* in stardict and dsl — i.e. a userspace filesystem built to avoid one file copy, and a direct breach of D52's standing rule. Revisit only if `fs.FS` sources are wanted on desktop for their own sake. **MediaStore** gives nothing: an app reads only its own contributions by path. **Declaring All-files on Play and arguing** is a parallel gamble, never the plan. A `*/*` `ACTION_VIEW` filter was rejected too — it makes the app a spam entry in every open-with sheet; `ACTION_SEND`/`SEND_MULTIPLE` on the dictionary MIME types only.

**The importer mirrors the whole picked subtree**, not a filtered extension set, because every format is a multi-file bundle (`.mdx`+`.mdd`, StarDict `.ifo`/`.idx`/`.dict.dz`/`.syn`, DSL plus `_abrv` plus `res/`) and siblings are resolved by path arithmetic, so relative layout must survive the copy exactly. Non-optional robustness: `StatFs` precheck, `<name>.part` + rename so an interrupted run leaves nothing half-formed and a re-run resumes, `DISPLAY_NAME` sanitising with a canonical containment check, depth and entry caps, cancellable worker, per-file failures collected rather than fatal.

**Standing rule, restated: the Android port adds no Go code and no build tags.** The Play flavour adds packaging, Java and strings — nothing else. `tools/verify-apk.sh` asserts it mechanically in CI: the Play APK declares no `EXTERNAL_STORAGE` permission and keeps `INTERNET`, the FOSS APK still declares All-files, and **both** keep `extractNativeLibs=true` with arm64 native code, because a compressed lib is not a file and the server is exec'd from `nativeLibraryDir` (D52) — a packaging change is exactly what would break that silently.

**Amendment (2026-08-13, user-directed): every app-specific external volume is scanned, and the import control lives on both pages.** Two gaps in the shape above, found by asking what `/setup` does in Play mode. First, `dictDirs` named one folder, so a microSD card — `getExternalFilesDirs()[1]`, app-owned and permission-free like the primary — was unreachable except by typing its path into the setup page, on the one flavour where typing a path is nearly always futile. `AppDirs.dictRoots` now returns `Dictionaries` under every mounted, writable app-specific volume, deduplicated by **canonical** path because the primary volume answers to several names (`/sdcard`, `/storage/emulated/0`, `/storage/self/primary`) and a folder listed twice is a folder scanned twice. The first-run prompt is gated on all of them, so a card populated over USB is not greeted as an empty install. The card is read, never written: the importer's destination stays the primary, because a single destination is the only thing a cancel/resume can reason about. **Its limit is stated rather than engineered around** — `seedConfig` writes the folder list once, and the app passes no `--dict-dir`, so a card inserted *later* is not added behind the user's back; that would mean the shell parsing and rewriting the user's TOML in Java to re-implement what `/setup` already does.

Second, and the actual defect: `onPageFinished` anchored the import button on `#panel .panel-head .headacts`, which exists only in `index.html`. But a first run where the user taps "Later" lands on **`/setup`** (`handleIndex` falls back to it while the registry is empty), whose own only affordance is a free-text path box that in this flavour can name almost nothing the app may read — so the sole way back to the picker was relaunching the app. The injection now falls through to a worded button before `#save`. Both anchors are **static markup**: `setup.html` builds its folder rows only after `/api/config` answers, so anchoring on a row would be a race with no way to win.

**Deliberately not done:** making the Play flavour hide "+ add another folder" and freeze the seeded path row. Once the card is found automatically the manual route is no longer *needed*, but it remains the escape hatch for a volume that appeared after first launch, and rewriting the desktop page's copy and controls from the shell is a third layer of selector-coupling for a page the shell is supposed to know nothing about. A wrong path already reports "✕ none found" inline. **`Use this folder` was proposed for hiding and must not be**: `save()` is the single commit for the folder list *and* the `useCached` library toggle, so hiding it would make "Keep using them" write-only — and on Play the prepared library in `files/db` is precisely the state that survives an import-as-move.

## D63 — Removing a dictionary is a wudict operation where no file manager can be one — **ACCEPTED 2026-08-13 (user-directed)**
D7 answered "how does a user delete a dictionary?" with *the file manager does that*, and put a Reveal control on every path so the handoff costs one click. That is a **delegation with a precondition**: another custodian must exist and be reachable. Android falsifies it. `AppDirs.root()` puts the library — and, in the Play flavour, the imported dictionaries — under `/sdcard/Android/data/<pkg>/files`, which DocumentsUI filters out of the picker, which every third-party file manager has been locked out of since Android 11, and which `ACTION_OPEN_DOCUMENT_TREE` refuses to grant a tree in since API 30. The only operations the platform defines on those bytes are **uninstall** and **clear storage**, both of which take the whole library and the config with them. So the app is the only process on the device that can free one dictionary's space, and refusing to do it is not caution — it is leaving the user with a 40 GB folder and a wrecking ball.

**The gap was never Android-only, and was never a delete button.** wudict had no removal primitive at *any* layer: not in the API, not in the CLI (`clean` removes orphans, i.e. what the library should not contain), only the panel switches. What is added is the primitive — `DELETE /api/library` and `wudict rm` — while the *offer* is gated: `canDelete = !(isLoopback && revealPossible())`, the exact complement of Reveal. One rule, not an `if android` branch: the app offers to delete precisely where it cannot hand the user to something that would. On a desktop at the keyboard the endpoint 403s, the control is not rendered, and **D7 stands untouched**. The Android port still adds no Go code and no build tags (D52/D54); this is a core feature that happens to be platform-conditional, and the shell contributes one manifest attribute.

**Two objects, never conflated.** The *prepared folder* (`<db dir>/<name>/`, D20) is ours and unambiguous. The *original files* are a set, not a file — `.mdx`+`.mdd`+numbered parts, StarDict's `.ifo`/`.idx`/`.dict.dz`/`.syn` plus a shared `res/`, DSL's `_abrv` plus `.files.zip` — so the set comes from the new `dict.SourceFiles` (the per-format sibling table moved out of `internal/server`, where `companionMedia` had already encoded half of it) and is shown to the user before anything happens. The two shapes where a stem is not exclusive — StarDict's `res/` folder, shared by convention, and a hand-made same-stem collision — are why it is *shown* rather than trusted.

**The default is "remove everything", because preparation is automatic.** Deleting only the prepared folder of a dictionary whose source is still in a scanned folder frees space until the next search re-prepares it (`AUTO_INDEX`), so the cautious-looking option is the one that lies. "Index only" is still offered, and the report says what will happen. In the other direction, "originals only" is governed by **D24 §4** read backwards — the source is the safety net, so it may only be cut once the media that would vanish with it has been packed — and it is additionally refused while `USE_CACHED` is off, because the prepared folder would survive with nothing listing it (D19).

**Rejected: a trash tier / undo.** It reclaims zero bytes at the moment the user is deleting *because they are out of space*, and it puts a second copy in the one directory nothing else on the device can open. The safety comes from stating the file list and the byte count before acting, and from `store.RemovePrepared`'s single guard: the folder's parent must be the library root, `Lstat`'d so a symlink is refused rather than followed.

**Second door: `android:manageSpaceActivity`.** It replaces "Clear storage" in App Info with an app-owned activity — the one place a user goes when the phone says it is out of space. `ManageSpaceActivity` draws nothing and owns nothing: it launches `MainActivity` with an extra and finishes, and the shell clicks the page's own `#panelBtn`. A Java-drawn management screen would be a duplicate of the ☰ panel that could only drift from it.

**Amendment (2026-08-13, user-directed): `~` is a claim about the machine, so the server chooses the label.** D48 shortened every displayed path by replacing the home prefix with `~`, and `/api/config` shipped `home` for the page to strip. On Android that renders `~/Dictionaries/…` for a path where **no** shell exists to expand it, and where `HOME` is the app's external files dir — a directory the user cannot type anywhere, cannot reach with any file manager, and never sees under that name. It is a lie on both flavours (Play swallows the dictionary paths, FOSS still swallows `~/db/…`), and it is worse than a long path because it looks actionable.

`home` is replaced by `pathAliases` — `{prefix, label}` pairs, longest prefix first, applied blindly by the page (D54: the page must not learn what Android is). Desktop sends exactly one pair, `$HOME → ~`, so its rendering is byte-for-byte what D48 produced. Android sends the names the **Files app itself** uses for the volumes the shown paths actually live on — `Internal storage` for `/storage/emulated/0` and `/sdcard`, `SD card (<mount id>)` for any other `/storage/<id>`, `App storage` for `/data/user/<n>/<pkg>` — derived from those paths rather than fixed, so a device with no card is never told about one. `runtime.GOOS == "android"` is the test, tag-free and already how `make android-go` builds (the precedent `revealPossible` set in D63). Still display-only: `data-full`, the clipboard and `/api/reveal` keep the absolute path, which is what a script — or a file manager — needs. The app's own directory is deliberately **not** hidden behind a friendly name: `Internal storage/Android/data/<pkg>/files/…` is exactly what a user comparing the panel against the Files app sees, and D63 is the control that acts on it.

**Amendment (2026-08-14, user-directed): the import control is a worded row, not an icon.** The injected affordance on `index.html` was a `↥` glyph inserted into `#panel .panel-head .headacts`. That strip is *chrome* — theme, close — and a user scans that corner for "get me out of here", so the one function without which this app is empty was the least findable thing in it, while the only worded entry point sat on `/setup`, two taps away and reachable in practice only on a fresh install. The glyph is replaced by a full-width `📥 Import dictionaries…` button at the top of the panel.

It is inserted **before `.allrow`**, not after: that row's `border-bottom` is what divides the header from the dictionary list, and the master switch has to stay adjacent to the cards it governs. Styling is inline and expressed **only in the page's own custom properties** (`var(--link)`, `var(--sp-1/2)`), so the shell ships no palette that would have to be kept in step with the page's two themes. The anchor moved from `.headacts` to `.panel-head` but is still static markup, and the reason is unchanged and worth restating: `loadDicts` rebuilds the list and `loadFolders` clears `#folderBody`, so a control placed in either would disappear at the first refresh — which is worse than no control. The `/setup` fallback branch and the single `#shellImportBtn` id guard are untouched.

Rejected here: labelling the header icon in place (keeps it in the chrome strip and, at `width:min(420px,92vw)`, risks wrapping the header on a 320dp phone); putting it in the Folders `.facts` group beside *Edit folders* / *Rescan* (its semantic home, but inside a **collapsed** `<details>`, i.e. strictly less discoverable than what it replaces); and adaptive emphasis by dictionary count (state and page-reading in the layer that must stay dumb).

## D64 — On Android the scarce resource is the platform's patience, not the phone — **ACCEPTED 2026-08-14 (user-directed)**
The performance work recorded in `docs/PERF.md` (§6b, §6c) tuned this program for a desktop, where using the machine is what a program is *for*: every core is free to take, idle RAM is wasted RAM, and a periodic timer is beneath notice. Android inverts all three. Sustained CPU is a battery complaint and, past `THERMAL_STATUS_MODERATE`, a throttling event that makes the app slow in a way the user blames on the app. Resident memory above what the platform thinks reasonable is a kill by the low-memory daemon — and on many vendor builds a lasting entry in a battery-abuse list that no amount of later good behaviour undoes. A wakeup every twenty seconds in a process that outlives its window is a core brought out of idle, forever, to discover there is nothing to do.

So the same binary must behave differently, and the constraint from D52/D54 still binds: **no Go build tags, no Go code that only exists for the port, and the page never learns what Android is.** Three mechanisms, in the order they matter.

**1. The power state, because only the shell can see it.** The server was exec'd away from the JVM (D52), so it cannot observe `onStop`, `onTrimMemory`, thermal status or battery saver — those signals exist only in the Java shell. `POST /api/power?state=active|background|restricted` is the whole interface: loopback-only like every control that acts on the machine rather than the library (a remote page must not be able to put someone else's process to sleep), POST because a GET would be followed by every prefetcher on the network. `PowerBackground` drops GOMAXPROCS to 1, refuses to *start* an auto-index (deferring, never cancelling — `autoTried` is not consumed, so the next search once the user is back still builds it), and sheds every handle that can be rebuilt, waiving the idle grace because "recently used" says nothing about what is about to be used once the user has left. `PowerRestricted` additionally closes prepared databases, which hold no headword map — only descriptors and a page cache. A desktop never leaves `PowerActive`, which is why none of this is a platform branch. Java-side, `PowerSignal` coalesces (a state that is superseded while queued is abandoned), retries three times at 800 ms, and lets its thread exit after 30 s idle; battery and power-save are *sampled* at each transition rather than watched with broadcast receivers, since a receiver is itself a wakeup the app would not otherwise take.

**2. Defaults that differ, as defaults and not as policy.** Every one is an ordinary config key, so the layering holds and anyone who wants desktop numbers on a phone sets them (`internal/config/tuning.go`). `MaxProcs` = half the cores, 2–4: phone core counts describe a big.LITTLE arrangement, and saturating all of them is precisely what pulls in the big cores where the heat and the battery go. It drives both `GOMAXPROCS` and the search fan-out. `PREVIEW_MEMORY` 64 MB rather than 1 GB (~180k headwords of direct backends at the measured ~350 B each). Compression level 1 rather than 6 for ingest: compressing every article of a large dictionary is the longest sustained CPU burn this program performs, level 1 costs roughly a tenth of it on highly repetitive article markup for a database on the order of a tenth larger, and storage is the resource a phone has most of — read-side is unaffected, since DEFLATE decoding does not depend on the level a stream was written at, so libraries stay interchangeable between platforms. `Warm` (pre-opening prepared dictionaries at startup) is off: on a phone the process may be started and killed repeatedly, so work done in anticipation is work usually thrown away.

**3. Doing nothing when there is nothing to do.** The janitor blocks on a channel while `needsSweep()` is false instead of ticking every 20 s forever. `media.db` opens on the first resource request rather than with the dictionary, and a corrupt or foreign one is remembered as failed so it is not retried on every image in every article. Each prepared dictionary's `database/sql` pool keeps one idle connection with a 30 s TTL and a 1 MiB page cache on Android — a hundred dictionaries is a hundred pools, and each connection holds its own cache for the life of the process. Deliberately **not** `SetMaxOpenConns`: capping the pool would make any path that holds a `*sql.Rows` open while issuing a second query on the same handle deadlock rather than merely queue. `FreeOSMemory` after a shed is coalesced through `scheduleReclaim` (2 s), because shedding a hundred dictionaries at once used to mean a hundred stop-the-world scavenges back to back — a CPU spike indistinguishable, from the platform's point of view, from the runaway work this whole mechanism exists to prevent.

**4. Being seen to release what we release.** Measured on device, shedding a 464k-headword preview backend emptied the Go heap (93.9 MB → 0.7 MB in the same code path on the desktop) while `VmRSS` sat unchanged at 184 MB across three search/background cycles, `FreeOSMemory` included. The cause is in the runtime, not here: `runtime1.go:parseRuntimeDebugVars` defaults `madvdontneed = 1` only when `GOOS == "linux"`, so an `android` build keeps `MADV_FREE` and every page the scavenger returns stays charged to the process until the kernel is short of memory. On a desktop that is the better default and the reason it exists. On Android the number *is* the outcome — the low-memory daemon, the vendor RAM watchdogs and the user's battery screen all read RSS/PSS — so memory released but still charged is memory not released, and the whole shedding mechanism above would have been invisible to every party that acts on it. The shell passes `GODEBUG=madvdontneed=1` to the exec'd child (`ServerProcess.java`, the one place that constructs its environment); the same measurement then reads 119.5 MB → 19.9 MB. The cost is a page fault per page on reuse, which is the cheap side of this trade. This is Java and environment, not Go code — the D52 rule holds.

**`SetMemoryLimit` was required to prove it does not make things worse, and the measurement changed the answer.** A soft limit has exactly one lever — collect harder — so set below the live set it means collecting continuously to free nothing: maximum CPU and maximum heat, which is the opposite of the goal. `TestMemoryLimitSweep` (env-gated, never in `make check`) runs each limit in a fresh child process, because the limit is process-global and a heap carries its history. Against the real corpus — 130 dictionaries, every one in preview mode, `PREVIEW_MEMORY` 64 MB, 60 fan-out queries, 18 cores, Go 1.26.5:

| limit | wall | GC share of CPU | cycles | live at end | preview held (open) | peak RSS |
|---|---|---|---|---|---|---|
| none | 140 s | 16.6 % | 26 | 5697 MB | 6333 MB (106) | 7180 MB |
| 96 MB | 1036 s | 44.0 % | 6290 | 1650 MB | 0 MB (0) | 6253 MB |
| 128 MB | 1069 s | 43.7 % | 6809 | 1083 MB | 395 MB (1) | 5730 MB |
| 192 MB | 1052 s | 44.0 % | 6502 | 2288 MB | 395 MB (1) | 5725 MB |
| 256 MB | 1144 s | 46.0 % | 6556 | 637 MB | 0 MB (0) | 5359 MB |
| 384 MB | 1239 s | 44.9 % | 7239 | 662 MB | 37 MB (1) | 5263 MB |
| 512 MB | 1210 s | 44.9 % | 6836 | 2950 MB | 0 MB (0) | 5286 MB |

**There is no knee.** Every ceiling from 96 MB to 512 MB behaves identically: GC pinned at 44–46 % of CPU — just under the runtime's own 50 % limiter, which is what is actually holding the number down — and wall time 7.4–8.8× the baseline, with no trend in the limit. The sweep's own thresholds fail all six rows. Two things fall out of this, and neither was visible in the code.

First, **the pressure path works and is not sufficient**. Shedding really did drop 106 open backends to zero or one, and it is why peak RSS falls from 7.2 GB to ~5.3 GB. But what remains is not cache: it is the working set of the fan-out itself, and at 512 MB the runtime still could not get in-use below 3.8 GB. A ceiling below what the process genuinely holds is not *approximately* right — it converts the program into a collector, and no amount of shedding underneath it changes that.

Second, **the preview budget is not enforced during a fan-out**: 64 MB was configured and 6333 MB was held, because `minEvictIdle` (45 s) protects every backend while a `dict=all` search keeps touching all of them, so the budget only ever binds between bursts. That is the documented intent (a reopen costs 0.2–1.1 s), and against a 130-dictionary library it means the budget is not a bound at all. This is a **desktop** finding; it is recorded here because it is what makes the live set in the table what it is, and it is not fixed by this ADR.

**So the ceiling is kept, and made corrigible.** The measurement disqualifies the obvious reading of D64's first draft — pick a good number — because no number is good for a workload chosen by the user: a *single* unprepared dictionary in this corpus holds a 395 MB headword index, larger than the entire ceiling a phone is given, so the pathological state is reachable on a phone by opening one big dictionary before it is prepared. `adjustLimit` therefore runs at the end of every janitor pass: after `relaxAfterPasses` (3) consecutive passes that began under pressure — by which point everything sheddable has been shed several times over and it did not help — the limit is raised to the measured footprint plus 25 %, and it is restored the moment the footprint falls clear of the configured value (strictly clear: `pressureRatio` of it, or restoring would re-create the state it is leaving). `needsSweep` had to stop returning false when nothing is reclaimable, because that is exactly the state in which the correction left is to the ceiling rather than to the memory. Three passes rather than one, so a transient spike never permanently raises the ceiling; and raising it converges rather than oscillates, since the relaxed ceiling is above the footprint and the restore condition is below it.

**Verified on a phone, where two things had to be corrected.** On a OnePlus PKG110 (Android 16, 8 cores, 11.5 GB) carrying 61 unprepared dictionaries, eight `dict=all` queries took the process to 4.9 GB resident and drove the ceiling up five times in a minute — the relax valve doing exactly its job, and the platform's own thermal status putting the app into `restricted` 25 s in, from heat our own fan-out produced. First correction, in the runtime rather than here: `GOOS=android` never gets `MADV_DONTNEED` (see §4 above), so everything shed stayed charged to the process. Second, in this mechanism: a raised ceiling was **never handed back**, because `restoreMemoryLimit` only runs inside a janitor pass and the janitor blocks when there is nothing to reclaim and no pressure — which is precisely the state after a relax, since the pressure test is taken against the raised ceiling. One heavy search bought a 6 GB ceiling for the life of the process. `needsSweep()` now stays true while `limitRelaxed()`, and the restore arms a reclaim. Re-measured: 4032 MB → 173 MB within 60 s of backgrounding, the configured 384 MB restored one janitor period later, and 10 ms of CPU over the next three minutes. The rule underneath the fix: **a mechanism that suspends a guarantee must keep something awake to resume it** — an idle janitor is only correct while its guarantees are in force.

**Confirmed on the device that has no headroom, where a third correction fell out.** A Xiaomi MI PAD 4 (Android 11, 6 cores, 3.8 GB) carrying 24 unprepared dictionaries reached **1.71 GB** on four queries — 45 % of the machine — and recovered to 110 MB with the ceiling restored, so §8.5's fix holds across two Android generations. What that device made visible is that the recovery is not the problem and the *work* is: the web UI aborts its fetch on every keystroke, and three fetches abandoned at 4 s still cost 90 s each and 1.0 GB, because `search.StreamOpen` consulted the context only while a worker waited for a semaphore slot — never after it was admitted, so with a free slot the `select` had two ready cases and half of a cancelled queue proceeded to open a dictionary for a client that had hung up. It now re-checks after the slot and after the open (14 of 24 opened, on an abort at 1 s, where all 24 opened before). The residual is honest and belongs to the *next* decision, not this one: an open in flight cannot be interrupted, and one 2.88M-headword MDX is 6–11 s and hundreds of megabytes on its own, so cancellation bounds a dead fan-out to the opens already running — bounding the rest needs a cap on how many backends one fan-out may materialise (PERF §8.2, §8.7). The rule this adds: **work that outlives its requester is the cheapest waste to find and the most expensive to leave**, because on a phone it is paid twice, in the CPU that computed it and the RAM that holds it.

That trade is deliberate and worth stating plainly: **being killed by the low-memory daemon is a better outcome than 45 % of CPU indefinitely.** A kill is one event the platform already handles — the shell restarts the server and `adoptRunningServer` finds it — while sustained GC is battery, heat, thermal throttling *and*, in the end, a kill anyway.

The rule, rather than the number: **a memory ceiling is only safe above the live set the workload actually holds, and since that is not knowable in advance it must be able to yield.** It is set on Android — where the alternative to a ceiling is being killed for a heap nobody was watching — and left unset on the desktop, where the machine's own memory manager is better at this than a number we would guess. The Android value is a fraction of physical RAM, floored at 192 MB and capped at 384 MB, and it bounds the **Go heap only**; the WebView's memory, typically the larger half of the app, is not ours to bound. This closes `docs/PERF.md` §7 question 4, and answers it "yes, with a release valve".

Rejected: a persisted **discovery cache** to skip the startup tree walk — detecting that the cache is stale requires the walk it exists to avoid, so it trades a bounded cost for an unbounded correctness risk (a dictionary added over MTP would be invisible). **Build tags** for any of the above — they would fork the binary that D53 already builds two flavours of, and every value here is a default a config key can override. **JNI or a Binder handle** so the Go side could read the platform signals itself — that is the fd-bridge argument of D62 in another costume, and the shell reporting three words over loopback costs nothing.

## D65 — A search gets a memory budget, and spends it or declines — **ACCEPTED 2026-08-14 (user-directed)**

`SEARCH_MEMORY` caps how much preview memory **one** query may newly materialise. Default **0 (uncapped)** on the desktop, `memoryLimitDefault()` on Android — the same 192–384 MB the ceiling is set to. `Registry.fanout()` mints one budget per `/api/search`; `entry.openWithin(f)` charges it. A dictionary already open costs nothing and is never declined. A dictionary whose last open is remembered (`entry.lastWeight`, kept across eviction, unlike `weight`, which must go to zero when the backend is dropped because the sweep totals it) is priced *before* it is opened, and refused if it does not fit — with `tooHeavy`, whose text names the size and says how to make it free: prepare it. A dictionary never opened has no price, so it is admitted and charged what it turns out to weigh; that charge is what closes the fan-out to everything behind it. `admit` is a CAS loop that declines an oversized entry **without consuming the remainder**, so one 395 MB dictionary early in the user's order cannot starve the cheap ones behind it, and `settle` corrects the reservation to the measured weight (returning it in full when the open fails).

**This is a bounded revival of S1, which D-105 rejected.** S1 was "skip unprepared dictionaries in search"; S2 (bounded preview memory) was chosen over it *because it keeps results complete*, and that reasoning has not gone stale — it is why the cap is off by default on the desktop, why the refusal is never silent, and why a prepared dictionary is never declined (it holds no headword index, so declining it drops results and reclaims nothing). What changed is the evidence: PERF §8.2 shows the preview budget does not bind during a fan-out at all — 64 MB configured, 6333 MB held — because `minEvictIdle` protects every backend a `dict=all` search keeps touching, and §8.4/§8.6 show what that costs a phone: 4.9 GB on an 11.5 GB device, **1.71 GB on a 3.8 GB one, 45 % of the machine for one keystroke**. Result completeness is worth paying for on a desktop and is not worth being killed for on a phone. The two budgets are complementary, not redundant: `PREVIEW_MEMORY` bounds what stays resident *between* searches; this bounds what a single search may *create*, which is the quantity the janitor is structurally unable to reach.

**The refusal is a result, not an omission.** The declined dictionary occupies its slot in the stream, so the page shows something where it would otherwise show nothing. A silently missing slot would make the cap dishonest: the user would read "no results in this dictionary" where the truth is "not looked".

**Amended 2026-08-16 (P74) — deferred, not declined.** As first shipped the slot carried `Error` set to `tooHeavy`'s text — "not searched: ~31 MB unprepared, over this search's memory budget — prepare it to search it for free" — and that was wrong three times over. It is our vocabulary, not the user's; it names a remedy the UI does not offer (preparation is silent and automatic by D20/D15, and no "prepare" verb exists anywhere in the interface); and, the actual defect, **the refusal blocked its own remedy**. `handleSearch` fires `maybeAutoIndex` only after a *successful* open and `openWithin` refuses *before* opening, so a declined dictionary was never opened, therefore never auto-indexed, therefore never prepared, therefore weighed the same next time — and admission runs in the user's preference order, so it was deterministically the same tail of the library, every query, forever. The cap did not defer those dictionaries; it removed them, and told the user to fix it with a control that does not exist.

The rule this establishes: **automatic while it is cheap, on demand once it is not.** A dictionary that fits the budget is opened and auto-indexed exactly as before, and since prepared ⇒ `previewWeight` 0, each one that lands frees budget for the next — the library converges on its own. A dictionary that does not fit is deliberately *not* queued for indexing: the fan-out cap **is** the RAM/CPU ceiling past which indexing stops being automatic, already measured and already tuned, so no new limit and no new config key is introduced. What lifts it is the user's tap. The slot now streams `deferred:true` with `bytes` and an **empty** `error`; the client renders a normal collapsed section, named, in preference order, reading *tap to search*, and opening it re-queries that dictionary alone. **A search naming exactly one dictionary is uncapped by construction** (`fan = nil` when `len(entries) == 1`): the budget bounds fan-out — N dictionaries materialised at once by one query — and one dictionary has no fan-out, its cost is bounded by itself, while `PREVIEW_MEMORY`, the janitor and the relax valve still bound the steady state. Refusing it, by contrast, leaves that dictionary unreachable through every path the app has. That one change makes the tap work and incidentally fixes `more…` and the dropdown-scoped searches, which are equally direct demands. The same open also promotes that dictionary's headword index from the background queue to the `frontLimit` lane (`entry.demandIndex`, CAS-once because a search runs on every keystroke), so one tap ends the deferral permanently rather than per query. No "prepare" button was added: that would re-create precisely what D31 removed with "index all" — a control named after our mechanism instead of the user's outcome. The tap is the affordance.

Two limits stated rather than hidden. **The first search of a cold library cannot be capped by cost**, because a fan-out is parallel: every opener reads "unknown" before any has settled a charge. Pricing needs one payment, and afterwards the cap binds. **An open in flight is still uninterruptible** (D64's residual), so the bound is the budget plus whatever was admitted before it ran out — `search.Workers()` (2–4 on Android) caps that overshoot at a handful of dictionaries rather than a hundred. The weight model over-charges a warm MDX by ~1.7× (§8.3), so the real peak sits comfortably under the budget; that is the correct direction to be wrong in here.

Rejected: **reference-counting backends** so the janitor could evict during a fan-out — it fixes the symptom in §8.2 by making eviction safe mid-search, but it does not stop the memory being *created*, which is the only thing a phone is measuring, and it puts a refcount on the hot path of every lookup. **Making `PREVIEW_MEMORY` bind harder** (shorter `minEvictIdle`, or sweeping on the request path) — D-105 measured that: a reopen costs 0.2–1.1 s, and evicting what the running fan-out is about to reuse converts a memory problem into a latency-and-CPU problem, which on a phone is the same problem. **A build tag or an Android-only code path** — the mechanism is platform-neutral and the platform difference is one default, exactly as D64 requires. **Measured, with a control.** MI PAD 4, 24 unprepared dictionaries, the same binary run twice minutes apart with `SEARCH_MEMORY=0` and with the Android default (233 MB): four cold `dict=all` queries fell from 212 s wall / 438 s CPU / 1.30 GB peak to **61 s / 123 s / 1.02 GB**, per-query latency from 99·49·39·25 s to 56·1·1·1 s, and the 961 MB dictionary that the control opened three times was declined by every query after the one that priced it. **CPU, not RAM, is what the cap buys** — −72 %, which on a phone is battery and heat — and the peak moved only 22 %, because the budget is per query and a resident dictionary is free, so a burst inside `minEvictIdle` still stacks. That is the correct division of labour and is now stated where it can be checked (PERF §8.8): this bounds what one request *creates*, `PREVIEW_MEMORY` and the janitor bound what stays. The cold-library cost is real too — 56 s of the capped run is the first query learning 24 prices — and the fix for it is to persist `lastWeight`, which is a later decision, not this one. The rule: **a budget that can only be enforced between requests is not a budget for what a request does** — bound the creation, not the residue.

## D66 — One word, one file: the import's vocabulary — **ACCEPTED 2026-08-16 (user-directed)**

The Play import (D62) copies a picked SAF tree into `Android/data/<pkg>/files/Dictionaries/<folder>` and then asked *"Imported N files. Remove the originals from the folder you picked?"* — **Remove originals** / **Keep them**. The question is unanswerable, and not because of that sentence alone: the app was using one word for two different files. The card-level delete (D63) called the file it removes "the original files", and on this flavour that file is itself the copy the importer made, while the import dialog's "originals" are the user's own files on shared storage. A user who has just been told the app copied everything cannot tell which of the two a dialog means, and guessing wrong either destroys their collection or leaves it stored twice. The rule: **the imported copy is "the dictionary files" everywhere; the user's own files are named by their folder, in quotes, and never called "sources" or "originals" unqualified.**

Three consequences. **The offer states the folder and the saving**: *"WuWeiDict now keeps its own copy, so the files in “Language” on your device are no longer needed — deleting them frees 4.2 GB."* The gigabytes are not decoration — a copy is exactly what a user watching their storage objects to, and the only useful thing we can tell them is how to get it back. When the provider reports no sizes the size clause is dropped rather than printed as `0 KB`, and when it will not name the folder the phrase falls back to "the folder you picked". **KEEP takes the affirmative slot**, inverting the shipped dialog: the destructive answer must not be where a reflex tap lands, since keeping costs one folder the user can delete whenever they like and a mistaken delete costs the collection. **Progress says "Importing N of M", not "Copying"** — copying is our mechanism and reads as the app helping itself to the disk, importing is what the user asked for. The single exception is the consent screen (`import_message`), which must keep saying that a copy is made and space is spent, because that is the screen where the user agrees to it.

Rejected: **deleting the picked folder silently** once the copy exists (the request that opened this). There are no temporary copies to clean up — the copy *is* the permanent library, the only bytes the exec'd server can read (D62) — so the files a silent delete would remove are the user's own, from a decision they never saw. The share-target route can hand us a provider's cache instead, and that route already offers no delete at all (`deletable = false`). The one thing that *is* deleted without asking is our own `<name>.part`: a kill mid-copy strands it forever, discovery ignores it, and the user can only see it as unexplained app storage, so `sweepPartials` clears the destination at the start of every import. Also fixed alongside, both being disk-space claims the user reads and neither of them true: the free-space precheck summed the whole batch including files already imported, so re-importing a folder to pick up one new dictionary could refuse itself for bytes it was never going to write; and sizes printed as raw MB, so a real collection announced itself as "12800 MB".

## D67 — Looking a word up is something the SHELL offers other apps — **ACCEPTED 2026-08-16 (user-directed)**

A dictionary on a phone is used from inside something else: a reader, a browser, a message. Until now WuWeiDict declared `MAIN/LAUNCHER` and nothing else, so the normal act — hit a word, see what it means, carry on reading — meant leaving the app you were reading, switching, and retyping the word. Three intent filters fix that, all on one `LookupActivity`: `ACTION_PROCESS_TEXT` (the selection toolbar, where the app's row entry reads **Look up**, via a per-filter `android:label` that overrides the activity label for that filter only), `ACTION_SEND text/plain` (the share sheet, for apps that suppress the toolbar and for passages), and `ACTION_VIEW` on `wudict://lookup?q=…` (other apps and automation — Tasker, Termux, a note app's link). They differ only in where the string comes from; everything after that is identical.

**The contract with the page is `?q=`, and there is no other.** `applyURL()` in `web/index.html` already reads `q`, `mode`, `dict` and `from`, fills the box and searches, so the whole feature is *load `http://127.0.0.1:6888/?q=<word>` in a WebView*: no Go change, no page change, no new endpoint, no new permission — D54 intact, the pages still do not know Android exists. `mode` is whitelisted to the four the `#mode` selector offers and `dict` is length-capped; a caller's query string is never pasted onto our origin, it is re-encoded from parsed parts. The selection itself is treated as hostile input, because it is: `PROCESS_TEXT` hands over whatever was highlighted, so the text is bounded at 4096 chars before it is normalised at all, whitespace-collapsed, cut to 256 on a code-point boundary, and an empty result gets a toast and `finish()` rather than a blank window floating over someone else's app.

Three structural consequences, and they are the actual work. **The child server stops belonging to `MainActivity`.** It was a `private static ServerProcess` there, started in `onCreate`, read back as "non-null means ready" — untrue the moment a second activity can ask at the same time, and useless to a popup launched while `MainActivity` is dead. It moves into `ServerProcess` as `IDLE/STARTING/READY/FAILED` with a waiting list, behind `ensure()`: a start in flight is joined, not duplicated, and `adoptRunningServer()` stays as the outer guard. **A popup closing never stops the server** (user's decision): `retain()`/`release(mayStop)` counts live windows, `MainActivity` passes `isFinishing()` and the popup always passes false, so the child dies only when the app itself is finished with no popup alive — the popup instead drops to `background` through `PowerSignal`, the Go side sheds caches and threads, and the next lookup from any app is instant rather than a cold start. **D64's "one place decides the power state" needed a second window to exist**, so `applyPower` moves verbatim into `Power` with a visible-window *count* in place of the `visible` boolean; with only `MainActivity` running the computed state is what it always was. `Shell` and `Ime` are extractions in the same spirit: origin, URL building, WebView settings, the external-link policy and the hide-IME-on-scroll rule are now written once and used by both windows.

Rejected. **The overlay bubble** — a floating result that follows you around — needs `SYSTEM_ALERT_WINDOW` plus a foreground service with its permanent notification: a permission Play treats as a special access, a persistent process on the platform whose patience is the scarce resource (D64), and all of it to save a window that Back already dismisses. **An AccessibilityService to capture selections** would grant WuWeiDict the ability to read every screen the user sees, to spare them one tap on a toolbar they are already looking at; no dictionary should ask for that, and the store review that asks *why* would be right to. **A Quick Settings tile and a clipboard-launcher shortcut** were dropped by request as duplicate doors. **Morphology for inflected selections** is deliberately absent: a selection is passed as typed and `mode` stays the page's default, so "running" behaves exactly as it does when typed by hand — stemming remains unscheduled in `docs/OPEN.md` rather than half-introduced through a side door.

## D68 — `clean` and `text` read the dictionary's own stylesheet — **ACCEPTED 2026-08-16 (user-directed)**

The extension popup rendered LDOCE's *destination* as one unbroken run of text with the entry's internal field codes spliced into it — `1 TTTRAVELthe place that someone…`. The reported cause (a cleanup regex eating whitespace) is not the cause: `htmlref.Sanitize` writes text tokens with `z.Raw()`, verbatim, and no regex touches article text anywhere. The source has no whitespace to eat. That article is 3796 elements, 3237 of them `<span>`, and **every** boundary in it is a `display:block` in `ldoce.css` — `.Sense`, `.GramExa`, `.EXAMPLE`, `.Collocate` — while `TT` and `TRAVEL` are `<span class="FIELD">`/`<span class="ACTIV">`, one of which is `display:none`. D61's `clean` strips classes and the `<link>`, so it deletes the only layout the markup has and un-hides what the dictionary hid. `text` had both defects for the same reason. This is not an LDOCE quirk: a dictionary's semantics live in its class names by construction, in every format we read.

**So `clean` and `text` parse that dictionary's CSS, once, into a flat `class → display` table.** Not a cascade, not a DOM, not a style engine: `htmlref.ParseCSS` walks the declarations and records the rightmost compound of each selector, folded across every stylesheet the entry links (capped at 4 sheets, 2 MB, 20000 classes, 8 levels of at-rule nesting). `Sanitize` gains one hook — `Policy.Elem`, consulted per start tag *after* the tag policy and never for an element it already dropped, so no stylesheet can talk a `<script>` back into the output — which drops a hidden class with its subtree and renames a block class to `<div>`; `Text` grows the same two rules, a skip depth and a block stack.

**The precedence ordering is the whole safety argument** for a table with no cascade: `Unset < None < Inline < Block`, merged by max, so where two rules disagree block beats inline (a spurious line break is benign; the missing one *is* the bug) and anything visible beats `none` (never hide on ambiguous evidence). A multi-class compound (`.collo.COLLOC`) contributes a boundary to each class but **never** a hide, because the table cannot record "only when both are present". Selectors whose applicability depends on state, attributes or identity — `:hover`, `[data-k]`, `#hw`, escaped names — are refused outright rather than approximated. `inherit`/`initial`/`unset` say nothing without a DOM and are dropped. A truncated file keeps its last rule, as a browser does.

**In memory, on the registry `entry`, never on disk.** It is derived data with the invalidation problem that implies; rebuilding it costs about what reading it back would; and D20 fixes the library folder at `{text.db, media.db, info.txt}`. Its lifetime is the open backend's — `entry.drop()` and `entry.reopen()` forget it — and `styleMu` is always taken before `dMu`, since derivation holds it across `open()`. Cost, estimated and unmeasured: ~1–3 ms and 10–25 KB once per dictionary, ~0.15–0.25 ms on the heaviest article (5–15 % of the clean path). **`raw` never derives it at all**, so the desktop default and the Android shell — which use `raw` — pay nothing.

Rejected: **keeping `class` and letting the client link the stylesheet** (the honest alternative). It renders better, but it inverts `clean`'s contract, which is markup a client that knows nothing about dictionaries can render — an extension popup, a clipboard, an LLM — and it makes every consumer fetch and host third-party CSS. **A real CSS engine**: the cascade needs the DOM, the DOM needs the article, and the table exists precisely so the answer can be computed once per dictionary instead of once per element. **Per-format layout heuristics** (guess that `.Sense` is a sense): the dictionary already states it, in its own file, unambiguously.

## D69 — The extension asks for no host, and hands the page no loopback URL — **ACCEPTED 2026-08-17 (user-directed)**

Hovering a word on `www.google.com` made the browser ask *"www.google.com is asking you to access other apps and services on this device"*. That is Local Network Access (Chrome/Edge 142+, Firefox 151+) and the browser named the right origin: the extension's own fetches run on an extension origin and are exempt, but `sanitize.js` wrote `http://127.0.0.1:6888/res/…` into `img`/`audio`/`source` and `popup.js` built its `new Audio()` in the page's `window` — so those subresource loads were *the page's* requests, and the page is what the prompt names. A dictionary extension that makes google.com ask permission to touch your machine is indistinguishable, to the person reading the prompt, from one that is doing exactly what they fear. There is no FAQ entry that beats not triggering it.

Two changes, and they are one decision because each pays for the other. **Media is proxied through the background worker** — `fetchMedia` validates the URL's origin against the configured base, caps the bytes, requires an `image/*` or `audio/*` content type and returns base64; the content script mints a `blob:` URL, and the popup's speaker button plays through an **offscreen document** (Chrome, `reasons:['AUDIO_PLAYBACK']`) or the background event page (Firefox), so click-to-play audio never enters the page at all. No loopback URL is handed to the page anywhere, so no page ever becomes an LNA client. **And the `host_permissions` entry for `http://127.0.0.1:6888/*` is removed**, which deletes the other half of the fright — the install prompt that said "read your data on 127.0.0.1" — leaving an extension whose declared reach is the pages it renders into.

That removal takes the CORS bypass with it, so **wudict answers CORS itself, for browser-extension origins, on the read-only client API only**: `GET /api/dicts`, `GET /api/search`, `GET /res/`. Not prefs, config, library, ingest, rescan, reveal or power — an extension may read dictionaries and can do nothing to the installation. The header may be trusted because `Origin` is set by the browser and cannot be forged by page script, and no web page is ever served from `chrome-extension://` or `moz-extension://`; what it cannot tell us on Firefox is *which* extension, since `moz-extension://<uuid>` is regenerated per installation. Hence the grant is by scheme, with `BROWSER_EXTENSIONS` to pin exact origins where that is wanted. `extensionOrigin` accepts a scheme and a host and nothing else — the id alphabet (`[A-Za-z0-9-]`, ≤128) is what rejects a path, port, query, fragment or userinfo without parsing any of them. Always `Vary: Origin`, never `*`, never `null`, never `Access-Control-Allow-Credentials` — there are no cookies, and enabling it would make a future one reachable cross-origin. `OPTIONS` handlers exist on the same three routes although today's requests are CORS-simple and never preflight, because `ServeMux` would answer a future preflight with a 405 that explains nothing.

The residual, stated rather than hidden: with `BROWSER_EXTENSIONS` unset, **any** installed extension can read your dictionaries. That is a widening, and it is bounded — it is read-only, it is the same reach any extension could take for itself by declaring the host permission, and one config line closes it. Weighed against a permission prompt that every user sees on every page, on a server that binds to loopback by default, the trade is the right way round.

Rejected. **Native messaging** (what `hover-trans-port` does): immune by construction, no HTTP and no host permission at all, and cheaper for us than for them — the binary is already local, so `wudict browser-host` would replace their 32 KB of installer scripting. It is still a second transport, a per-browser host manifest, an install step the web store cannot perform, and chunking around a 1 MB message cap. The right endgame if the LNA rules ever tighten around extension origins; not the price of this fix. **An extension-origin iframe for the popup** — it would additionally beat a strict host-page `img-src`/`media-src` CSP, which can still block our `blob:` media (no worse than today, where it blocked the loopback URL); deferred as a UI rewrite rather than a permission fix. **`Access-Control-Allow-Origin: *`** — it grants the same read to every website, which is precisely the thing LNA exists to prevent. **Keeping the host permission and explaining the prompt in the docs**: the prompt appears on the user's bank's page, not in our documentation.
