# Decision log (ADR-lite)

Status: PROPOSED (awaiting user), ACCEPTED, REJECTED, SUPERSEDED. One line of context each; details in SPEC.md.

## D1 — Source handling: dual-backend — **ACCEPTED 2026-07-24 (user-directed)**
Default = **direct readers** over native format indexes (exact/prefix lookup, zero import step). **Ingest is opt-in** via config `ingest = off|text|full` (global default + per-dictionary override) and unlocks fuzzy/FTS. DSL auto-ingests text transparently (no native index). Supersedes the earlier hybrid-ingest-only proposal.
- Consequence: format packages implement both a runtime `Lookuper` and a sequential `Reader` (ingest scan) — parsing written once, two entry points.
- Known risk accepted: Slob direct lookup uses in-memory refs + Go collation instead of ICU; huge slobs may need a sidecar key cache later.

## D2 — Resource storage — **ACCEPTED 2026-07-24 (user-directed)**
`ingest=off|text`: resources lazy from source (MDD/res/res.zip/.files.zip/slob bins). `ingest=full`: resources packed into a **separate** `<slug>.media.db` (never mixed into the text DB) so text DBs stay small and exchangeable. Pairing via shared `dict_uuid`; runtime resolution order media.db → source → 404; text.db alone degrades gracefully.

## D3 — Server model: persistent HTTP server — **ACCEPTED 2026-07-24**
mdict-go-web style (config layering, auto-open browser). CGI dropped: kills pooling, in-memory direct-backend indexes, SSE progress. CGI shim possible later.

## D4 — SQLite driver: mattn/go-sqlite3 — **ACCEPTED 2026-07-24, AMENDED 2026-07-25**
cgo driver, build with `-tags sqlite_fts5` (as draego does), for native/dev builds. Amendment (P7): release cross-builds use `-tags purego` → `modernc.org/sqlite` (pure Go, FTS5 included) so the GitHub workflow builds every target on one ubuntu runner with CGO_ENABLED=0 — no C toolchains. Both drivers pass the same test suite (`make test-purego`).

## D5 — UX wording for ingestion: "Enable fuzzy & full-text search" — **ACCEPTED 2026-07-24**
Per-dict/all action; progress "Preparing search index…"; full-ingest variant "…and pack media". Ingest is a feature upgrade, not onboarding — adding a dictionary = dropping files in the dict dir.

## D7 — Location of generated .db files: cache dir only — **ACCEPTED 2026-07-24**
`~/.wudict/db/` — dict dirs stay pristine, works on read-only sources. Since DBs are exchange artifacts, the UI must expose them ("Reveal in Finder" / show path per dictionary) so users can find and share them despite the hidden location.

## D12 — Open strategy & streaming search — **ACCEPTED 2026-07-25 (user-directed, P8)**
Opening a dictionary (heavy in-memory index) is the real latency, not searching. Three rules: (1) **cheap probe** — `dict.Probe` reads header-only metadata (name/entry-count) so `/api/dicts` and cache-location never build the full index; formats without a prober fall back to full Open (guarded by `HasProber` to stay off concurrent/auto-ingest paths). (2) **lazy source** — an ingested dict opens only its `.text.db`; the direct backend is opened solely on a resource-fallback miss (the embedded Store serves its auto-attached media.db first), so ingesting a dict now *lowers* its open cost instead of doubling it. (3) **background warm** — `Registry.Warm()` pre-opens all dicts bounded off the request path.
- `/api/search` streams **NDJSON** (`begin`/`hit`/`end`); `hit` carries a preference slot index so the client renders progressively and honors a user-defined dictionary order. The `dict` param accepts an ordered, enabled-only id list (panel drag/chevron order + enable toggles, persisted client-side). Dropdown stays alphabetical (name lookup) — distinct task from result ranking.

## D13 — Auto-index on first search — **ACCEPTED 2026-07-25 (user-directed)**, values renamed 2026-07-28
Indexing is no longer an explicit action. `AUTO_INDEX = on|off` (default **on**, opt-out). The values were `fuzzy|off` until D16 retired the word "fuzzy" for a search mode that no longer existed; `fuzzy` is still accepted as a synonym for `on`, so an existing config.toml keeps working. Since D24 what it builds is the ~2 MB find index only — never the heavier contains/full-text indexes, and it never strips or rebuilds what a user has chosen. The first time a dictionary is searched, the server builds its **headwords-level** index in the background (`entry.maybeAutoIndex`, `sync.Once`, guarded by `Caps.Fuzzy` so already-indexed/DSL/wudict dicts no-op) — cost follows usage, no first-run indexing storm (`Warm` still only *opens*). Full-text stays opt-in (large/expensive). Failures (read-only cache, no reader) are swallowed silently. UI fallout: panel drops "Fuzzy only"; "Enable fuzzy & full-text search" → **"full-text search"**, "Full + pack media" → **"FTS + pack media"**; a fuzzy search on a not-yet-built dict shows "preparing fuzzy index…" (ready on the next query) while full-text keeps its explicit "enable full-text search" link. Builds on D12 (cheap open makes the extra index free at query time).

## D9 — Split-DB naming: `<slug>.text.db` + `<slug>.media.db` — **ACCEPTED 2026-07-24**
Slug = human-readable dictionary name (filesystem-safe). Self-describing for manual transfer/exchange; loader pairs by `dict_uuid`, not by name.

## D19 — The library is private; using it is a remembered choice — **ACCEPTED 2026-07-27 (user-directed)**
Reverses D17. The db dir is wudict's **library** — its own working area — and is **never a discovery root by default**. Four parts:
1. **Precise registration.** `store` registers the bundle main file `text.db` (exact name) and the loose `.text.db` suffix — never bare `.db`, which made an internal sidecar a public dictionary type: a `media.db` carries the same `user_version` and `meta` table as a text.db (for uuid pairing), so it opened as a phantom `wudict:slob` dictionary. Exact-name matching also avoids a `text.db` *suffix* swallowing an unrelated `context.db`.
2. **Hard guard + exclusion.** `DICT_DIR == DB_DIR` is a startup error (canonical paths, symlinks resolved); independently, `dict.ExcludeDir` makes discovery skip the library subtree wherever it sits — which also covers a db dir nested inside the dictionary folder, a case the equality check alone would miss.
3. **Consent (`USE_CACHED`, default off).** The library is listed only when the user opts in. This makes `reg.Count()==0` a *correct* first-run signal again with no special-casing: opted out + empty dictionary folder ⇒ empty registry ⇒ setup page appears. Dedup when opted in is by **source path** (a prepared dictionary is hidden only when its source is among the discovered files), so a dictionary whose source lives outside the current dictionary folder is still offered instead of silently vanishing.
4. **Enriched setup page — one page, one act** (harmonized 2026-07-27). The page presents two *sources* of one library (folders, and previously imported dictionaries), so it commits **once**: a single primary button at the foot, plus a way back. The former second button ("Use these dictionaries", sitting under the library list) was not merely redundant — it posted without the `path` params, **silently discarding any folders typed above it**. Folded into the one Save, whose label names the deed (folders → "Use this folder"/"Use these folders"; library alone → "Use these dictionaries") and which enables when *either* source is chosen. The escape hatch is **"Back to dictionaries"**, not "Cancel" (nothing is pending to abandon — no change applies until Save) and not "Close" (this is a page at its own URL, not a modal over content); and it is an `<a href="/">` styled as a button, not a `<button>` assigning `location.href`, so ⌘/middle-click, the context menu, the status bar and the "link" role all work. The keep-checkbox moved down beside the list it governs, and one line states the whole outcome: `✓ 55 dictionaries in 2 folders + 82 previously imported`. The "keep my N previously imported dictionaries" checkbox defaults to **CHECKED** when the library is non-empty (amended 2026-07-27): those dictionaries exist because the user prepared them, checking only makes otherwise-invisible ones reachable and is reversible, while leaving it off silently hides working dictionaries whose data sits on disk. It also mirrors the real setting once one exists, and now sends its state **both ways** (`useCached=0` turns the library off) — before, it was write-only-true, so clearing it could not undo an earlier yes. Note the box only governs prepared dictionaries this folder does *not* account for: one whose source is in the chosen folder keeps working with its indexes either way, via `PreparedFor`. Below the folder chooser it lists "Previously imported dictionaries" (name · format · entries · index/media badges) with **Use these dictionaries**, plus an "also keep my N previously imported dictionaries" checkbox on the folder flow — three outcomes: folder only, library only, both. Clicking a Use button *is* the "don't ask again": it persists `USE_CACHED=1` via `config.SaveKey`, and the setup page only ever appears while nothing is in use. Listing the library (`GET /api/library`) never enrolls it.

Rejected alternative (the elegant-but-lossy "Option A"): drop the library scan entirely and require users to copy prepared dictionaries into their dictionary folder. Refused because it forces **data duplication** — the app would refuse to use data it already has. Consent achieves the same separation of concerns without making the user pay twice for the same dictionary.

## D20 — Library layout: one folder per dictionary + `info.txt` receipt — **ACCEPTED 2026-07-27 (user-directed)**
The flat `<slug>-<hash8>.text.db` / `.media.db` naming is replaced by `<db dir>/<source file name>/{text.db, media.db, info.txt}` — e.g. `AHD5-2017/`. A dictionary is now **one folder**: copy, move, zip or hand it over as a unit, and drop it into a dictionary folder to use it elsewhere (discovery recognizes the bundle by its `text.db`). Details:
- **Naming** mirrors the source *file* (extension dropped; `.dsl.dz` drops both), spaces and case preserved, only path-illegal characters replaced. Collisions between same-named sources take a format tag — `AHD5-2017` and `AHD5-2017 (mdx)` — never a hash.
- **Allocation is a claim**: `ClaimDir` uses `os.Mkdir` (atomic) and immediately writes the `source` line, so two concurrent first-time ingests of same-named sources cannot take the same folder. Read paths call `LookupDir`, which never creates anything — browsing dictionaries can't litter the library. Ownership is always verified, so a same-named dictionary in another format can never be served from the wrong folder.
- **Registry layers, one source of truth**: folder names are the inventory (`ls` is the listing); each `text.db` meta is authoritative for content. `info.txt` is a *derived receipt*, regenerated after every ingest and media pack, carrying exactly one fact of its own — `source`, the claimed path. That claim is the **ownership record**, deliberately outranking meta's `source_path`, which is only what a format reader chose to report (real readers report relative or empty paths). No library-wide manifest: that would be a real second source of truth.
- **Staleness moves into the meta.** The content hash used to live in the file name; now `SourceChanged` compares recorded size/mtime, re-hashing the first 1 MiB only when those differ, and a changed source is re-indexed **in place**. Consequences: a touched-but-unchanged file no longer re-indexes, stale `-oldhash` files no longer accumulate, and "superseded ingest" disappears as an orphan category. `clean` now reports incomplete/unreadable folders, interrupted ingest temps, and pre-folder flat leftovers — never a healthy prepared dictionary, whatever became of its source.
- **Adoption, not migration** (user-directed, revised 2026-07-27). The first cut treated pre-folder flat files as disposable (`clean` fodder) — but a real library contained exactly those, so the library listed nothing and the user was asked to re-prepare data the app already had, i.e. the data duplication D19 exists to avoid. `store.AdoptLoose` now runs at server startup and **renames** `<slug>-<hash8>.text.db` (+ its `.media.db`) into `<name>/{text.db, media.db, info.txt}` — no re-indexing, nothing deleted, folder chosen so adopting and re-preparing converge on the same place. A loose file is left untouched only when that dictionary already has a prepared folder; that (a genuine duplicate) is the sole remaining "superseded" orphan class. Still no *schema* migration: the databases themselves are unchanged.

## D21 — DICT_DIR takes several folders — **ACCEPTED 2026-07-27 (user-directed)**
One dictionary root was a needless limit (external drives, shared folders, a second collection). Syntax per layer, chosen so each looks native where it is written: **repeatable flag** (`--dict-dir A --dict-dir B` — nothing to escape, identical on every platform), **`os.PathListSeparator` in the environment** (`:`, `;` on Windows — it is a path list, so it follows the `$PATH` convention; a comma would be novel and `:` on Windows collides with drive letters), **TOML array** `DICT_DIR = ["a", "b"]` with the scalar form still valid, so nothing breaks and no migration is needed. Semantics — the part that actually matters:
- **Order ranks nothing.** Result ranking already belongs to the panel (D12, drag/chevrons, persisted). Root order decides exactly one thing: which folder wins a tie.
- **Two levels of dedup.** Folders: `dict.DedupeDirs` collapses one folder listed twice however it is spelled — a repeat, a trailing separator, a symlink, a case variant on a case-insensitive filesystem — using `os.SameFile` where both paths exist (string comparison sees none of those) and canonical strings for paths that do not (an unmounted drive must still be kept, and still deduped). First spelling and order win. Applied at `NewRegistry`/`SetDirs`, so every source funnels through it, and again when the setup page saves, so duplicates never reach `config.toml`. Nested folders are NOT duplicates: they are different directories whose overlap is reported per root. Dictionaries: dedup by canonical path (`EvalSymlinks`). Overlapping roots are normal once several are allowed (`~/Dicts` plus `~/Dicts/Spanish`, a symlinked shortcut); without it the same dictionary gets two registry ids — two panel rows and doubled hits in every all-dictionaries search. `DiscoverAll` reports per root both what it contributed (`New`) and what it holds (`Total`), so an overlapped folder reads "1 dictionary, already listed above" instead of the lie "no dictionaries found".
- **A missing folder is a warning, never fatal** — an unmounted drive must not take the other folders down. Reported per folder at startup and per row on the setup page.
- **The `DICT_DIR == DB_DIR` guard applies to every folder**; nesting is still covered by `dict.ExcludeDir`. The **library stays single** (D19/D20 depend on one place for prepared dictionaries) — the asymmetry is deliberate: many sources, one library.
- Wherever the CLI takes a folder (`list`, `ingest`, `searchall`) it now takes a list too, in either spelling.
Fixed in passing: `filepath.WalkDir` lstats its root, so a **symlinked dictionary folder silently yielded nothing**; `Discover` now resolves the root it is given (links *inside* the tree are still not followed, which keeps cycles and surprise duplicates out).

## D22 — Folders are visible and editable from the app — **ACCEPTED 2026-07-27 (user-directed)**
Where dictionaries are read from, where prepared ones live, and which `config.toml` is in effect were visible only in the startup block on stderr — a terminal the user may never see, since the app opens a browser for them. The setup page knew all of it but was reachable only while the registry was empty. Fixed with three pieces, no new mental model:
1. **`/setup` is permanent**, pre-filled with the folders in use and offering Cancel once dictionaries are being served. It is the folder *editor*, not just the first-run chooser.
2. **A settings disclosure in the panel** — moved to the top (2026-07-27): one line directly under the master switch, above the first card, showing a cog and the counts (`3 folders · 112 dictionaries`) with **no visible label**, per show-don't-tell; the name survives as `title`/`aria-label` for tooltips and screen readers. At the foot of a 55-card list it was undiscoverable; at the top it costs one line and doubles as the panel's scope. The cog is an **inline SVG**, not ⚙️: emoji renders as a colour blob on macOS and flat on Windows, sits on its own baseline, and cannot inherit `currentColor`. Originally described as a foot-of-panel disclosure (`GET /api/config`): each dictionary folder with its own count/status, the library with prepared/in-use counts, the config file — all click-to-copy, with **Edit folders…** linking to `/setup`.
3. **Value origins.** `config.Load` records which layer set each key (`flag`/`env`/`file`/`default`). When a flag or environment variable outranks the file, both the panel and the editor say so: *"set by the --dict-dir flag — it overrides the config file"*. Without this the UI would happily save a folder list that silently does nothing next launch; a settings screen that lies is worse than none.
**Rescan moved out of the panel header into that section** (user-directed): it re-walks every folder and re-opens every dictionary, far too expensive to sit beside the close button as a curiosity click.
**Reveal in the file manager** uses each platform's own established wording — *Reveal in Finder* (macOS), *Show in File Explorer* (Windows), *Open Containing Folder* (Linux) — with the matching command (`open -R`, `explorer /select,`, `xdg-open` on the containing folder, since selection is not portable there). Two guards, both deliberate: the path must be one the app already displays (a dictionary folder or below, the library or below, or the config file — never an arbitrary path handed to the shell), and the request must come from **loopback**, since revealing opens a window on the machine running the server, not the one browsing it.
Deliberately NOT built: an editor for launch-time settings (port, IP, speex backend). Those cannot be applied live, so offering edit fields would invent a "restart required" mode this app does not have.

## D23 — A second launch hands over instead of failing — **ACCEPTED 2026-07-27 (user-directed)**
Launching wudict while it is already running now opens the **running** instance in the browser and exits 0, behind a deliberately loud ASCII banner saying the new launch did nothing. This is the desktop single-instance activation pattern (a second double-click activates the running app; Windows apps forward the command line and focus the window) translated for an app whose window IS a browser tab.
- **Identity first.** A port can be held by anything, so we `GET /api/config` with a 700ms timeout and require the `Server: wudict/<version>` header (added for this purpose, on every response). Anything else — a foreign server, no answer, a timeout — keeps the original "port in use" error and opens nothing. Sending a user's browser to an unknown local service on the strength of a port number would be worse than an error.
- **Loud, because the launch is a lie otherwise.** The banner states that the options just passed were NOT applied, prints what the running instance is actually serving, and — when the requested folders differ from the running ones — says so explicitly. Silently opening an old instance is exactly how someone spends ten minutes wondering why their new `--dict-dir` did nothing.
- **Bind before working.** The listener is now claimed *before* adopting library folders, scanning dictionaries or auto-preparing indexes. Binding last meant a duplicate launch printed a full startup summary and built a search index before discovering it had nothing to do.
- `--no-browser` is honoured (banner only), and the handoff exits **0**: the user's intent ("open wudict") was satisfied. Scripts that relied on a non-zero exit for "could not start" see 0 in this one case.
**Rejected: an HTTP `/exit` endpoint to kill the running instance** (user's option B). Any web page could fire `GET http://127.0.0.1:6888/exit` with an `<img>` tag — no CORS, no user action — so a random site could kill the app; it would also discard work in flight (a long ingest), might not be the user's instance to kill on a shared machine, and races `TIME_WAIT` on rebind. If takeover is ever wanted, the safe mechanism is a PID lockfile plus `SIGTERM` behind an explicit `--replace` flag: a signal requires the same OS user and cannot be sent by a web page.

## D24 — Cheap by default, enriched by one click — **ACCEPTED 2026-07-28 (user-directed)**
A prepared dictionary could take several times the disk of the file it came from. Measured on a 40k-entry dictionary (45.6 MB source, 5.1 MB gzipped): the "headwords only" database was **72.4 MB**, of which **69.1 MB (95%) was article text** — every search index together came to 2 MB. So the disk problem was never the indexes.
1. **Article bodies are DEFLATE-compressed per row** (measured 3.8x smaller; the test corpus is random word soup and therefore pessimistic — real dictionary HTML compresses further). Per row rather than in shared blocks so a row stays independently readable without a block cache; skipped for bodies under 120 bytes and whenever it fails to win. Discrimination is a one-byte NUL sentinel — article text never starts with NUL — so **mixed rows are legal**: databases written before this keep opening, with no migration and no schema-version bump. `NO_COMPRESS=1` / `--no-compress` restores verbatim storage for those with disk to spare.
2. **The trigram ("contains") index is opt-in per dictionary.** It is only 3% of yesterday's database, but ~100% of a compressed, bodyless index — it costs as much as everything else put together, and serves a mode most people never use. `store.Plan{FullText, Contains}` replaces the single Level; the default plan builds neither trigram nor anything else optional.
3. **Finding a headword has no switch.** exact and prefix (accent-insensitive) work on every backend and cost ~2 MB, so they are not features to enable — which is why their badges were removed: a badge lit on every row for every dictionary is decoration. The panel now shows the three things that cost real disk (**contains · full-text · media**) as switches with their measured sizes, one click to add, one to remove.
4. **Stripping is offered only while the source file exists.** That is what makes it reversible — and it removes the need for confirmation prompts entirely: a dictionary whose source is gone carries the only copy of its own text, so its switches are locked with an explanation rather than made dangerous. Rule: *the source is the safety net; without it, nothing can be stripped.*
**Formats that prepare themselves are not an exception** (fixed 2026-07-28): DSL and BGL have no native index, so their text.db must exist and must hold the article text — but *indexing that text for full-text search* was still automatic for them, the last place where a heavy index was imposed rather than chosen. They now prepare with the same cheap plan as everyone else (first open of the measured dictionary: 29.5 MB → **17.2 MB**), and full-text is a switch for them like any other format.
Net on the measured dictionary: default preparation went from **84.0 MB (1.84x the source) to 29.5 MB (0.65x)** — 17.2 MB for a format that prepares itself, with contains and full-text no longer paid for by people who never use them. Auto-indexing (D13) now builds only the ~2 MB find index and never strips or rebuilds what a user has chosen.

## D25 — Background work must not take the machine — **ACCEPTED 2026-07-28 (user-directed)**
Measured (docs/PERF.md): a single "all dictionaries" search over a 100-dictionary library started **one ingest goroutine per dictionary** — no bound anywhere — producing 18 GB RSS and 1000 %+ CPU. Four fixes:
- **F1 Bounded indexing.** All background preparation flows through one limiter, `INDEX_WORKERS`, **default 1**: preparing a dictionary saturates a core and holds ~300–500 B per headword, and a background convenience must never take the machine from the person using it. `"auto"`/`0` = every core; the value is clamped to `[1, NumCPU]`. Work the user explicitly asked for gets a separate single slot, so a click never queues behind a long background job (worst case INDEX_WORKERS+1). Measured: 424 % → 154 % CPU.
- **F2 Release what is superseded.** After a dictionary is prepared, its direct backend — the thing holding the per-headword map — is closed after a 10 s grace (in-flight reads finish) and the pages handed back with `FreeOSMemory`. `Registry.Warm` no longer opens *unprepared* dictionaries at all: opening one builds that map, and doing it for a whole library was several GB for dictionaries nobody had searched. Measured: 474 MB → 172 MB resident after the storm.
- **F3 One copy, not two.** Preparing no longer calls `e.open()` for a display name while `OpenReader` parses the same file again; the name comes from a header-only probe. The largest object in the process is no longer duplicated for the duration of an ingest.
- **F4 Optional ceiling.** `MEMORY_LIMIT` (e.g. `"4GB"`) sets Go's soft heap limit; unset means none. With F1 in place the peak is close to the live set anyway, so this is a safety net rather than a necessity.
- **S2 Bounded preview memory** (user-directed, same day). An all-dictionaries search still materialised every *unprepared* dictionary's headword map (~6 GB transient). `PREVIEW_MEMORY` (default **1 GB**) now caps what unprepared dictionaries may hold open, weighed at `EntryCount × 350 B`; a janitor evicts least-recently-used backends every 20 s, **never** touching one used in the last 45 s and **never** running on the request path — a search fanning out over a hundred dictionaries would otherwise evict what it is about to reuse, and each reopen costs 0.2–1.1 s. Prepared dictionaries weigh zero and are never evicted (nothing to reclaim); the predicate is "answers from a prepared database", which also catches DSL/BGL embedding a `*store.Store` directly. `entry.open` moved from `sync.Once` to double-checked locking so an evicted backend can be reopened. Chosen over S1 (skipping unprepared dictionaries in search) because it keeps results complete. Extended the same day to `upgraded.src` — the source handle a prepared dictionary opens when a resource misses `media.db`. It holds the same per-headword cost, so it is weighed, timestamped on each resource fetch and released by the same janitor; the sweep ranks both kinds on one LRU (`reclaimable{used, bytes, free}`). Releasing it is invisible: text still comes from SQLite and the next resource request reopens the handle.

## D26 — MDict sub-entries: inlined, not searched — **ACCEPTED 2026-07-29 (user-directed)**
Repacked MDict dictionaries store an article's expandable sections as ordinary headwords with an `@` prefix — LDOCE6 No-Voice ships **95,162 of them against 65,382 real words**, so 59 % of its "entries" are `@collocations_woman`, `@examples_woman`, `@entrymenu_woman`. Two consequences, handled separately:
1. **A link to one is not navigation.** `entry://@examples_woman` used to go through `lookupWord`, replacing the article being read with a fragment of itself (and `lookupWord`'s trailing-digit strip turned `@wordfamilies_0654` into `@wordfamilies_`). Such a link now **inlines** the section next to the link that asked for it, with a close control; a second click removes it. Nothing touches the search box, the URL or history — this is expansion *within* an article, not a move between articles. Script-bearing articles render in the sandboxed iframe, which is same-origin, so `frame.js` fetches the fragment itself (`/api/search?mode=exact`) and inserts it where the article's own stylesheet and `toggle()` are already loaded — the fragment's own ►/▼ accordions work with no extra plumbing. Shadow-DOM articles get the same handler in `index.html`. The fragment's duplicate `<link rel=stylesheet>` is stripped on insert.
2. **They are hidden from browsing.** `@`-prefixed headwords are excluded from prefix, contains, full-text, the accent-fold fallback and the headword listing — but remain reachable by **exact** lookup, which is exactly what the inlining needs. A bare `"@"` (the symbol as a headword) is not hidden. The filter lives in the SQL, so limits apply to visible rows and **existing prepared databases behave correctly with no re-index**; new ingests additionally record `sub_entries` and report `entry_count` as words only (an already-prepared dictionary keeps its old inflated count until re-indexed — cosmetic, self-healing).
Measured before/after on the real dictionary: a prefix search for "collocations" returned `@collocations_000, @collocations_1, @collocations_12…` via the fold fallback; it now returns nothing.

## D14 — Resource URLs: root-only, root-absolute `/res/…` — **ACCEPTED 2026-07-25 (user-directed)**
**Reverses** the earlier relative-URL convention. wudict is served at the site root; `RewriteEntryHTML`, client `resURL`, and the srcdoc bridge all emit **root-absolute** `/res/{dictID}/…`. Reason: articles render in three contexts (main page, Shadow-DOM, **srcdoc iframe**) and a *relative* ref resolves against each context's differing base URL — third-party dictionary scripts inside srcdoc re-resolve against the wrong base, producing the `res/{d}/res/{d}/…` doubling 404 (hit twice: OED `OED4.js`, AHD5 `wavs/*`). Absolute `/res/` is context-insensitive: same origin URL everywhere, trivial `startsWith("/res/")` idempotency, one rewriter. Trade-off: implicit reverse-proxy **subpath** mounting is dropped; if ever required it returns deliberately via injected `<base href>` + a server-known prefix, not implicit relative URLs. Related: resource Content-Type is now taken from an authoritative `webMIME` extension map at serve time (Go's `mime.TypeByExtension` returns `text/plain` for `.css`/`.js` on some platforms → browsers reject stylesheets/scripts under strict MIME checking).

## D29 — FTS5 is mandatory, so the tag-less build must be the safe one — **ACCEPTED 2026-08-02 (user-directed)**

## D30 — Startup readiness is an explicit phase, and `/api/dicts` streams — **ACCEPTED 2026-08-02 (user-reported)**
On a slow machine, or a fast one with ~100 dictionaries, the first launch showed `Loading dictionaries…`, then **`⚠ All dictionaries are disabled — enable some in the ☰ panel`**, then — minutes later — normal search. The warning was false and actively misleading: it sent the user to a panel that would list their dictionaries perfectly intact.

Three defects compounded. (1) `doSearch` used one emptiness test, `!enabledOrderedIds().length`, for two unrelated conditions — "the user disabled everything" and "the list has not arrived". (2) The search form was live from first paint (`autofocus` + a submit handler bound at parse time) while `loadDicts()` was still in flight, so an eager query reached that branch with `dicts === []`. (3) `/api/dicts` was all-or-nothing — fan out, `wg.Wait()`, one array — so the vulnerable window lasted as long as the **sum** of every dictionary's metadata resolution, not the slowest one. The warning then *persisted*, because `loadDicts`'s cleanup was `finally{if(!lastQuery)setStatus("")}` and the premature search had already set `lastQuery`.

**`/api/dicts` now streams NDJSON** (`begin`+`total` → one `dict` per row in completion order → `end`), which is what D12 already did for `/api/search` and for the same stated reason: time-to-first-byte must be one open, never the sum of all of them. `total` comes from the registry with no opens at all, so the client knows how many are coming before any of them resolve.

**The client has a named readiness phase** — `boot` (0 rows: search controls `disabled` **in the markup**, so there is no window between first paint and script execution; indeterminate spinner; rotating Cook Ding 庖丁解牛 waiting messages) → `partial` (≥1 row: fully interactive, per the requirement that search unlocks on the **first** available dictionary) → `ready` → `failed` (stream error, or no `begin` within 20 s: interactive anyway, with a retry — a hung server must never leave the form permanently inert).

**The gate is now phase-derived, not count-derived.** "All disabled" requires a *settled, non-empty* list: mid-stream the rows that happen to have arrived may all be disabled while dozens still coming are not, so before `ready` the same branch reads as loading and re-runs itself when the stream completes. `handleIndex` serves `/setup` when the registry is empty, so on this page an empty list can only ever mean "not ready yet". Supporting fixes: `setStatus` takes an owner token so a long-running writer retracts only its own message; the panel header says "Still loading…" rather than "No dictionaries"; `renderPanel` repaints are debounced (it rebuilds its whole list, and would otherwise run once per arriving row).

**Deliberately indeterminate, with a factual counter.** Per-dictionary cost spans orders of magnitude (cold MDX ~180 ms, cold SLOB ~1 s), so a progress *bar* would be guessing; `N of M ready` cannot be. The counter removes the uncertainty that causes the panic, the messages handle the mood, and none of them claims imminence.

**Standing rule:** never let one predicate carry two meanings. If a test is reachable in a state its message does not describe, the state — not the message — is what is missing.

## D31 — Bulk full-text is an offer in the drawer, not a call to action in the header — **ACCEPTED 2026-08-02 (user-reported)**
The panel header carried a **`⚡ index all`** button. Two independent faults, one psychological and one factual.

**Factual: the name was untrue.** Every dictionary is indexed by headword automatically on preparation (`AUTO_INDEX`, D20/D24) — "index all" therefore described work already done, and its real semantics were *"build the full-text index inside article bodies for every dictionary"*, the one index that costs gigabytes of disk and a long single-file CPU pass. Naming our mechanism instead of the user's outcome made the label a lie.

**Psychological: prominence signalled the opposite of the truth.** Top-right of a sticky header is prime real estate reserved, by every convention the user brings with them, for the primary action. A lightning bolt plus "all" reads as *complete your setup* — so an optional extra was dressed as a repair for a product that is already fully functional. Curiosity alone guarantees clicks, and the cost is asymmetric: the click is instant and free, the consequence is minutes-to-hours of CPU and unbounded disk. **Prominence must track value to the user, not cost to the machine.**

Reworked to three rules. (1) **Name the outcome**: "Full-text search for all…", with the ellipsis signalling that a confirmation follows rather than an immediate act. (2) **Site it by value**: it moves into the "Folders & configuration" drawer as quiet muted text beside "Rescan folders" — deliberate, findable, not encountered. **Standing rule:** a control's visual weight is a claim about how much the user wants it. Never spend prominence on an action whose cost the user cannot see, and never let a control's label describe our implementation when the user is deciding about their disk.

## D32 — `wudict.toml`, created only in `~/.wudict`, portable only when declared — **ACCEPTED 2026-08-02 (user-directed)**
The config file was `config.toml`, searched in `<exe-dir>` → `~/.wudict` → `/etc/wudict` → `./`, and generated **next to the executable if that directory was writable**, falling back to `~/.wudict`.

**The writability probe was answering a question it cannot answer.** It was read as *"this directory is ours"*. It is not: `go install` lands in `~/go/bin` and Homebrew (Apple Silicon) in `/opt/homebrew/bin` — both user-writable, both **shared bin directories**, and both the most likely install paths. The exe-adjacent pattern is sound — but only under a precondition it never checked: *the application owns its directory*. Guessing harder (matching `/opt`, `/usr`, …) was considered and rejected: a denylist is incomplete by construction and would still have missed `~/go/bin`, `~/.local/bin` and Scoop.

**The rule is inverted, and now complete.** Nothing is inferred: wudict writes exactly one path, `~/.wudict/wudict.toml`, beside the library it already owns. **Portable mode is declared by the user** placing a `wudict.toml` next to the binary — it then wins the search and receives the saves, and the creation path is never reached. One `if`, no platform branches, no probe.

The old name is the most generic filename in existence, and the bare `./config.toml` candidate turned that into a live defect: running wudict from a Rust or Hugo checkout parsed a stranger's file, `EnsureConfigFile` then saw "a config exists" and declined to create ours, and `cfg.Source` — which is `Server.ConfigPath` — pointed `SaveKey` at it, so the setup page would **write `DICT_DIR` into someone else's file**. **The resolution is announced on every start, not just the first.** A config file in the wrong place is otherwise invisible, which is the whole reason this went unnoticed. `printStartup` already listed the dictionary folders and the library; the config line now always names a real path (previously the first run — the one that created the file — reported `(none — built-in defaults)`, because `EnsureConfigFile`'s result never reached `cfg.Source`), marks portable mode, and **lists every shadowed lower-priority file it ignored**. Two binaries with two config files is the classic "I edited it and nothing changed", and naming the loser costs four lines.

## D33 — Enabled set and order live on the server (`state.json`), not in localStorage — **ACCEPTED 2026-08-02 (user-directed)**
Which dictionaries are searched, and in what order, were kept in `localStorage` under `wudict_order` / `wudict_disabled`.

**localStorage is keyed by origin**, and the origin includes the port. Changing `SERVER_PORT`, reaching the same server as `127.0.0.1` instead of `localhost`, opening it from a phone on the LAN, or clearing site data each hands the user a blank slate. Curating a hundred dictionaries and losing it to a port change is not a preference that survived; it is a preference that was never stored. The **server owns the dictionaries** — it is the only party that can answer "which of them do I search" consistently for every client, and the only one that can *act* on the answer.

Acting on it is the second reason, and the one that made this a bug rather than a preference. `Registry.Warm()` pre-opens every prepared dictionary; it had no way to know any of them were disabled, so **turning a dictionary off bought the user nothing** — the SQLite handle was opened anyway. A switch whose only effect is on the client's request parameters is a decoration. `Warm` now skips disabled entries, which is why `Prefs` is a **constructor option** (`WithPrefs`) and not a setter: `NewRegistry` starts the warm-up, and a warm-up told what to skip after the fact has already spent the memory.

**The line is "does this describe the collection, or the browser looking at it?"** Theme, wide mode and the last dictionary picked in the dropdown stay in `localStorage` — they *should* differ between a laptop and a phone. The enabled set and the order move to one collection-level `state.json`, placed **beside the `wudict.toml` in effect** rather than at a hardcoded path, so a portable install (D32) carries state and config together and `--config` re-points both. It is deliberately not inside the library folders: D20 defines those as individually transferable units, and "which dictionaries are enabled" is a fact about the set, not about any member.

**Identity is repaired, not assumed.** Ids are `sha256(path)[:12]`, so renaming a folder changes every id at once. Records store `{id, path, name}` and are re-attached down a ladder of decreasing strength — id → absolute path → *unique* file name — where each rung may only claim an entry no stronger rung took, and the file-name rung requires uniqueness on **both** sides (without that guard every library entry, all of them named `text.db`, would swap identities with each other). The repair is written back, so a later save cannot resurrect the stale id as a duplicate. `name` is stored for a readable file and never used to match: it is a display string, and matching on it would be fake precision.

**Nothing is deleted on the client's word.** The client can only speak for dictionaries it can see, so a save retains records it did not mention, appended in their stored order — an unmounted drive must not cost the user the settings for everything on it. Symmetrically, the client refuses to save at all if its initial read failed: "nothing is disabled, no order" would be our ignorance overwriting their configuration. A first run reports `exists: false`, which is the client's one-time cue to adopt (and then erase) an older build's `localStorage` rather than starting the user over.

Unauthenticated LAN writes are not a new exposure: `/api/setup` already lets any client on the interface rewrite `DICT_DIR` in the config file, and this is strictly less powerful.

**Standing rule:** state belongs wherever the thing it describes lives. Per-device *look* is the browser's; per-collection *meaning* is the server's — and a switch the server cannot see is a switch that does nothing.

## D34 — `Fold` is versioned; a stale index is marked, not disabled — **ACCEPTED 2026-08-02**
`dict.Fold` is called in two places with different lifetimes: at query time on what the user typed, and at ingest time on every headword, where the result is **persisted**. Nothing recorded which version of `Fold` produced a stored index, so **any future edit to `Fold` would silently desynchronise every prepared dictionary** — add `ß`→`ss` and a query folds to `strasse` while an index built last month still holds `straße`. No error, no warning, and invisible to every test, because tests ingest fresh data with the same `Fold` they query with. The failure mode is a search that quietly stops finding words it used to find. This was a live defect independent of any morphology or normalization work (O2/O3 in `docs/OPEN.md`).

**The audit corrected the scope.** `Fold`'s output reaches disk in exactly **one** place: `ingest.go:198`, the trigram index behind *contains*. Three things that looked folded are not — `entry_fts` stores raw `w`/`txt` and folds with SQLite's own `unicode61 remove_diacritics 2` tokenizer; `idx_entry_w` is a raw `COLLATE NOCASE` index; and the direct backends rebuild their fold indexes on every open. So a `Fold` change invalidates one index, on dictionaries that opted into one mode — not the whole library. Knowing that is what made the response proportionate.

**Absent means 1, not 0.** Every database ever written carries no `fold_version` key and was, necessarily, built by the folding in force when the key was introduced. Defaulting a missing key to 0 would have declared every existing library stale on the day this shipped — a feature whose first act is a false alarm teaches users to ignore it.

**A stale index is marked, not disabled, and never auto-rebuilt.** Both of the obvious stronger responses are wrong. *Disabling contains* overreacts: a folding change alters one narrow class of characters, so a stale index is still exactly correct for every dictionary containing none of them — withdrawing the mode from a Spanish dictionary because Japanese dakuten handling changed is absurd, and for a source-less dictionary it would be an unrepairable loss where a partly-correct index was available. *Auto-rebuilding* is worse: a version bump makes every contains-enabled dictionary stale at once, which is precisely the first-run indexing storm `docs/PERF.md` M2 warns about. The proportionate response to "possibly inaccurate for some characters" is to say so and offer the repair.

**The repair reuses the switch that is already there.** A stale chip stays *on*, gains a dotted border and a `⟳`, and its click sends `contains=1` — the feature it already has — which `setFeatures` reads as "rebuild this". No new endpoint, no new confirmation, no third chip state to explain: asking for something you already have is an unambiguous request to make it true again, and it is the same atomic temp+rename rebuild as any other index change.

No logging was added in `store`: it is a library that returns diagnostics rather than printing them (D13). The `logx.V` line lives in `setFeatures`, where it reports the *action*, not the state.

**Standing rule:** any function whose output is written to disk owns a version constant, bumped in the same commit as the behaviour. The alternative is not "we will remember" — it is a silent, undetectable divergence between what was indexed and what is queried.

## D35 — Expand-all is a page-lifetime toggle, remembered nowhere — **ACCEPTED 2026-08-02 (user-directed)**
Results render as one `<details class="dict">` per dictionary, and exactly one — the highest-preference dictionary with hits — opens automatically. Comparing a word across a whole collection therefore meant opening sections by hand. A `⊞`/`⊟` button now opens and closes all of them.

The interesting decision was where the state lives, and the answer is **nowhere**.

**Not on the server.** D33's rule ends *"a switch the server cannot see is a switch that does nothing"* — that clause was written about disabling a dictionary, which was a decoration until `Warm()` could act on it. Expand-all is the mirror case: it has **no server-side consequence at all**. The same NDJSON is streamed, `perDict` is unchanged, nothing is opened, indexed or skipped differently. The switch does its entire job in the browser, so putting it in `state.json` would have bought a `UIPrefs` struct, a schema change, merge semantics and tests for a value the server would never read.

**Not in localStorage either**, which is where `wudict_theme` and `wudict_wide` live. The sharper discriminator behind D33's look/meaning heuristic is **how expensive the state is to recreate**: a curated order and enabled set across a hundred dictionaries is minutes of work, so losing it to a port change (localStorage is origin-scoped) is a real injury. Expand-all is one click. Persisting it only buys the failure mode where a user enables it once on a wide screen and meets an inexplicably different app on a laptop weeks later, with nothing on screen to explain why.

**Page lifetime is the sweet spot, and it is self-clearing.** One `let expandAll=false`. Reload returns to the default; there is no tomorrow in which it surprises anyone. It survives searches *within* the page, which is the point — the people who want this are comparing term after term, and a click-scoped action would charge them a click per query, penalising exactly the workflow it exists for.

**A toggle, not a one-shot action, because the two directions are symmetric.** VS Code's explorer offers *Collapse All* with no inverse, and that works only because the directions are asymmetric there: collapsing is bounded, expanding a file tree is unbounded. Here both directions are bounded and equal — N dictionaries, all open or all shut — and expanding by one click while collapsing costs one click per dictionary would be a one-way door. Symmetric operations want a toggle.

The default is untouched: auto-open the top-preference dictionary, which gets the user reading with no scrolling and is right for almost every search.

Two implementation notes. The auto-open block is skipped entirely while expand-all is on, and `openedIdx` stays `null` — otherwise a lower-index dictionary arriving late would close a section being read. And `content-visibility:auto` on open sections hands back the cost: articles are built eagerly either way (`renderSlot` appends them all; the accordion only hides them), so opening pays layout and paint, which the browser can now skip for anything not scrolled to.

**Standing rule:** before choosing where a setting lives, ask what breaks if it is lost. State that is expensive to recreate earns durable storage; state that is one click away earns none, and storing it anyway only buys a way to confuse the user later.

## D36 — One `.col` geometry for the toolbar and the content — **ACCEPTED 2026-08-02**
Adding the expand-all button (D35) made the toolbar visibly wider than the result cards. The button was not the cause; it was the first thing to touch a boundary that had been in the wrong place all along.

**The measurement.** `.container` was `width:92%; max-width:800px; padding:0 var(--sp-2) var(--sp-5)` under a global `box-sizing:border-box`, so the cards sit `--sp-2` (`.618em` — φ⁻¹, from the project's own golden-ratio spacing ladder) inside their 800px box. `.bar form` was `max-width:800px; margin:0 auto` with **no gutter of its own**. Below the cap, `.bar`'s horizontal padding stood in for one and the two happened to line up; above it, nothing did, and the bar ran ~9.9px wider on each side. The misalignment therefore existed at every viewport over 600px, in a varying amount — invisible only because `justify-content:center` kept a content-sized cluster of controls away from its own edge. Five buttons filled the row, the cluster reached the boundary, and the boundary was wrong.

**The naive fix was wrong in the other direction.** Simply adding `padding:0 var(--sp-2)` to the form corrects widths above the cap and *breaks* the ≤600px case, where the form would then be inset twice — once by `.bar`, once by itself — while the cards are inset once. Two elements described by two rules that have to agree at three breakpoints (`auto` / `92%` / `800px`), in two modes (normal / wide), is six chances to drift and no mechanism preventing it.

**So the geometry is named once and worn by both.** A `.col` class carries width, cap, centring and gutter; `<main class="col container">` and `<form id="frm" class="col">` wear it, `.container` keeps only its bottom padding, and `.bar form` keeps only the flex arrangement of what is inside it. `.bar` drops its horizontal padding — it is full-bleed anyway, and the gutter now belongs to the column. The wide-mode override and the ≤600px `width:auto` are each stated once, for both. The two boxes are no longer *equal*; they are the *same*, which is the only version of this that stays true.

**Ends anchored, not centred.** `.bar form .tools{margin-left:auto}` on the first view toggle splits the row at its real semantic seam — query controls (`input`, mode, dictionary, 🔍) against view controls (`◐ ⇔ ⊞ ☰`) — so free space is absorbed in the middle and both ends stay pinned to the column. Content no longer determines width; width determines layout, and a sixth button costs nothing. It is inert at 800px, where the controls already fill the row, and does its work in wide mode.

The 🔍 button was considered for removal (Enter submits, the input is `autofocus`, `/` focuses it, and mobile keyboards render a Search key for `type=search` in a form) and **kept** by decision: it is the one control that names the app's primary verb.

**Standing rule:** when two elements must line up, do not give them matching values — give them the same rule. Matching values are a coincidence maintained by hand, and every breakpoint doubles the number of hands.

## D37 — Sticky section headers, sized by `[open]` — **ACCEPTED 2026-08-02**
Scrolling a long article lost all trace of which dictionary it came from: the `<summary>` naming it had scrolled off, and the top bar auto-hides on scroll-down, so nothing on screen answered the question.

**The header was already there; it just did not stay.** The alternatives considered all proposed *adding* something — a breadcrumb in the bar, a transient pill that fades in while scrolling, a per-dictionary colour. Each was rejected on its own terms. The breadcrumb is disqualified by our own scroll handler (`cur>80&&cur>prevScroll` hides the bar exactly while you are reading, so the information would be absent precisely when wanted). The fading pill is the worst option available: every appearance is peripheral motion, the one stimulus the visual system is built to interrupt on, spent to tell the reader something they only sometimes want. Per-dictionary hues have the best theory — colour resolves pre-attentively, before foveation — and fail in practice at 105 dictionaries, where hues stop identifying anything, and against a deliberately calm one-accent palette they would cost more composure than they buy recognition. Colour is a good redundant cue and a bad primary one.

So: `position:sticky` on the existing summary. Nothing new to learn, nothing new to render, and a second benefit that turns out to matter more than the first — **the collapse control is now permanently within reach**, so a dictionary can be closed from anywhere inside it rather than by scrolling back to find its top. With expand-all (D35) that becomes the primary way of navigating results.

**`overflow:hidden` → `overflow:clip` is what makes it work at all.** `hidden` establishes a scroll container, and a sticky element sticks to its nearest scrollport — which would have been a box that never scrolls, so the header would simply not have moved. `clip` clips to the same border-radius and creates no scrollport. One word, and the difference between working and mysteriously not.

**Two jobs, two sizes, and `[open]` already distinguishes them.** A *closed* header is a row in a list scanned across a hundred dictionaries: it wants presence. An *open* one is a context label consulted occasionally while reading: it wants to disappear. That maps exactly onto a state CSS already has, so the compact size (~39px → ~25px) needs **no sentinel element, no IntersectionObserver and no scroll handler** — and, better than any of those, the resize is triggered by a click the user just made instead of arriving as a surprise in their peripheral vision. Detecting *stuck* would have been more precise and worse: it would animate on scroll, which is the motion this design is trying not to spend. Horizontal padding moved from `em` to `rem` so the type change moves the header's height and never the name's left edge.

**`--stick` is measured, not guessed.** The bar wraps to two rows on narrow screens, so a hard-coded offset would either hide headers under it or float them below a gap; a `ResizeObserver` publishes the real height (a `resize` listener would miss the reflow caused by the dictionary `<select>` growing as names load). `body.barhidden` drops it to `0` when the bar slides away, on the bar's own `.28s`, so the two read as one piece of chrome moving rather than two things reacting to each other.

**Standing rule:** when the interface has to answer "where am I", look first for the element that already says so and ask why it left. Adding an indicator is the second-best answer to a question a persisting label answers for free.

## D38 — Section scroll corrections: two rules, both conditional — **ACCEPTED 2026-08-02**
Should clicking an accordion section scroll it into view? **Not unconditionally**, and the two directions fail differently enough that they need different rules.

**Scrolling every opened section to the top is wrong here, for a reason specific to this app.** The top-preference dictionary is already open when results arrive, so clicking a *second* summary is nearly always an act of **comparison** — "and what does Chambers say?". Moving the page to put the new section at the top takes the one being read off screen and turns comparison into replacement. Two further objections: expanding a section pushes only what is *below* it, so the summary the user clicked never moves and their visual anchor is already perfect; and under expand-all (D35) the behaviour would fire once per dictionary.

**Open needs help only when it revealed nothing.** Click a summary sitting near the bottom of the viewport and the content unfolds entirely below the fold — the user asked to see something and saw nothing. So: if the section's top is below half the viewport, bring it up to the bar; otherwise do nothing. Silence in the common case.

**Close needs help not to vanish, and that need is one D37 created.** Before sticky headers, collapsing a section meant scrolling back to its top first, so closing could never disorient. Now it can be collapsed from 3000px inside itself, after which the document shrinks, the browser clamps the scroll position, and the user lands somewhere arbitrary — often the end of the page. Returning them to the row they just closed is not taking control away; it is honouring the position they still implicitly occupy. Firefox and Chrome's scroll anchoring hides some of this. Safari does not.

That asymmetry is not the usual smell of a wrong rule, because the two cases have different causes: open occasionally fails to *reveal*, close fails to *stay*.

**Three implementation traps, all avoided.** (1) The `toggle` event fires for programmatic opens too — `renderSlot` sets `det.open = expandAll` on every arriving row, so a `toggle` handler would make the page jump while results stream in. Listening for a **click on the summary** is inherently user-initiated (and sidesteps `toggle` not bubbling). (2) The new height must be laid out before it is measured, so the decision happens in a `requestAnimationFrame` after the browser has applied the toggle. (3) Both corrections scroll **up**, which brings the auto-hidden bar back — so they must aim at the bar's real height and not at `--stick`, which is momentarily `0` while the bar is away. `--barh` and `--stick` were split for exactly this, and `scroll-margin-top:var(--barh)` on the section lets `scrollIntoView` land correctly with no arithmetic and no re-derivation when the bar rewraps.

`prefers-reduced-motion` downgrades both to an instant jump — mandatory for anything that moves the viewport without being asked.

**Standing rule:** never move the viewport to express a state change. Move it only when the alternative is the user losing their place — and then by the smallest amount that fixes it.
